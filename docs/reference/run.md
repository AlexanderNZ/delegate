# Reference: `delegate run`

`delegate run <workflow>` builds the [**tickets**](../glossary.md#ticket) of a [**workflow**](../glossary.md#workflow). For each ticket, the [**engine**](../glossary.md#engine) makes a [**worktree**](../glossary.md#worktree), spawns the [**specialist**](../glossary.md#specialist) of the [**stack**](../glossary.md#stack) through a [**harness**](../glossary.md#harness) [**adapter**](../glossary.md#adapter), checks the specialist report, runs the [**gates**](../glossary.md#gate) itself, and records each event in a [**journal**](../glossary.md#journal). In [**`assure`**](../glossary.md#assure) [**mode**](../glossary.md#mode), the engine then verifies the branch with a [**blind**](../glossary.md#blind) [**verifier**](../glossary.md#verifier), and moves the [**run branch**](../glossary.md#run-branch) to the branch only on [**ACCEPT**](../glossary.md#accept). A [**REJECT**](../glossary.md#reject) starts a [**fix-up**](../glossary.md#fix-up) round, up to two rounds. In [**`economy`**](../glossary.md#economy) mode, the engine builds a [**chain**](../glossary.md#chain) of branches, runs no gate for one ticket, and at the end runs the gates once and verifies once for each stack. See [the economy chain](#the-economy-chain) and [the chain verification](#the-chain-verification). A specialist that ends capped or failed, whose gates are red, or whose report is not valid after it committed work, continues in the same worktree, up to the limit of the mode. A ticket that passes all of these is in the built state.

A [**coordinator**](../glossary.md#coordinator) can stop a [**run**](../glossary.md#run) and go on later with `--resume <run-id>`. See [the resume](#the-resume). To stop a run at its next step boundary, and cut off no agent, use `delegate pause <run-id>`. See [the pause](#the-pause). To go on with one failed step of a run, add `--retry <ticket>`. See [the retry](#the-retry). To see the state of a run, or to follow it, use `delegate status` and `delegate watch`. See [the reference of status and watch](status-and-watch.md).

A workflow can hold many tickets. The engine takes them in dependency order. A failed step does not end the run: a ticket whose [**blocker**](../glossary.md#blocker) failed is skipped, and the independent tickets still run.

To check a workflow file without a build, use `--dry-run`. See [the workflow reference](workflow.md).

To start a run that the shell or the harness cannot stop, add `--detach`. See [the detached run](#the-detached-run).

## What a run does

1. The engine validates the workflow. A problem exits 1 and creates nothing.
2. The engine checks that no other run holds the lock of the run branch. See [the run lock](#the-run-lock). A held lock exits 1 and creates nothing.
3. The engine checks that `base-branch` is a branch of the repository and that no ticket branch exists. A problem exits 1 and creates nothing.
4. The engine takes the lock.
5. The engine creates the run branch at the commit of `base-branch`, and writes `run-start` to a new journal. That commit is the base of the run. See [the base of the run](#the-base-of-the-run).
6. For each ticket in dependency order, the engine does the [**step**](../glossary.md#step) below, or skips the ticket. See [the skip rule](#the-skip-rule). A failed step does not end the run.
7. In `economy` mode, the engine verifies the chain. See [the chain verification](#the-chain-verification).
8. The engine writes `run-end`, and releases the lock.

A step has these parts:

1. Make a worktree and the branch `<run-branch>-<ticket id>` from the base of the run, and install the [**push guard**](../glossary.md#push-guard) in it. See [the guards](#the-guards). In `economy` mode the branch starts from the tip of the previous ticket. See [the economy chain](#the-economy-chain). In `assure` mode, the branch of a ticket with `blocked-by` starts from the tip of the run branch, and so does every ticket branch with `ticket-start = "run-branch"`. See [the ticket start](workflow.md#ticket-start).
2. Spawn the specialist through the adapter. The prompt is the specialist brief.
3. Read the [**report**](../glossary.md#report) from the report path and check it against the schema.
4. Check that the branch holds at least one commit beyond the point where it started: the base of the run, the tip of the previous ticket in `economy` mode, or the tip of the run branch. `step-start` records that point in `base_commit`.
5. Compare the changed paths with the [**hotspot**](../glossary.md#hotspot) patterns of the stack. A match fails the step. See [the hotspot guard](#the-hotspot-guard).
6. In `assure` mode, run each gate of the stack in the worktree. The engine runs all gates, also after a red gate. A gate that the journal holds green on the same commit does not run again. See [one green gate run for each commit](#one-green-gate-run-for-each-commit). A specialist that ends `failed` or `capped`, a red gate, and a report that is not valid on a branch with a commit start a [**continuation**](../glossary.md#continuation). See [the continuation](#the-continuation). In `economy` mode, the engine runs no gate here: a valid report with the status `committed`, on a branch with a commit, builds the step. The gates run once, on the tip of the chain. See [the chain verification](#the-chain-verification).
7. In `assure` mode, rebase the branch onto the run branch, and run the gates again. See [the rebase](#the-rebase-onto-the-run-branch).
8. In `assure` mode, verify the branch. See [the verifier step](#the-verifier-step).

The engine does not trust the report for the gates. A gate that is red is recorded red when the report says `gates_green` is true.

The engine never merges to `base-branch`, never pushes, and never closes a ticket. A worktree and a branch stay after a failed step.

The engine sets `core.fsmonitor` to false for each worktree (see [the push guard](#the-push-guard)) and in the configuration of each verifier copy that it makes, and it stops the fsmonitor daemon of a copy before it removes the copy, so a run leaves no daemon behind, whatever the global git configuration of the user is.

### The base of the run

A run has one base: the commit of `base-branch` at the start of the run. The journal records it in the field `base_commit` of `run-start`. The run branch starts at that commit.

- No ticket branch starts from `base-branch` itself. Other work can land on `base-branch` while the run goes on, and the run does not see it. A ticket branch starts from the base of the run, from the tip of the run branch, or from the tip of the previous ticket in `economy` mode.
- So the rebase onto the run branch copies no commit of `base-branch` onto a ticket branch, and the verifier diff and the hotspot guard see only the commits of the ticket.
- A [**resume**](../glossary.md#resume) uses the `base_commit` of `run-start`, not the tip of `base-branch`. A journal from version 1.2.0 or earlier has no `base_commit` in `run-start`. The resume then uses the `from_commit` of the first `run-branch-advance`, or the tip of the run branch when the run branch did not move. The run branch started at the base of the run and moves only by fast-forward, so both are the base of the run.
- To give a run the newer commits of `base-branch`, start a new run.

## The continuation

A specialist that ends `capped` or `failed`, whose gates are red, or whose report is missing or not valid after it committed work, continues in the same worktree. The commits that it made stay on the branch. The engine does not make a new worktree or a new branch.

- A specialist ends `capped` or `failed` when the adapter result has the [**end state**](../glossary.md#end-state) `capped` or `failed`. The engine does not read the report of that run. A result `finished` with an exit status other than 0 and no valid report also counts as `failed`. See [the end of an agent session](#the-end-of-an-agent-session).
- A specialist whose gates are red has a valid report with the status `committed`, and at least one gate of the stack exits with a status other than 0. This trigger is only in `assure` mode. In `economy` mode, red gates on the tip of the chain start a fix-up round. See [the chain verification](#the-chain-verification).
- **A report that is missing or not valid, on a branch with work, gets a continuation for the report only.** The check of the report fails: there is no file at the report path, or the text is not JSON, a field is missing, a field has the wrong type, or a value is not permitted. The branch holds at least one commit beyond the point where it started. The code can then be correct, so the engine does not fail the step. It sends a continuation that asks only for a corrected report. The trigger is `report-missing` when there is no report file, and `report-invalid` when the file is there. This prompt has a `## Continuation` section, a `## Commands` section with the foreground rule of the specialist brief, and a `## Report` section. It holds the ticket id, the report path, each problem of the check on its own line, the commits on the branch, and the shape of the report. It tells the specialist to write only the report, and to change no file and add no commit. It does not give the task again, so the prompt is the same when the engine resumes and when it starts a new agent. The engine then reads the report again, and the step goes on from the check of the report.
- A report that is missing or not valid, on a branch with no commit beyond its start, fails the step. A valid report with a status other than `committed` fails the step. None of these starts a continuation.
- For the other triggers, the continuation brief (`## Continuation`) holds the ticket id, the reason that the last run stopped, the commits on the branch so far, and, for a red gate, the output of the red gates. It also holds the report rule with the absolute report path, as the first brief does. The specialist continues from these commits, and adds each change as a new commit.
- If the adapter has `supports_resume` set to true, and the last result has a `session_id`, the engine resumes that [**session**](../glossary.md#session). It sets `resume_session` in the request to the `session_id` of the last result, so each continuation resumes the newest session. The session keeps the context of the first brief, so the prompt holds only the continuation brief and the `## Gates` section of the specialist brief. The journal records the mode `resume`.
- Otherwise the engine starts a new agent, with `resume_session` set to `None`. A new agent has no context, so its prompt is the full specialist brief with the continuation section added. The journal records the mode `brief`. This is also the mode when the adapter supports resume but the harness gave no session id.
- The [**tier**](../glossary.md#tier) and the model are those of the first specialist run.
- The engine journals `continuation` before each continuation, with the count, the trigger, the commits, and the reason.

One count covers the five triggers. Each mode has a continuation limit:

| Mode | Limit |
|---|---|
| `assure` | 2 |
| `economy` | 1 |

When the specialist is not done after the limit, the step fails. The journal records `continuation-limit` with the count, and the reason of the step ends with `the continuation limit of <n> is reached`. The branch and the worktree stay, with all commits. The fix-up specialist of an `assure` round is not continued: its failure fails the step.

## The end of an agent session

Two rules decide how the engine reads the end of an agent session. They apply to the specialist, the fix-up specialist, and the verifier.

**A valid report and a success continue the step, whatever the exit status.** The end state of the adapter result comes from the last result event of the session. The exit status does not change it. When the end state is `finished` and the exit status is not 0, the engine reads the report. A valid report continues the step, as with the exit status 0. For example, a coordinator stops an idle session with SIGTERM after its valid report. The exit status is 143, and the step continues. When the report is missing or not valid, the run counts as `failed`, as before. The specialist then continues, and the fix-up specialist and the verifier fail the step. The end states `capped` and `failed` are never a success, also with a valid report.

**After a valid report, an idle session ends.** The engine gives each agent run an idle timeout of 900 seconds and a check of its report. While the agent runs, the adapter watches the stream of the session. The report can be valid, and the agent can write no event to the stream for 900 seconds. Then the adapter ends the session: it sends SIGTERM, and SIGKILL after 10 seconds more. The adapter result has `ended_idle` set. The journal records `idle-timeout` just before the result event of that agent. The step continues with the report, whatever the end state and the exit status. A session that ends at the idle timeout is not a failure, so it does not start a continuation.

The idle timeout is longer than the ten minutes that a harness gives one foreground command at most. A foreground command writes no event while it runs. So the engine does not stop an agent that waits for one.

## The resume

`delegate run --resume <run-id>` goes on with a run that stopped or paused. A run stops when its process is killed, or is interrupted with Ctrl-C. See [Ctrl-C](#ctrl-c). A run pauses at a step boundary after `delegate pause`. See [the pause](#the-pause). Such a run has no `run-end` in its journal. The run id is on the line `run <run id>` that the command printed, and it is the name of the directory in `runs/`.

The engine rebuilds the state of the run from its journal, and starts at the first step that is not complete. It appends to the journal and never rewrites a line. It writes `resume` first, and `seq` goes on from the last line. The workflow must be the one that the run started from: `mode`, `adapter`, `base-branch` and `run-branch` must be the same. If one differs, the command exits 1 and names the field. The tickets can differ from the newest plan of the run: that is a plan change, and its rules decide. See [the plan change](#the-plan-change). A run that has a `run-end` cannot be resumed, unless the resume has a plan change or `--retry`.

The engine treats each ticket by what the journal holds for it:

| State in the journal | What the [**resume**](../glossary.md#resume) does |
|---|---|
| `step-end` (built, or failed) | The step is complete. The engine does not build it again, and it gives the adapter no invocation. |
| `skip` | The ticket stays skipped. |
| `run-branch-advance`, and no `step-end` | The run branch holds the commit already. The engine writes `step-end` with the state `built`, with no invocation. |
| `step-start`, and no `step-end` | The step is open. The engine uses its worktree and branch again. See below. |
| nothing | The ticket did not start. The engine builds it as in a new run. |

An open step goes on as follows:

- The worktree is used again as it is. A rebase that the stop left half done is aborted. If the worktree is gone, the engine makes it again on the same branch.
- A ticket that did not start yet starts from the base of the run that `run-start` records, not from the tip of `base-branch`. See [the base of the run](#the-base-of-the-run).
- After a `rebase` with the result `rebased`, the commits of the ticket are the commits beyond the `onto_commit` of the newest such event. The hotspot guard and the continuation brief use this point, so they do not see the commits of the run branch under the ticket.
- If the journal shows a valid report after the last time the specialist was spawned, the engine does not spawn the specialist again. It runs the gates, and the step goes on from there. A gate that the journal holds green on the commit of the branch does not run again. So a resume after a stop at the verifier runs no gate on that commit.
- Otherwise the engine spawns the specialist in the same worktree. If the branch holds commits beyond the point where it started, the prompt is a continuation brief with the reason `the run was interrupted`. If it holds none, the prompt is the first brief. A new agent has no context, so the engine never resumes a session across a stop.
- The continuations that the journal holds count against the limit of the mode.
- In `assure` mode, the verification starts again with a full pass. The first verifier of the resume has the round number equal to the number of [**verdicts**](../glossary.md#verdict) that the journal holds, and the limit of two fix-up rounds counts across the stop. A verifier run that ended with no verdict does not count: for example, a verifier that a stop or the time limit of a harness killed. The resume runs that round again.

## The pause

`delegate pause <run-id>` asks a run to stop at its next step boundary. The run does not cut off an agent or a gate, so the work that runs now is not lost. To stop a run at once, press Ctrl-C or stop its process. See [Ctrl-C](#ctrl-c) and [the resume](#the-resume).

```
delegate pause <run-id> [--repo <repo>]
```

The command writes the request file `pause-request` in the directory of the run, beside its journal. It sends no signal, so it works from any shell on the same host. It prints `run <run id>: pause requested; the run stops at its next step boundary` and the path of the request, and exits 0. A second request before the engine reads the first one writes the file again.

The engine reads the request at each step boundary:

- Before the step of a ticket starts. In `economy` mode, the step of a ticket ends when the specialist reports, so a pause during a specialist lets the step end, and the next step does not start.
- Before a gate runs. In `assure` mode, the gates come after the specialist, so a pause during a specialist stops after its valid report, before its gates. A gate that does not run again (`gate-skip`) is not a boundary.
- Before a verifier starts. In the verification of an `economy` chain, a pause during the gates of the chain stops after the gates, before the verifier.

At the boundary, the engine writes `pause-requested` with the time of the request, then `paused` with the ticket and the work that did not start. It removes the request file. The run writes no `run-end`. It releases the [**run lock**](../glossary.md#run-lock), and the command prints `paused <where>; go on with delegate run --resume <run-id>` and exits 3. A run with no step boundary left ends as usual, and the engine removes the request file.

`delegate status` shows the run as `pausing` while the request waits, and as `paused` after `paused`. See [the reference of status and watch](status-and-watch.md#delegate-status). `delegate watch` exits with the code 7 at `paused`.

To go on, use `delegate run --resume <run-id>`. The resume goes on from the boundary as from a stop: an open step continues in its worktree, a specialist with a valid report is not spawned again, and a gate that the journal holds green on the same commit does not run again. See [the resume](#the-resume). The resume accepts a plan change under its rules. So you can pause a run, add or change a ticket that has not started, and go on. See [the plan change](#the-plan-change). The resume removes a request that a process before it did not read.

The command refuses these runs, and writes no file. It exits 1, and the message names the run:

- A run that has ended: it has a `run-end`, and no `resume` after it.
- A run that is paused already.
- A run whose process stopped: no live process holds the lock of its run branch. Such a run needs no pause. Go on with `delegate run --resume <run-id>`.
- An unknown run id, or a journal that is not valid.

## The plan change

A resume can add tickets to a run, and change or remove tickets that have not started. The built work of the run stays. To change the plan, pause the run, stop it, or let it end. See [the pause](#the-pause). Edit the workflow file. Then run `delegate run --resume <run-id> --dry-run` to see the change, and `delegate run --resume <run-id> --reviewed <ids> --detach` to go on.

The plan of a run is the tickets in plan order, with the id, the stack, the `blocked-by` and the text of each ticket. `run-start` records it in the field `plan`, with the SHA-256 of each text. A resume compares the workflow with the newest plan of the run: the `plan` of the newest `plan-change`, or else the `plan` of `run-start`. When the plan is the same, the resume goes on as usual. When it differs, the engine applies these rules:

1. **The built part is fixed.** The built part is each ticket of the old order up to the last ticket with a `step-start`. Each ticket in it keeps its id, its text, its stack, its `blocked-by` and its place in the order. A change to one of these fields is refused, and the message names the ticket and the field. A ticket that the run skipped inside the built part is fixed too, because the run went past it.
2. **A new ticket goes after the built part.** It goes at the end, or before a ticket that has not started. The engine computes the order again from `blocked-by`, and the new order must start with the built part, in the same order. Each blocker of a new ticket must be in the plan. The branch of a new ticket must not exist.
3. **A ticket that has not started can change.** Its text, its `blocked-by` and its stack can change, and so can its place among the tickets that have not started. "The next ticket needs the new work first" is one more entry in its `blocked-by`. A changed ticket that the run skipped is no longer skipped: the [**skip**](../glossary.md#skip) rule applies to it again.
4. **No built work is changed.** A new ticket that comes before a ticket with a `step-start` is refused. The message tells the coordinator to retry the step, or to start a new run.
5. **A new ticket gets its own gates and verifier.** In `economy` mode, the verification of the chain covers each built ticket whose work the run branch does not hold. It reads only the events after the newest `retry` or `plan-change`. So a ticket that a plan change adds after the verification of the chain gets its own gates and verifier, and the tickets that the chain verification accepted are not verified again.
6. **The journal records the change.** The resume writes `resume`, then `plan-change` with the added, the changed and the removed tickets, the new order and the new plan. `delegate status` and `delegate watch` show the tickets of the newest plan, and the progress and the ETA count them.
7. **A ticket that has started cannot be removed.** A ticket that has not started can be removed.
8. **The coordinator reviews the later tickets.** A later ticket is a ticket that has not started and comes after an added or changed ticket, in the new order. A new ticket is not a later ticket. A resume with later tickets needs `--reviewed <ids>`, the ids separated by commas, or `--reviewed all`, that covers each of them. Without it, the resume is refused, and the message names the tickets to review. `plan-change` records the later tickets in `reviewed`. Read each later ticket against the added and changed tickets before the resume, and change its text or its `blocked-by` where a precondition changed.
9. **Each later ticket gets the section "Plan change".** The specialist [**brief**](../glossary.md#brief) and the full verifier brief of each later ticket get the section `## Plan change`. It names each added or changed ticket that comes before the ticket, with its text, and says where the work of those tickets is. It tells the specialist to check the assumptions of its ticket against that work, and to report `blocked`, with the reason in `blocked_reason`, and build nothing, when the ticket no longer fits. It tells the verifier to check the diff against the changed plan too. A ticket before the first added or changed ticket gets no such section.

A refused resume changes nothing: no journal line, no branch and no agent. The command exits 1 and names each ticket and field at fault.

A plan change also goes on with a run that ended: a `run-end` before the newest `plan-change` does not end the run. A plan change does not go on with a run that an [**invariant**](../glossary.md#invariant) violation halted. A journal of an earlier version of `delegate` has no `plan` in `run-start`. A resume of such a run with the same ticket ids goes on as before. A plan change on such a run is refused: the engine cannot check the built part, so start a new run.

### The dry run of a resume

`delegate run [<workflow>] --resume <run-id> --dry-run` applies the rules, and changes nothing. It takes no lock. With no plan change, it prints `run <run id>: no plan change` and the order. With a plan change, it prints:

- `old order:` and `new order:`, the ticket ids of each plan.
- One line for each rule: `rule <n>: ok: <rule>: <detail>`, or `rule <n>: refused: <rule>: <reason>`.
- `later tickets to review, in plan order:` and the later tickets, when there are any.
- `ticket <id> (added):` or `ticket <id> (changed):` and the text of each added or changed ticket, in plan order, each line indented by two spaces.

The dry run takes `--reviewed` too. It exits 1 when a rule of the plan change refuses the resume, and 0 when the rules accept it. Each refusal also goes to stderr. The dry run checks only the plan. It does not check the other conditions of a resume, for example the [**run lock**](../glossary.md#run-lock), or a run that ended with no plan change.

## The retry

`delegate run --resume <run-id> --retry <ticket>` goes on with one failed step of a run. A failed step has a `step-end`, so a resume without `--retry` does not build it again. The retry also works in a run that has a `run-end`. It takes the [**run lock**](../glossary.md#run-lock), and it builds the steps that are not complete, as a resume does.

The retry uses the worktree and the commits of the step again, and goes on at the first phase that did not complete. The phase comes from the journal events of the step. In `assure` mode the retry spawns no specialist:

| Events of the failed step | Where the step goes on |
|---|---|
| No `verify-start` | The gates. The engine checks the report of the specialist again, runs the gates, rebases onto the run branch, runs the gates again, and starts the full verifier at round 0. A step whose gates are red uses the continuations that are left. |
| A `verify-start`, and no `verdict` | The full verifier, at round 0. |
| A `verify-start` after the last `verdict`, which is a REJECT | The scoped verifier of the fix-up commit, at the same round. The engine checks the fix-up commit again: the hotspots, and the rule that it is a new commit on top of the rejected commit. The gates do not run again. |
| A REJECT as the last `verdict`, and a `fixup-report` of the next round that says `committed` | The gates of the fix-up. The engine checks the fix-up commit again and runs the gates, then starts the scoped verifier. |

The verifier round of the retry is the number of verdicts in the journal. A verifier run that ended with no verdict does not count against the fix-up limit. After the first verifier of the retry, the step goes on as usual: a REJECT starts a fix-up round, up to the limit.

The run branch can move after the step failed, when the run built another ticket after it. The branch of the step then does not hold the tip of the run branch. The engine checks a fix-up commit, rebases the branch onto the run branch, runs the gates, and starts a full verifier at the round of the retry. The rejected commit is not on the rebased branch, so a scoped verifier cannot run.

The engine writes `retry` before it goes on, then a new `step-end` and a new `run-end`. The newest `step-end` of a ticket wins, and so does the newest `run-end`. In `assure` mode, a ticket that the failed step made the engine skip stays skipped.

### The retry in economy mode

In `economy` mode the engine runs no gate and no verifier for one ticket. So a failed step of `economy` mode goes on at the specialist or at the check of its report, as an open step does after a stop:

| Events of the failed step | Where the step goes on |
|---|---|
| The last `report-validation` after the last spawn of the specialist is valid and says `committed` | The gates (`phase` `gates`). No specialist spawns. The engine checks the report, the commits and the hotspots again. The step is then built, and the gates run on the tip of the chain. |
| Any other | The specialist (`phase` `specialist`). The specialist continues in the worktree of the step. If the branch holds commits beyond its start, the prompt is a continuation brief with the reason `the step failed: <reason>`. If it holds none, the prompt is the first brief. |

The `round` of the `retry` event is 0. The retry gives the specialist the continuation limit of the mode again: the continuations of the failed step do not count, and the spawn of the retry is not a continuation, as the spawn of a resume is not.

After the step, the chain goes on. The engine checks each ticket after the step that it skipped again, with [the skip rule](#the-skip-rule): a ticket whose blockers are now built is built, from the tip of the chain. Then the engine runs [the chain verification](#the-chain-verification). It covers only the built tickets whose work the run branch does not hold yet, and it counts only the gates, verdicts and fix-up rounds after the `retry` event. So a ticket that the run before accepted is not verified again, and the fix-up rounds of the run before do not count against the limit.

### When a step cannot be retried

The command exits 1, names the ticket, and changes nothing, when the step cannot be retried:

- The ticket is not a ticket of the run.
- The step is built, was skipped, did not start, or is open. Resume an open step without `--retry`.
- In `assure` mode: the specialist, or the fix-up specialist of the next round, gave no valid report that says `committed`. A retry of `assure` mode spawns no specialist.
- In `assure` mode: the verifier accepted the branch, and the step failed after the verdict.
- In `assure` mode: the verifier rejected the branch after the last fix-up round.
- In `economy` mode: the verification of the chain failed the ticket. The chain failed as a whole.
- In `economy` mode: a ticket after it in the chain is built. The branch of that ticket does not hold the commits of the step.
- In `economy` mode: the step started from another commit than the chain gives it now. The verification of the chain added a fix-up commit to the ticket before it, or failed the tickets before it.

`--retry` without `--resume` is a usage error, and the command exits 2.

## The run lock

A lock prevents a second run on one run branch. A run takes the lock of its run branch before it changes anything, and releases it when it ends: when the run ends, when a step crashes, and when the process is interrupted with Ctrl-C. A resume takes the same lock.

- If another run holds the lock, and its process exists, the command exits 1. The message names the run branch, the run id, and the process id of the holder: `run branch <name> is in use by run <run id> (process <pid>)`. The run in progress is not changed. `--break-lock` does not remove the lock of a process that exists.
- A process that is killed cannot release its lock. The next run finds a lock whose process no longer exists.
- `--resume <run-id>` takes over a lock that names the same run id and a process that no longer exists. It needs no flag. The engine removes that lock, takes a new one, and goes on. It writes `lock-broken` with the run id and the process id of the old holder. When the run ends, the command prints a note on stderr: `delegate run: took over the lock of <name> from run <run id>, process <pid>, which no longer exists`.
- A lock of another run id, whose process no longer exists, stays. The command exits 1 and says so: `run branch <name> is locked by run <run id>, process <pid>, which no longer exists; pass --break-lock to remove the lock`. Nothing is changed.
- With `--break-lock`, the engine removes a lock whose process no longer exists, also the lock of another run, takes a new one, and goes on. It writes `lock-broken` with the run id and the process id of the old holder, and it prints no note. The flag is for a lock of a process that no longer exists, so check that no other run uses the branch. A process id can be used again by an unrelated process. If so, the lock looks alive. Remove the lock file by hand.
- A lock file that cannot be read exits 1 and names the file. Remove it by hand when no run uses the branch.

The lock is a file for each run branch in `locks/`, and it holds the run id and the process id. The lock protects one machine: the state is in the git directory of the repository.

## A crash in a step

An exception that the engine did not plan for is a crash. Examples are an exception from the adapter, and a failure of git in the middle of a step. A crash leaves the state of the step unknown, so it ends the run. The engine does these things in order:

1. It writes `step-end` with the state `failed`. The `reason` is `crashed: <exception type>: <message>`.
2. It writes `skip` for each ticket that it did not reach. The `blockers` list is empty, and the reason is `the run ended after ticket <id> crashed`.
3. It writes `run-end` with the result `failed`.
4. The command prints one line `delegate run: ticket <id>: crashed: ...` on stderr, and exits 1.

The branch and the worktree of the ticket stay as the crash left them.

## The skip rule

A ticket is skipped when at least one of its blockers is not built. A blocker is not built when its step failed or when it was skipped, so a [**skip**](../glossary.md#skip) passes down the chain. The engine makes no worktree and no branch for a skipped ticket. The journal records `skip` with the blockers and the reason, for example `blocked by a, which failed`. The command prints one line `delegate run: ticket <id>: skipped: <reason>` on stderr. A ticket with no unbuilt blocker still runs, also after a failed step of another ticket.

## The guards

The guards use git only, so they hold in every harness, also in a [**headless**](../glossary.md#headless) run that skips the hooks of the harness.

### The push guard

The engine installs the push guard in each worktree that it makes, also in a worktree that a resume uses again.

- The engine sets `core.hooksPath` for that one worktree only. It writes the setting, with `core.fsmonitor=false`, to the file `delegate.config` in the git directory of the worktree (`.git/worktrees/<name>/`). The configuration of the repository includes that file with an `includeIf "gitdir:<git directory of the worktree>"` section, so git reads the file in that worktree and in no other checkout. The main checkout and the other worktrees keep their own hooks, and a `pre-push` hook of the repository still runs for a push from the main checkout.
- The engine does not set `extensions.worktreeConfig`, because tools that use go-git, such as `tea`, refuse a repository with that extension. Git ignores an include whose file is missing, so the settings of a worktree go with its git directory. The engine removes the `includeIf` section of a worktree that it removes, and of each worktree whose `delegate.config` file is gone, when it makes the next worktree.
- An earlier version of the engine set `extensions.worktreeConfig`, and kept the settings in the `config.worktree` file of each worktree. When the engine makes a worktree, it moves those settings of each of its earlier worktrees to the include file, so the push guard of an earlier worktree still holds. Then it removes the extension when no `config.worktree` file holds another setting, and the repository holds `hooks/` in the [**state directory**](../glossary.md#state-directory) from an earlier run. An extension that a setting of a person needs stays, and so does an extension in a repository with no earlier run.
- The directory that `core.hooksPath` names is `hooks/<run id>/<ticket id>/` in the [**state directory**](../glossary.md#state-directory). It holds a `pre-push` hook that prints `delegate: push refused` on stderr and exits 1, so every push from the worktree fails.
- The directory also holds a wrapper for each other hook of the repository (or of the host, when the host sets `core.hooksPath`). The wrapper runs the original hook with the same arguments and the same input, so those hooks still run for the commits of the specialist.
- The guard does not stop a push with the `--no-verify` option, because git skips every `pre-push` hook then. It also does not stop a push from a clone or from another directory. It holds against the plain push command of a specialist in the worktree.

### The hotspot guard

After the specialist reports `committed` and the branch holds a commit, and before the gates run, the engine compares the paths that the branch changed since the point where it started (the `base_commit` of `step-start`) with the `hotspots` of the stack. After a fix-up specialist, the engine compares the paths that changed since the rejected commit. The engine does this in every mode.

- A changed path is a path that is added, changed, or deleted. A rename counts as its old path and its new path.
- A pattern that ends with `/` names a directory. It matches every path below the directory.
- Any other pattern is matched against the whole path with `fnmatch` rules: `*` matches any characters, also `/`. A pattern that names a directory also matches every path below it. `LICENSE` matches `LICENSE` and does not match `LICENSE.md` or `docs/LICENSE`.
- A match fails the step at once. The engine writes `hotspot-finding` and the step ends with a reason that names each path: `hotspot finding: <path> matches the hotspot '<pattern>'`. No gate runs, no continuation starts, and no verifier starts. The branch and the worktree stay as they are, and the run branch does not move.
- A change outside the hotspots goes on to the gates and the verification.

### The worktree invariant

The verifier works in a [**temporary copy**](../glossary.md#temporary-copy). It must not change the real worktree of the ticket, which is the worktree where the specialist built the branch. The engine checks this in every harness, also in one with no command guard.

- Before each verifier run, the engine takes a snapshot of the worktree of the ticket: the HEAD commit, and for each path that `git status` reports, the status code and a hash of the content of the file. A file that git ignores is not in the snapshot. The engine takes the snapshot again when the verifier ends.
- A difference is an [**invariant**](../glossary.md#invariant) violation. A verifier that commits, that adds or deletes a file, that edits a tracked file, or that rewrites a file which was already changed or untracked, makes the snapshots differ. The engine does this check for the first verifier of a ticket and for the verifier of each fix-up round.
- A violation halts the run. The engine writes `verify-result`, then `invariant-violation` with the worktree, the HEAD commit before and after, and one entry in `changes` for each path that differs. The engine writes `step-end` with the state `failed` and the reason `invariant violation: ...`. It writes `skip` for each ticket that it did not reach, with the reason `the run ended after ticket <id> halted the run`. It writes `run-end` with the result `failed`. The command prints one line `delegate run: ticket <id>: invariant violation: ...` on stderr, and exits 1.
- The [**verdict**](../glossary.md#verdict) does not count. The run branch does not move, also when the report on disk says ACCEPT. The branch and the worktree stay as the verifier left them. A run that a violation halted cannot be resumed.
- A verifier that writes only in its temporary copy does not halt the run. The engine removes the copy after each verifier run, also when the run halts.
- The check covers the worktree of the ticket. It does not cover the main checkout of the repository, which the coordinator can change at any time, and it does not cover a path outside the repository.

## The rebase onto the run branch

In `assure` mode, the engine rebases the ticket branch onto the run branch before the verifier starts, and runs the gates again on the rebased tree. A ticket branch that starts from the run branch (a ticket with `blocked-by`, or `ticket-start = "run-branch"`) holds the run branch already, so its rebase has no conflict. A ticket branch that starts from the base of the run holds no commit that the run branch does not hold, except its own. So the rebase copies only the commits of the ticket. The first gate results have the phase `build`. The gate results after the rebase have the phase `rebase`. A rebase that changes the commit runs the gates again, so the journal shows a gate result before and after the rebase. A rebase that keeps the commit runs no gate again: for example, when the run branch is still at the commit where the ticket branch started. The journal then shows `gate-skip` with the phase `rebase` for each gate. See [one green gate run for each commit](#one-green-gate-run-for-each-commit).

- The engine writes `rebase` with the run branch tip (`onto_commit`) and the branch tip before (`from_commit`) and after (`to_commit`) the rebase.
- A rebase that stops with a conflict fails the step. The engine aborts the rebase, so the branch keeps its commits and the worktree is clean. The journal records `rebase` with the result `conflict` and the conflicting files in `files`. The independent tickets go on.
- A rebase that fails for another cause fails the step. The result is `failed`, and the reason holds the message of git.
- A branch with no commit beyond the run branch after the rebase fails the step. The run branch holds its work already.
- A red gate after the rebase fails the step. No verifier starts.

The engine does not rebase in `economy` mode.

## One green gate run for each commit

The engine does not run a gate again on a commit for which the journal holds a green result of that gate. Before each gate, the engine reads the commit that the worktree has checked out. If the journal holds a `gate-result` of the same command on that commit, with `green` true, the gate does not run. The engine writes `gate-skip` with the commit, the `seq` of the green result in `green_seq`, and the reason. The gate counts as green, and the step goes on.

- A rebase that keeps the commit runs no gate again. The `rebase` event then has the same `from_commit` and `to_commit`. The green gate results of the phase `build` are valid for the rebased commit.
- A rebase that changes the commit runs the gates again on the new commit.
- `delegate run --resume` after a stop at the verifier runs no gate on the commit whose gates the journal holds green. The journal of the resume shows `gate-skip` for the phase `build` and for the phase `rebase`.
- A red result does not count. A gate that was red on a commit runs again on that commit, for example in a retry.
- A `gate-result` without `commit`, from a journal of an earlier version, does not count.
- The rule looks at the commit only. A gate whose result depends on a file outside the commit, or on the environment, keeps its first green result for that commit.

## The economy chain

In `economy` mode, the tickets form a chain. Each ticket branch starts from the tip of the previous ticket, so a dependent ticket sees the work it depends on.

- The previous ticket is the last ticket before it, in the order of the plan, that was built. A ticket that failed or was skipped is not part of the chain, and its branch is not a start point.
- The first ticket starts from the base of the run. So does a ticket whose earlier tickets all failed or were skipped.
- `step-start` records the start commit in `base_commit`. The commits of a ticket are the commits beyond `base_commit`. The check for a commit, the hotspot guard, and the continuation brief all use this point, so the commits of earlier tickets in the chain do not count for a ticket.
- The specialist runs on the tier `standard`. The `specialist` entry of `tier-overrides` replaces it.
- The engine does not rebase in `economy` mode.

## The chain verification

In `economy` mode, the engine runs the gates and verifies once for each stack, after the last ticket of the chain. The engine does not run the gates or verify a ticket by itself, and it does not move the run branch before the end.

1. The chain holds the tickets that were built. The stacks are the stacks of these tickets, in the order of their first ticket.
2. For each stack, the engine first runs the gates of the stack once, on the chain tip, in the worktree of the last ticket of the chain. The gate events have the phase `chain`. A gate that the journal holds green on the same commit does not run again. See [one green gate run for each commit](#one-green-gate-run-for-each-commit).
3. Red gates start a fix-up round. The fix-up specialist of the stack works on the chain tip, in the worktree of the last ticket. Its [**brief**](../glossary.md#brief) holds the red gates and their output in `## Findings to fix`, and the commit with the red gates in `## Rejected commit`. The fix-up is a new commit on the chain tip. The engine then runs the gates again.
4. Green gates go on to one verifier. The verifier tier is `verifier`, as in `assure` mode, whatever the tier of the specialists is. The verifier works in a temporary copy of the chain tip. The [**brief generator**](../glossary.md#brief-generator) makes the [**brief**](../glossary.md#brief) (`chain_brief`). It holds the text of each ticket of the stack and, for each of them, the diff of the commits that the ticket added (`git diff <base>...<tip>`). It holds no diff of a ticket of another stack. It also tells the verifier to start each [**finding**](../glossary.md#finding) with the id of its ticket in square brackets, for example `[b] The header row is missing.` When red gates caused fix-up commits before this verifier, the brief also holds their [**delta**](../glossary.md#delta) (`git diff <commit with the red gates>..<tip>`). When the fix-up commits of the stacks before this stack change a file of a ticket of this stack, the brief also holds their delta, and names those files. See [the fix-ups and the other stacks](#the-fix-ups-and-the-other-stacks).
5. The `## Gates` section of the verifier brief gives the gate commands, the commit, and the output of the green gates. It tells the verifier not to run the gates again. The verifier can run a single test or another command to check a claim.
6. On ACCEPT, the next stack is verified.
7. On REJECT, the stack gets a fix-up round. The fix-up is a new commit on the chain tip. It runs in the worktree of the last ticket of the chain, with the specialist of the stack and the findings verbatim. The engine then runs the gates of the stack on the new tip. Red gates start a fix-up round, as in step 3. Green gates go on to a fresh verifier with the scoped brief: the findings, the [**delta**](../glossary.md#delta) from the rejected commit, and the output of the green gates. The steps of [the fix-up round](#the-fix-up-round) apply.
8. The rounds of red gates and of a REJECT count together. The limit is 2 rounds for each stack in `economy` mode. Red gates or a REJECT after the second round fail the stack, and the run. The engine does not verify the stacks after it.
9. When every stack is accepted, the engine moves the run branch to the chain tip by fast-forward, and writes `run-branch-advance`. The run branch moves only then.

### The fix-ups and the other stacks

A fix-up commit of a stack goes on the chain tip, so it can change a file of a ticket of another stack. The files of a stack are the files that the tickets of the stack changed, by the old name and the new name of a renamed file. The rule has two directions:

- **A stack that the engine verifies after the fix-up.** The first verifier of the stack is a full pass. When the fix-up commits of the stacks before it change a file of the stack, its brief holds the delta of those fix-up commits, `git diff <chain tip before the first fix-up>..<tip when the stack starts>`, in the section `### The fix-ups of the stacks before this stack`. The section names the files of the stack that the fix-ups change. When the fix-ups change no file of the stack, the brief does not hold them.
- **A stack that the engine verified before the fix-up.** The engine does not verify that stack again. No verifier checks the fix-up against the tickets of that stack, and the journal does not record it. The verifier of the fix-up sees it only in its delta. Before you merge the run branch, read each fix-up of a later stack that changes a file of an earlier stack: `git diff <rejected_commit>..<run branch>`, with the `rejected_commit` of the first `fixup-start` of the later stack.

The events of a stack carry the id of the last ticket of the stack in `ticket`. `verify-start`, `verdict` and `fixup-start` also carry `stack` and `tickets` (the ids of the tickets of the stack). `fixup-start` also carries `trigger`: `gates-red` or `reject`.

### The finding map

A finding maps to a ticket when it starts with `[<ticket id>]` and the id is a ticket of the stack. The `verdict` event holds `mapped` (a map from a ticket id to its findings, without the label) and `unmapped` (the findings that map to no ticket, unchanged). A finding with an unknown label, or with no label, is unmapped. The engine never drops it: the journal holds it, and the command prints `delegate run: unmapped finding: <finding>` on stderr when the stack fails.

When a stack fails after the last fix-up round:

- Each ticket that a finding of the last verdict names fails. The reason is `the verifier rejected the chain after 2 fix-up rounds: <its findings>`.
- If no finding names a ticket, every ticket of the stack fails, with the reason `the verifier rejected the branch after 2 fix-up rounds: <all findings>`.
- If the gates are red, every ticket of the stack fails, with the reason `gates red on the tip of the chain after 2 fix-up rounds: <red gate commands>`.
- The tickets of the stacks that were not verified fail with the reason `not verified: the chain ended when the verification of the stack '<name>' failed`.
- The engine writes a new `step-end` with the state `failed` for each of them. The newest `step-end` of a ticket wins, in `status` and in a resume.
- The run branch does not move.

A ticket that failed in the build is not in the chain. The engine still verifies the tickets that were built. If they are all accepted, the run branch moves to the chain tip, and the run ends `failed` because of the ticket that failed.

A resume that stops before the end of the chain verifies the stacks again. A stack with an ACCEPT verdict in the journal is not verified again. Each `fixup-start` of the stack in the journal counts against the fix-up limit. A verifier run that ended with no verdict does not count. The resume goes on at the gates of the chain. A gate that the journal holds green on the tip does not run again. The first verifier of the resume is a full pass, and its brief also holds the delta of the fix-up commits of the stack.

## The verifier step

In `assure` mode, the engine verifies each ticket branch that has green gates. In `economy` mode, the engine verifies the chain at the end instead. See [the chain verification](#the-chain-verification). The steps below describe one ticket branch; the chain verification uses the same temporary copy, the same invariant check, and the same verdict report.

1. The engine makes a temporary copy of the branch. The copy is a clone with its own git directory and no remote. It holds the run branch and the ticket branch, and the ticket branch is checked out. A change in the copy cannot reach the real repository. The copy is the working directory of the verifier, so the [**verifier guard**](../glossary.md#verifier-guard) keeps the copy read-only too: to break a test for a [**red proof**](../glossary.md#red-proof), the verifier copies the copy again to another temp directory. The engine makes the copy also when the HEAD of the repository is on the run branch. The engine removes the copy when the verifier ends.
2. The engine makes the verifier brief with the brief generator (`full_brief`). The brief holds the task (the ticket text), the diff `git diff <run-branch>...<ticket branch>`, the gates of the stack, the path of the copy, the report rule with the absolute report path, and the foreground rule of the specialist brief (`## Commands`). The brief never holds a line of the specialist report. The report section names two ways to write the verdict, in this order. The first way is the Write tool, with the absolute report path as `file_path`. The rendered verifier has the Write tool, and its guard permits a Write only to an absolute path in a temp directory, with no `..` component; the report path is in a temp directory that the engine makes with `mkdtemp`. See [the verifier guard](commands.md#the-verifier-guard). The second way, for a verifier with no Write tool or a harness that refuses the Write, is the one command form that writes the verdict through the [**verifier guard**](../glossary.md#verifier-guard): `printf '%s\n' '<the JSON object>' > <report path>`, with the JSON on one line, and with each `$`, backtick, apostrophe, `<`, `>` and `&` written as a JSON escape (`\u0024`, `\u0060`, `\u0027`, `\u003c`, `\u003e`, `\u0026`). The guard refuses a heredoc and a here-string, and it refuses some of these characters in a command also inside quotes. The JSON parser of the engine reads each escape back as the same character. The fix-up brief and the chain brief carry the same section.
3. The engine spawns the verifier of the stack through the adapter. The working directory is the copy. The tier is `verifier`, whatever the tier of the specialist is. The `verifier` entry of `tier-overrides` replaces it. The model comes from the tier column of the adapter.
4. The engine checks that the verifier left the real worktree as it was. See [the worktree invariant](#the-worktree-invariant). A difference halts the run before the engine reads the verdict.
5. The engine reads the verdict report and checks it against the schema. When the verifier ended and wrote no report file, the engine takes the last JSON object with a `verdict` field from the final text of the verifier, writes it to the report path, and checks it in the same way. The journal records `source` `final-text` in `verify-report`. A permission mode that refuses a shell redirect to a file (for example Claude Code in `dontAsk` mode) refuses the printf form. On such a host the Write tool works only with a Write allow rule for the temp directory in the settings of the host. Without that rule the final text is the only way to give the verdict, and the brief tells the verifier to end its final message with the verdict object in each case.
6. On ACCEPT, the engine moves the run branch to the commit that the verifier saw. It moves the branch only by fast-forward. The rebase puts the run branch under the ticket branch, so a fast-forward is possible. If the run branch holds a commit that the ticket branch does not hold, the step fails and the run branch does not change.
7. On REJECT, the run branch does not change, and the engine starts a fix-up round. See [the fix-up round](#the-fix-up-round). After the last round, the step fails, the journal holds the findings, and the command prints them on stderr and exits 1.

The engine keeps the verdict report and the [**event stream**](../glossary.md#event-stream) of the verifier in `runs/<run id>/verifier/<ticket id>/`.

## The fix-up round

A REJECT starts a fix-up round. The limit is 2 rounds for each ticket in `assure` mode, and 2 rounds for each stack in `economy` mode. In `economy` mode, red gates on the tip of the chain also start a fix-up round, and the two causes count together. See [the chain verification](#the-chain-verification). A round has these parts:

1. The engine writes the findings of the rejected verdict to `runs/<run id>/findings/<ticket id>.fixup-<round>.md`, one finding on each line, with the prefix `- `.
2. The engine sends the specialist a fix-up brief in the same worktree. The brief holds the ticket, the findings verbatim (`## Findings to fix`), the rejected commit (`## Rejected commit`), the [**file boundary**](../glossary.md#file-boundary), the gates, and the report path. The tier and the model are those of the first specialist run.
3. The engine reads the report of the fix-up specialist and checks it, as for the first run. A specialist that ends `failed` or `capped`, a missing or invalid report, and a status other than `committed` fail the step.
4. The fix must be a new commit on top of the rejected commit. The engine asks the brief generator (`fixup_brief`) for the fix-up verifier brief. The generator refuses when the rejected commit is not an ancestor of the branch (the specialist amended or rewrote history), and when the branch tip is the rejected commit (the specialist added no commit). A refusal fails the step, and the journal records the reason in `fixup-refused`.
5. The engine runs the gates of the stack itself. In `assure` mode, a red gate fails the step. In `economy` mode, these are the gates of the chain: a red gate starts the next round, up to the limit.
6. The engine spawns a fresh verifier in a new temporary copy. The brief starts with `## Findings under verification`, so the verifier works in the mode `fix-up`. The brief holds the findings verbatim, the delta `git diff <rejected commit>..<ticket branch>` (not the full diff), the gates, the path of the copy, the foreground rule, and the report path. It never holds a line of a specialist report. The verdict report must name the mode `fix-up`.
7. On ACCEPT, the engine moves the run branch to the tip that the verifier saw, by fast-forward only. On REJECT, the next round starts. Its rejected commit is the tip that the last verifier saw, so its delta holds only the newest fix-up.

Each round spawns a new verifier with a new session. The engine never resumes a verifier session. After the second round, a REJECT fails the step with the reason `the verifier rejected the branch after 2 fix-up rounds: <findings>`. The independent tickets go on.

## Where the engine writes

All files are in the [**state directory**](../glossary.md#state-directory). By default it is `<git common dir>/delegate/`. The working tree of the repository stays clean.

### The state root of a host

A host can move the state directory of every repository out of the git directory with the environment variable `DELEGATE_STATE_ROOT`. Its value must be an absolute path. The state directory of a repository is then `<root>/<name>-<key>/`. Both parts come from the git common directory, which every worktree of a repository shares: `<name>` is the name of the directory that holds it (for a main checkout, the name of its top level), or its own name when it is not called `.git` (a bare repository or a separate git directory), and `<key>` is the first 12 hex digits of the SHA-256 of its absolute path. So one root serves every repository of the host, two repositories get two directories, and every worktree of one repository, linked worktrees included, finds the same directory and the same run lock. `delegate run`, `status`, `watch` and `--resume` all use it. A value that is not an absolute path is an error. With no value, the state directory is `<git common dir>/delegate/`, as in 1.2.0.

A host needs the state root when its agents run in a permission mode that refuses a write on a path with a `.git` component. Measured on the agent host on 2026-10-18: Claude Code in `dontAsk` mode refused `Edit` and `Write` in `.git/delegate/...`, also with an allow rule for them, and permitted them in the same layout without `.git`. With the default state directory, the specialist on that host could write neither in its worktree nor its report. Such a host also gives its agents a settings file that allows the tools they need: see [the settings of a host](claude-code-adapter.md#the-settings-of-a-host).

The paths below are relative to the state directory.

| Path | Content |
|---|---|
| `runs/<run id>/journal.jsonl` | The journal of the run. |
| `runs/<run id>/run.log` | The standard output and the standard error of a detached run process. See [the detached run](#the-detached-run). |
| `runs/<run id>/reports/<ticket id>.specialist.json` | The report path that the brief gives the specialist. |
| `runs/<run id>/findings/<ticket id>.fixup-<round>.md` | The findings that start a fix-up round. |
| `runs/<run id>/reports/<ticket id>.fixup-<round>.specialist.json` | The report path that the fix-up brief gives the specialist. |
| `runs/<run id>/reports/<report name>.stream.jsonl` | The event stream of the specialist or the fix-up specialist, beside its report. A continuation writes `<report name>.stream-2.jsonl`, then `-3`, and so on. |
| `runs/<run id>/verifier/<ticket id>/` | The verdict report (`verdict.json`), the event stream of the verifier (`verdict.stream.jsonl`), and the files that the verifier run wrote beside the report. |
| `runs/<run id>/verifier/<ticket id>/fixup-<round>/` | The same files for the verifier of a fix-up round. |
| `runs/<run id>/gates/<ticket id>/<phase>-<round>.log` | The output of one gate run, which the gate runner writes while the gate runs. The next gate run of the same phase and round writes `<phase>-<round>-2.log`, then `-3`, and so on. `gate-start` names the file. |
| `worktrees/<run id>/<ticket id>/` | The worktree of the ticket. |
| `hooks/<run id>/<ticket id>/` | The hooks directory of the worktree. See [the push guard](#the-push-guard). |
| `locks/<run branch>.lock` | The lock of a run branch while a run holds it. The branch name is percent-encoded. |

The run id is the UTC time and four hexadecimal characters, for example `20261008T093837Z-e9dc`.

## The detached run

With `--detach`, the command checks the options and the workflow first. A problem exits 1 or 2, as without `--detach`, and starts no run. Then the command starts the run in a new process with the `setsid` system call, and exits 0. The new process has no terminal, and it is outside the process group of the shell that started the command. A harness that stops its tool shell, or a background task at a time limit, does not stop the run.

The command prints two lines:

- `run <run id>`: the id of the run. Give it to `delegate status`, `delegate watch` and `--resume`.
- `log <path>`: the file `runs/<run id>/run.log` in the state directory. The run process writes its standard output and its standard error to this file, so the log holds the lines of [the output](#output-and-exit-codes) of a run in the foreground.

The command makes the directory of the run and the log before the run starts. A problem after the start, for example a lock that another run holds, goes to the log, and the run has no journal.

`--detach` also works with `--resume <run-id>` and with `--retry <ticket>`. The run id is the id of the resumed run, and the run process appends to the same log. An unknown run id exits 1 and starts nothing. `--detach` cannot go with `--dry-run`.

## Output and exit codes

On stdout, the command prints `run <run id>` and `journal <path>`. On stderr, it prints one line `delegate run: ticket <id>: <reason>` for each failed step, and one line `delegate run: ticket <id>: skipped: <reason>` for each skipped ticket. A run that paused also prints `paused <where>; go on with delegate run --resume <run-id>` on stdout.

With `--detach`, the command prints `run <run id>` and `log <path>`, and exits 0 when the run process started. The run process writes its own output to the log. See [the detached run](#the-detached-run).

When stdout is a terminal, the command also sets the title of the terminal. The title is `delegate run` when the command starts, and `delegate run · <short run id>` when the run holds its lock. The short run id is the four hexadecimal characters at the end of the run id, for example `e9dc`. With `--dry-run`, the title stays `delegate run`. When stdout is not a terminal, or when the environment variable `DELEGATE_NO_TITLE` is `1`, the command writes no title. See [the terminal title](status-and-watch.md#the-terminal-title).

| Code | Meaning |
|---|---|
| 0 | Every ticket is built. In `assure` mode, the verifier accepted every ticket. In `economy` mode, the verifier accepted every stack of the chain. |
| 1 | The workflow or the [**tier file**](../glossary.md#tier-file) is not valid, the run cannot start, a step failed, a ticket was skipped, or a verifier rejected a ticket. The message names the input. No traceback is shown. |
| 2 | A usage error. |
| 3 | A pause request stopped the run at a step boundary. The run has no `run-end`. Go on with `--resume <run-id>`. See [the pause](#the-pause). |
| 130 | Ctrl-C stopped the run in the foreground. The journal holds `interrupted`, and no `run-end`. Go on with `--resume <run-id>`. See [Ctrl-C](#ctrl-c). |

### Ctrl-C

Ctrl-C stops a run in the foreground at once. It does not wait for a step boundary, so it can cut off an agent or a gate. To stop a run at its next step boundary, use `delegate pause`. See [the pause](#the-pause). After Ctrl-C, the command does these steps:

1. It releases the [**run lock**](../glossary.md#run-lock) of the run branch.
2. It writes `interrupted` in the journal. The run writes no `run-end`.
3. It prints `run <run id>` and `journal <path>` on stdout, and one line on stderr. See the line below.
4. It exits with the code 130, as a shell gives for SIGINT. It shows no traceback.

```
delegate run: interrupted; the run <run id> stopped. Go on with delegate run --resume <run id>
```

`delegate run --resume <run-id>` then goes on as after a crash. An open step continues in its worktree. See [the resume](#the-resume). When Ctrl-C comes before the run writes its journal, there is nothing to resume: the command prints `delegate: interrupted` on stderr and exits 130. A detached run has no terminal, so Ctrl-C in the shell does not stop it.

## Why a step fails

| Reason in the journal | Cause |
|---|---|
| `the specialist ended <state> with exit status <n>` | The adapter result is `failed` or `capped`, and the engine does not read the report. Or the result is `finished` with a bad exit status, and the report is not valid. See [the end of an agent session](#the-end-of-an-agent-session). |
| `report missing: ...` | The specialist wrote no file at the report path, and the branch holds no commit beyond its start. On a branch with a commit, the specialist continues for the report first. See [the continuation](#the-continuation). |
| `report ... is not valid JSON`, `must be a JSON object`, `invalid: <field>: ...` | The report does not match the schema, and the branch holds no commit beyond its start. The message names the field. On a branch with a commit, the specialist continues for the report first. See [the continuation](#the-continuation). |
| `the specialist reported status 'blocked'` (or `'partial'`) | The report is valid, but its `status` is not `committed`. |
| `branch ... holds no commit beyond ...` | The report says `committed`, but the branch has no new commit. |
| `hotspot finding: <path> matches the hotspot '<pattern>'` | A changed path matches a hotspot pattern. See [the hotspot guard](#the-hotspot-guard). |
| `gates red: <commands>` | At least one gate command exited with a status other than 0. After the rebase, the reason ends with `(after the rebase onto <run branch>)`. |
| `crashed: <exception type>: <message>` | An exception from the adapter or from git ended the step. See [a crash in a step](#a-crash-in-a-step). |
| `<reason>; the continuation limit of <n> is reached` | The specialist was continued `<n>` times, and it still ended `failed` or `capped`, its gates were still red, or its report was still missing or not valid. `<reason>` is the reason of the last run. |
| `rebase onto <run branch> stopped with a conflict in <files>` | The rebase of the ticket branch onto the run branch had a conflict. The engine aborted the rebase. |
| `rebase onto <run branch> failed: ...` | The rebase failed with no conflict. The message holds the cause from git. |
| `branch ... holds no commit beyond <run branch> after the rebase; ...` | The run branch holds the work of the ticket already, so no commit is left. |
| `the verifier could not start: ...` | The engine could not make the copy or the verifier brief. The message holds the cause. |
| `invariant violation: the verifier changed the real worktree <path>: ...` | The worktree of the ticket differs after the verifier run. The run halts. See [the worktree invariant](#the-worktree-invariant). |
| `the verifier ended <state> with exit status <n>` | The verifier result is `failed` or `capped`, and the engine does not read the verdict report. Or the result is `finished` with a bad exit status, and the verdict report is not valid. |
| `report missing: ...`, `report ... is invalid: <field>: ...` | The verdict report does not match the schema. The message names the field. A report that names another mode than the mode of the run (`full`, or `fix-up` in a fix-up round) is invalid. |
| `the verifier rejected the branch after 2 fix-up rounds: <findings>` | The verdict is REJECT after the last fix-up round. |
| `the verifier rejected the chain after 2 fix-up rounds: <findings>` | `economy` mode. The findings of the last verdict name this ticket. See [the finding map](#the-finding-map). |
| `gates red on the tip of the chain after 2 fix-up rounds: <commands>` | `economy` mode. The gates of the stack are red on the chain tip after the last fix-up round. |
| `not verified: the chain ended when the verification of the stack '<name>' failed` | `economy` mode. The ticket is in a stack after a stack that failed. |
| `the fix-up specialist ended <state> with exit status <n>` | The adapter result of the fix-up specialist is `failed` or `capped`. Or the result is `finished` with a bad exit status, and the report is not valid. |
| `the fix-up specialist reported status 'blocked': ...`, and the report errors above | The report of the fix-up specialist is missing, is invalid, or has a status other than `committed`. |
| `the fix-up of round <n> is refused: ...` | The branch does not hold the rejected commit, or holds no commit beyond it. The message holds the cause from the brief generator. |
| `run branch <name> cannot fast-forward to <branch>: ...` | The verdict is ACCEPT, but the run branch holds a commit that the ticket branch does not hold. |

## The adapter interface

An adapter is a Python object that follows the interface in `delegate.ports.harness`. It registers by name with `delegate.adapters.register(name, adapter)`. The workflow field `adapter` names it. The built-in names `claude-code`, `opencode`, and `cursor` are valid workflow values. The adapters `claude-code` and `opencode` have implementations: see [the `claude-code` adapter](claude-code-adapter.md) and [the `opencode` adapter](opencode-adapter.md). A run with `cursor` exits 1 until an implementation registers under that name.

The adapter has the attribute `supports_resume`. It is true when the harness can resume a session. See [the continuation](#the-continuation).

The adapter has the attribute `tier_column`, which names the column of the [**tier table**](../glossary.md#tier-table) with its models. The engine resolves the model from that column. The specialist tier is `strong` in `assure` mode and `standard` in `economy` mode. The `specialist` entry of `tier-overrides` replaces it. The verifier tier is `verifier` in every mode. The `verifier` entry of `tier-overrides` replaces it, but it cannot name a weaker tier: the workflow is refused when it loads. See [the workflow reference](workflow.md#tier-overrides).

The adapter has the method `run(request)`.

| `request` field | Meaning |
|---|---|
| `agent` | The agent name, from the `specialist` field of the stack, or from the `verifier` field for the verifier. |
| `model` | The model from the tier column of the adapter. |
| `prompt` | The specialist brief, or the verifier brief. |
| `cwd` | The worktree path for the specialist. The path of the temporary copy for the verifier. |
| `report_path` | The path where the agent writes its report. |
| `event_stream` | The path of the file where the adapter captures the event stream of the harness. The engine chooses it beside the report, and never over an earlier stream: `<report name>.stream.jsonl`, then `<report name>.stream-2.jsonl`, and so on. The stream of a verifier goes in `runs/<run id>/verifier/<ticket id>/` (or its `fixup-<round>/` directory) from the start, outside the temporary copy. The directory of the file exists. The engine writes the path to the journal in `agent-start` before it calls `run`. |
| `resume_session` | The session id of the last run, when the engine resumes that session for a continuation. Otherwise `None`. The engine sets it only for an adapter with `supports_resume` set to true. |
| `idle_timeout` | The idle timeout in seconds: 900 for each agent run. See [the end of an agent session](#the-end-of-an-agent-session). |
| `report_valid` | The check of the report: a function with no argument. It reads the report at `report_path`, and gives true when the report is valid. |
| `mcp_servers` | The MCP servers of the stack, from its `mcp-servers` table: a tuple of `McpServer` values, each with a `name` and one of `command` and `url`. The tuple is empty when the stack names no server. The specialist and the verifier of the stack get the same servers. See [the workflow reference](workflow.md#mcp-servers). |

`run` returns a result.

| `result` field | Meaning |
|---|---|
| `exit_status` | The exit status of the harness process. |
| `end_state` | `finished`, `failed`, or `capped`: the end that the stream of the session gives. The exit status does not change it. |
| `session_id` | The session id, or `None` when the harness gives none. |
| `event_stream` | The path of the captured event stream: the `event_stream` of the request. |
| `ended_idle` | True when the adapter ended the session at the idle timeout. Then `report_valid` gave true, and the harness wrote no event for `idle_timeout` seconds. Otherwise false. An adapter that cannot end a session ignores `idle_timeout` and `report_valid`, and gives false. |

The adapter also has the method `activity(stream)`. It reads an event stream that the adapter captured, and returns an `Activity` with three fields. The stream can be the partial stream of an agent that still runs. `delegate status` uses it, in each form. See [the snapshot](status-and-watch.md#the-snapshot).

| `Activity` field | Meaning |
|---|---|
| `tokens_new` | The new tokens that the agent used so far, as a whole number: the input, the cache writes, and the output, with the thinking tokens. |
| `tokens_cache` | The cache reads of the agent so far, as a whole number. Each turn reads the context again from the cache, so this count grows with the turns times the size of the context. |
| `last_event` | The time (UTC) of the newest event of the stream that has a time, or `None` when the stream has no such event. When the newest event has no time and shows that the agent works, an adapter can give the modification time of the stream file. The `claude-code` adapter does this: see [its activity](claude-code-adapter.md#the-activity). |

Half a line at the end of a stream is not an error, because a live harness writes it now. A missing file, or a line before the last one that is not JSON, raises an `AdapterError`. A file that the process cannot read raises the error of the file system. `delegate status` shows no tokens and no activity for a stream that raises one of these errors. See [a stream that cannot be read](status-and-watch.md#a-stream-that-cannot-be-read).

## The specialist brief

The brief has five sections. `## Task` holds the ticket id and the ticket text. `## File boundary` holds the worktree path, the report rule, the hotspot patterns of the stack, and the no-push rule. The report rule tells the agent to write the report only at the absolute report path. Except for its worktree and the report, the agent creates, changes, or removes nothing inside the git directory. The engine keeps the worktree and the report inside the git directory, so a relative path from the worktree is not safe. `## Commands` tells the agent to run every command in the foreground, with no background task and no monitor tool. In a headless session the notifications of these tools do not come to the agent, and a monitor that stays open keeps the session alive after the report. `## Gates` holds each gate command of the stack and the gate rule. The engine runs these gates after the report, and their result decides the step. The specialist does not run a gate command itself: it runs only the tests of the code that it changes. Without this rule, each ticket runs the gates two times. In `economy` mode, the section says that the engine runs the gates once, on the tip of the chain, and not after this ticket. The fix-up brief and the continuation brief hold the same `## Gates` section. `## Report` holds the report path, the JSON type of each report field, and one example object. It says that `gates_green` states whether the tests that the specialist ran pass, and that the result of the gates of the engine decides. The engine makes this text from the field tables of the report module, so the brief and the report check always agree. The example passes the report check.

## The specialist report

The specialist writes a JSON object to the report path. A field that this table does not list is ignored.

| Field | Type | Meaning |
|---|---|---|
| `ticket` | string | The ticket id. It must equal the id of the step. |
| `status` | string | `committed`, `blocked`, or `partial`. |
| `branch` | string | The branch with the work. |
| `head_sha` | string | The tip of the branch. |
| `commits` | list of strings | The commits that the specialist added. |
| `gates_green` | boolean | The claim of the specialist that the tests that it ran pass. The engine runs the gates itself, and their result decides. |
| `summary` | string | A short account of the work. |
| `worktree` | string | Optional. The worktree path. |
| `blocked_reason` | string | Optional. The reason, when `status` is not `committed`. |
| `judgement_calls` | string | Optional. The decisions that the specialist made. |

## The verdict report

The `## Report` section of the verifier brief holds the report path, the JSON type of each field, and one example object, as in the specialist brief. The verifier writes a JSON object to the report path. A field that this table does not list is ignored.

| Field | Type | Meaning |
|---|---|---|
| `mode` | string | The mode of the verifier. It must be `full` in the first pass and `fix-up` in a fix-up round. |
| `verdict` | string | `ACCEPT` or `REJECT`. |
| `criteria` | list of objects | One object for each acceptance criterion, with the strings `criterion` and `evidence`. An ACCEPT needs at least one. |
| `gate_output` | string | The output of the gates that the verifier ran. |
| `findings` | list of strings | The defects. A REJECT needs at least one. |
| `unverified` | list of strings | What the verifier could not verify. |

## The journal

The journal is a JSONL file. The engine only appends to it. Each line is a JSON object with `seq` (the position, from 1), `time` (UTC, ISO 8601), and `event`, plus the fields below.

| `fixup-report` | `ticket`, `round`, `valid`, `path`, `reason` (`null` when valid), `status`, `blocked_reason` (as in `report-validation`) |
| `fixup-refused` | `ticket`, `round`, `reason` (the refusal of the brief generator) |
| `run-branch-advance` | `ticket`, `run_branch`, `from_commit`, `to_commit` |
| `step-end` | `ticket`, `state` (`built` or `failed`), `reason` (`null` when built). In `economy` mode a ticket can have a second `step-end` with the state `failed`, from the chain verification. The newest one wins. |
| `run-end` | `result` (`built` or `failed`), `built`, `failed`, `skipped` (lists of ticket ids) |

## Limits of this version

- In `assure` mode with `ticket-start = "base-branch"`, a ticket with no `blocked-by` starts from the base of the run, not from the accepted work of the tickets before it. The rebase puts the accepted work under the branch before the gates run again and before the verifier starts. The specialist itself does not see that work.
- The engine can resume a run only while the journal has no `run-end`, or with a plan change. A run that a crash ended cannot be resumed without a plan change: start a new run. `--retry` goes on with one failed step also after `run-end`. In `assure` mode, the tickets that the engine skipped for that step stay skipped.
- During a retry of a run that ended, `delegate status` and `delegate watch` read the old `run-end` until the retry writes a new one.
- If a process is killed between the move of the run branch and the write of `run-branch-advance`, the resume fails that step with the message `holds no commit beyond ... after the rebase`. The run branch holds the work of the ticket. Check it by hand.
- In `economy` mode, a defect shows only at the end of the chain. That is also true for a defect that the gates find. The stack of a rejected chain fails as a whole when no finding names a ticket.
- In `economy` mode, a fix-up commit goes on the chain tip. A stack that the engine verified before it does not see that commit, also when the commit changes a file of that stack. The verifier of the fix-up sees only the delta. A stack that the engine verifies after it sees the commit only when the commit changes a file of the stack. See [the fix-ups and the other stacks](#the-fix-ups-and-the-other-stacks).
- In `economy` mode, `--retry` cannot go on with a step that a later built ticket went past, or whose chain start moved. The engine does not rebase in `economy` mode, so the branch of the step cannot join the chain again.
- A gate has no time limit.
