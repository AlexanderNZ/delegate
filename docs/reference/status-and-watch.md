# Reference: `delegate status` and `delegate watch`

`delegate status` and `delegate watch` show the state of a [**run**](../glossary.md#run). They read only the [**journal**](../glossary.md#journal) of the run, and the event-stream files and the [**gate**](../glossary.md#gate) log files that the journal names. They need no [**workflow**](../glossary.md#workflow) file, and no tool beyond git, which finds the [**state directory**](../glossary.md#state-directory). They do not need `jq`. `status` reads the [**event streams**](../glossary.md#event-stream) through the [**adapter**](../glossary.md#adapter) of the run, for the tokens and the activity of each agent. It does not need the adapter: see [a run with no stream reader](#a-run-with-no-stream-reader). `watch` needs no adapter.

Both commands find the journal in the state directory of the repository, in `runs/<run-id>/journal.jsonl`. See [the journal](run.md#the-journal).

## `delegate status`

```
delegate status [run-id] [--repo <dir>] [--json | --follow] [--interval <seconds>]
```

The first line gives the run id, the result, the [**mode**](../glossary.md#mode), and the adapter. The result is `running` until the journal holds `run-end`, and then `built` or `failed`. The second line gives the progress of the run. The third line gives the path of the journal. Then each [**ticket**](../glossary.md#ticket) of the run has one line, in plan order:

```
run 20261016T030000Z-abcd: running (mode assure, adapter claude-code)
progress: 50%, 1 of 2 ended, 10m50s used, ETA 9m10s, 45k tokens
journal /path/to/repo/.git/delegate/runs/20261016T030000Z-abcd/journal.jsonl
ticket a: state built, verdict ACCEPT, branch run/demo-a, last event 2026-10-16T03:10:00+00:00
  progress: 10m00s used, 19k tokens
ticket b: state running, verdict -, branch run/demo-b, last event 2026-10-16T03:10:00+00:00
  progress: specialist, 50s used, 26k tokens, last activity 12s ago
```

The line of a ticket has this form:

```
ticket <id>: state <state>, verdict <verdict>, branch <branch>, last event <time>
```

| Part | Meaning |
|---|---|
| `state` | `pending` (no event yet), `running` (`step-start`, and no `step-end`), `built`, `failed`, or `skipped`. |
| [**`verdict`**](../glossary.md#verdict) | The verdict of the newest `verdict` event of the ticket, or `-` when there is none. A verdict of a [**chain**](../glossary.md#chain) in [**`economy`**](../glossary.md#economy) mode covers each ticket in its `tickets` field. |
| `branch` | The branch of the ticket, from `step-start`, or `-` when the ticket has no [**step**](../glossary.md#step). |
| `last event` | The time of the newest event of the ticket, or `-` when there is none. |

The progress comes from [the snapshot](#the-snapshot), and follows [the rules of the progress and the ETA](#the-progress-and-the-eta):

- The progress line of the run gives the percentage, the tickets that ended, the time used, the ETA, and the tokens. The ETA is the time from now, or `-` before the first ticket ends. A run that ended shows no ETA.
- A ticket with a [**step**](../glossary.md#step) has a line `  progress: ...` under its line. It gives the phase of a running ticket, the time used, and the tokens. While an agent of the ticket runs, it also gives the time since the last activity of the agent. While a gate of the ticket runs, it also gives `gate <command>` and `gate log changed <time> ago`: the gate command, and the time since the log file of the gate last changed. For example: `  progress: gates, 3m50s used, 19k tokens, gate python3 -m pytest -q, gate log changed 30s ago`.
- A pending ticket and a skipped ticket have no progress line.

A ticket that failed or was skipped has the line `  reason: <reason>`, after its progress line.

`status` exits 0 when it printed the run. It exits 2 when the repository has no run, when the run id is unknown, or when the journal is not valid. The message on stderr names the repository, the run id, or the journal. An event stream that cannot be read is not an error: see [a stream that cannot be read](#a-stream-that-cannot-be-read). `--json` and `--follow` together are a usage error.

### The snapshot

`status --json` prints one snapshot of the run as one JSON object. Two plugins read it, so the fields below are a contract. A new field can come in a later version. A field does not change its type or its meaning.

| Field | Type | Meaning |
|---|---|---|
| `run_id` | string | The id of the run. |
| `state` | string | `running` until the journal holds `run-end`, then the result of the run: `built` or `failed`. |
| `time` | string | The time of the snapshot (ISO 8601, UTC, whole seconds). For a run that ended, it is the time of `run-end`: the clock of the run stops there. |
| `elapsed_seconds` | integer | The time that the run used: from `run-start` to `time`. |
| `tickets_total` | integer | The number of [**tickets**](../glossary.md#ticket) of the run. |
| `tickets_ended` | integer | The number of tickets that ended: `built`, `failed`, or `skipped`. |
| `percent` | integer | The part of the run that is complete, from 0 to 100. See [the progress and the ETA](#the-progress-and-the-eta). |
| `eta` | string or `null` | The estimated time of the end of the run (ISO 8601, UTC), or `null` before the first ticket ends. See [the progress and the ETA](#the-progress-and-the-eta). |
| `tokens` | integer or `null` | The tokens of the run: the sum of `tokens` of all tickets. A ticket whose `tokens` is `null` adds nothing. `null` for [a run with no stream reader](#a-run-with-no-stream-reader). |
| `tickets` | list of objects | One object for each ticket, in plan order. See the table below. |

| Ticket field | Type | Meaning |
|---|---|---|
| `id` | string | The id of the ticket. |
| `state` | string | `pending`, `running`, `built`, `failed`, or `skipped`, as in the lines of `status`. |
| `phase` | string or `null` | For a running ticket, the phase of its [**step**](../glossary.md#step): [**`specialist`**](../glossary.md#specialist), [**`gates`**](../glossary.md#gate), [**`verifier`**](../glossary.md#verifier), or [**`fix-up`**](../glossary.md#fix-up). `null` for a ticket that does not run. |
| `elapsed_seconds` | integer | The time that the ticket used: from its `step-start` to its first `step-end`, or to `time` while it runs. 0 for a ticket with no step. |
| `tokens` | integer or `null` | The tokens of all agents of the ticket: each specialist run, each fix-up specialist, and each verifier. In [**`economy`**](../glossary.md#economy) mode, the verifier of a [**chain**](../glossary.md#chain) counts for the last ticket of its [**stack**](../glossary.md#stack). `null` for [a run with no stream reader](#a-run-with-no-stream-reader), and for a ticket with [a stream that cannot be read](#a-stream-that-cannot-be-read). |
| `idle_seconds` | integer or `null` | While an agent of the ticket runs: the seconds from the newest event of its stream to `time`. When the stream has no event with a time yet, the seconds from its `agent-start`. `null` when no agent of the ticket runs, for example in the `gates` phase. An agent runs from its `agent-start` until its result event, a `step-end`, or `run-end`. The verifier of a chain runs after its ticket ended, so a ticket that ended can show it. `null` for [a run with no stream reader](#a-run-with-no-stream-reader), and when the stream of the agent that runs [cannot be read](#a-stream-that-cannot-be-read). |
| `gate` | string or `null` | While a gate of the ticket runs: the gate command, from its `gate-start`. A gate runs from its `gate-start` until its `gate-result`, a `step-end`, or `run-end`. The gates of the phase `gates` and the gates of a fix-up round both show. `null` when no gate of the ticket runs. |
| `gate_idle_seconds` | integer or `null` | While a gate of the ticket runs: the seconds from the last change of its log file (the `gate_log` of its `gate-start`) to `time`. The gate runner appends the output of the gate to the log while the gate runs. `null` when no gate of the ticket runs, and when the log file is missing or cannot be read. It needs no stream reader. |

The phase of a running ticket follows its newest event:

| Event | Phase |
|---|---|
| `step-start`, [**`continuation`**](../glossary.md#continuation), or `agent-start` with the role `specialist` | `specialist` |
| `report-validation` that is valid, `rebase`, or `gate-start`, `gate-result` or `gate-skip` of the phase `build` or `rebase` | `gates` |
| `verify-start`, or `agent-start` with the role `verifier` | `verifier` |
| `fixup-start`, or `agent-start` with the role `fix-up` | `fix-up`. The gates of a fix-up round stay in the phase `fix-up`. |

The tokens and the time of the newest event come from the method `activity` of the adapter of the run. See [the adapter interface](run.md#the-adapter-interface), and the activity of [the `claude-code` adapter](claude-code-adapter.md#the-activity) and [the `opencode` adapter](opencode-adapter.md#the-activity).

The token count of a `claude-code` stream:

- The count of one turn or one [**session**](../glossary.md#session) adds the input tokens, the cache-read tokens, the cache-creation tokens, and the output tokens.
- When the stream holds a `result` event, the count of that session is the `usage` of the `result` event. The `usage` of an `assistant` event is partial, so it is not the count of a session that ended.
- For a session that has no `result` event yet (an agent that runs now), the count is the sum of its turns: one turn for each `message.id`, with the newest usage of that message.
- A resumed session writes its events in the same stream, after the `result` event of the earlier session. The count of the stream adds the count of each session. The streams are the files that `agent-start` and the result events name. The stream of an agent that runs now can be missing for a short time, before the [**harness**](../glossary.md#harness) opens it: it then has 0 tokens. Any other stream that is missing is [a stream that cannot be read](#a-stream-that-cannot-be-read).

### A run with no stream reader

The `status` process can have no reader of the streams of a run:

- The adapter of the run is not known to the process. For example, a script registered the adapter in its own process.
- The adapter has no method `activity`. For example, an adapter of an earlier version.

Each form of `status` then works, and exits 0. It shows the progress and the ETA. It shows no tokens and no activity: in the JSON, `tokens` and `idle_seconds` are `null`, and the lines of `status` and `status --follow` have no tokens and no last activity. `status` does not read the streams of such a run. The running gate and the time since its log changed do not need the reader, so they show.

### A stream that cannot be read

`status` only shows data. Each form of `status` works, and exits 0, when an event stream of the run cannot be read. The rule: any error from the check that the stream exists, or from the method `activity` of the adapter, makes that stream a stream that cannot be read. For example, a stream cannot be read when:

- The file is missing. The stream of an agent that runs now is the exception: before the harness opens it, it has 0 tokens.
- The process cannot search a parent directory of the file.
- The process cannot read the file, for example because the file has no read permission.
- The path is a directory.
- The file is not UTF-8 text.
- A line before the last one is not JSON.
- A line is JSON, but it is not an event that the adapter can use. For example, a line is a number or a list, a `timestamp` is not a time, a usage value of a `claude-code` stream is not a number, or a `step_finish` event of an `opencode` stream has no `part.tokens.total` number.

`status` then shows no tokens and no activity for that agent:

- In the JSON, the `tokens` of its ticket is `null`. The count of the other agents of the ticket would not be the count of the ticket.
- When the agent runs now, the `idle_seconds` of its ticket is `null`.
- The `tokens` of the run is the sum of the other tickets.
- The lines of `status` and `status --follow` show no tokens for the ticket. While the agent runs, they show no last activity for it.

Only `status` treats such a stream as no data. `delegate run` reads the stream of an agent for its [**end state**](../glossary.md#end-state), and a stream that it cannot read stays an error there.

### The progress and the ETA

The percentage:

- A ticket that ended (`built`, `failed`, or `skipped`) counts 1.
- A running ticket counts by its phase: `specialist` 0, `gates` 0.6, `verifier` 0.8, `fix-up` 0.8.
- A pending ticket counts 0.
- The percentage is the sum, divided by the number of tickets, times 100, rounded down.

The ETA:

- Before the first ticket ends, the ETA is `null`.
- After that, the ETA is `time` + M × N − R. M is the mean duration of the ended tickets. N is the number of tickets that did not end. R is the `elapsed_seconds` of the running ticket.
- The mean uses the tickets that ended after a step (`built` or `failed`). A skipped ticket has no step and no duration, so it does not count in the mean. It counts as ended.
- The ETA is never earlier than `time`. For a run that ended, it is the time of `run-end`.

In `economy` mode the verification of the chain runs after the last ticket ends. The percentage is then 100, and the ETA is `time`, until the run ends. The last ticket of each stack shows the tokens and the `idle_seconds` of the verifier of its stack.

### The follow view

`status --follow` draws the snapshot in the terminal: one line for the run, and one line for each ticket. After each interval (`--interval`, 2 seconds by default) it reads the journal and the streams again, and draws the lines again in place. It exits 0 when the run ends, after it draws the last snapshot.

```
run 20261016T030000Z-abcd running 50%, 1 of 2 ended, 10m50s used, ETA 9m10s, 52k tokens
  a built, 10m00s used, 26k tokens
  b running specialist, 50s used, 26k tokens, last activity 12s ago
```

- The run line gives the run id, the state, the percentage, the tickets that ended, the time used, the ETA, and the tokens. The ETA is the time from now, or `-`. A run that ended shows no ETA.
- A ticket line gives the id, the state, the phase of a running ticket, the time used, and the tokens. While an agent of the ticket runs, it also gives the time since its last activity. While a gate of the ticket runs, it also gives the gate command and the time since the log of the gate changed, as the plain lines do.
- For [a run with no stream reader](#a-run-with-no-stream-reader), the lines have no tokens and no last activity.
- The view cuts each line to the width of the terminal. It shows no tool call and no path.
- When standard output is not a terminal, the view prints each snapshot as plain lines, one snapshot after the other, with no cursor control.

## `delegate watch`

```
delegate watch [run-id] [--repo <dir>] [--until verdict] [--stall-minutes N] [--max-minutes N] [--from <position>] [--poll-seconds N]
```

`watch` reads the journal, prints each event as one line, and exits when it has a reason. A [**coordinator**](../glossary.md#coordinator) can run `watch` as a background task, and act on the exit code. A line has the position (`seq`), the time, the event name, and then each field of the event that is not a list or an object, as `name=value`. The field `output_tail` is not printed. Before it exits, `watch` prints the reason on a line that starts with `watch:`, and then the line `position <seq>`. The position is the `seq` of the last event that `watch` reported.

| `--max-minutes <n>` | Exit after N minutes, before a harness time limit, and print the position to go on from; N is a number greater than 0. |
| `--from <position>` | Go on after the event with this position, which an earlier watch printed; no event is reported twice. |
| `--poll-seconds <poll-seconds>` | How often to read the journal; default 1. |

### Exit codes

<!-- generated:begin watch-exit-codes -->
<!-- Generated by `delegate docs`. Do not edit this section by hand. -->

| Code | Reason | When |
|---|---|---|
| 0 | run succeeded | The journal holds `run-end` with the result `built`. |
| 1 | run failed | The journal holds `run-end` with the result `failed`. |
| 2 | error | A usage error, a repository with no run, an unknown run id, a journal that is not valid, or a `--from` position beyond the end of the journal. |
| 3 | problem | An event is a problem. See [the problem events](#the-problem-events). |
| 4 | verdict | `--until verdict` is set and the journal holds a `verdict` event. |
| 5 | stall | `--stall-minutes` is set and nothing changed for that time. |
| 6 | time limit | `--max-minutes` is set and the time is used. |

<!-- generated:end watch-exit-codes -->

Code 2 is also the code that `argparse` gives for a usage error.

`watch` checks the events in order. The first event that gives a reason ends the watch, so a run that failed exits 3 at its first problem, and not 1. The code 1 follows when `watch` goes on from the position of that problem.

### The problem events

A problem is one of these events. The line `watch: problem: ticket <id>: <reason>` names the ticket and the reason.

| Problem | The event | Reason in the line |
|---|---|---|
| A step ends blocked or partial | `report-validation` or `fixup-report` with a `status` other than `committed` | `the step ended <status>: <blocked_reason>` |
| A step ends with [**gates**](../glossary.md#gate) that are not green | `step-end` with the state `failed`, when the newest result of a gate command of the ticket is red | `the gates are not green: <commands>` |
| An agent fails | `adapter-result`, `fixup-result` or `verify-result` with the [**end state**](../glossary.md#end-state) `failed`, or (for a [**fix-up**](../glossary.md#fix-up) [**specialist**](../glossary.md#specialist) and a [**verifier**](../glossary.md#verifier)) the end state `capped` | `the <role> ended <end state> with exit status <n>` |
| An agent returns no result | `report-validation`, `fixup-report` or `verify-report` with `valid` false | `the <role> returned no valid result: <reason>` |
| A second [**continuation**](../glossary.md#continuation) of a step | `continuation` with a `count` of 2 or more | `the step continued <n> times (limit <n>, trigger <trigger>)` |
| A step fails for any other reason | `step-end` with the state `failed`, and no red gate | `the step failed: <reason>` |

A specialist that ends `capped` continues, so it is not a problem. The first continuation of a step is also not a problem. A gate that is red and turns green after a continuation is not a problem.

An agent that ends `finished` with an exit status other than 0 is not a problem at its result event. With a valid report, the step continues. Without a valid report, the next report event or the `step-end` gives the problem. An agent that `delegate run` ended at the idle timeout is also not a problem. The journal records `idle-timeout` before its result event, and `watch` does not check that result event. See [the end of an agent session](run.md#the-end-of-an-agent-session).

### The verdict

With `--until verdict`, `watch` exits at the first `verdict` event. The line is `watch: verdict: ticket <id> round <n>: <verdict>: <findings>`. For the verdict of a chain in `economy` mode, the line is `watch: verdict: stack <name> (tickets <ids>) round <n>: <verdict>: <findings>`. The [**findings**](../glossary.md#finding) are separated by `; `. Without the option, `watch` goes past each verdict.

### The stall

`--stall-minutes N` compares the time now with the newest modification time of the journal, of the event-stream files that the events name (`event_stream`), and of the gate log files that the events name (`gate_log`). If the difference is N minutes or more, `watch` exits. The line is `watch: stall: the journal, the event streams and the gate logs have not changed for N minutes; last event: <the line of the last event>`. A run that has ended is not a stall.

The journal names the [**event stream**](../glossary.md#event-stream) of an agent in `agent-start`, before the agent starts. While an agent runs, its own stream therefore shows a change too. The journal names the log file of a gate in `gate-start`, before the gate runs, and the gate runner appends the output of the gate to it. A long gate that writes output is therefore not a stall. A gate that writes no output for N minutes is a stall. A journal of an earlier version names a stream only when the agent has ended: for such a run, set N to more than the longest time of one agent run.

### The position

`--max-minutes N` ends the watch before a [**harness**](../glossary.md#harness) kills the background task. The line is `watch: time limit: N minutes are used; the run is not at its end`. Each exit prints `position <seq>`. `watch --from <seq>` goes on after that event:

- It prints no event with a position of `<seq>` or less, so no event is reported twice.
- It reads the earlier events for the problem rules. A step-end after the position still finds the red gate before the position.
- If the journal ended at or before the position, it exits with the result of the run.
- If the journal holds fewer events than `<seq>`, it exits 2.
