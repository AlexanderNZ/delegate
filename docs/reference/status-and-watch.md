# Reference: `delegate status` and `delegate watch`

`delegate status` and `delegate watch` show the state of a [**run**](../glossary.md#run). They read the [**journal**](../glossary.md#journal) of the run, and the event-stream files and the [**gate**](../glossary.md#gate) log files that the journal names. To find the [**active runs**](../glossary.md#active-run), they also read the lock of each [**run branch**](../glossary.md#run-branch), and the `run.log` of a run directory that has no journal. `status` also reads the [**pause**](../glossary.md#pause) request in the directory of the run. They need no [**workflow**](../glossary.md#workflow) file, and no tool beyond git, which finds the [**state directory**](../glossary.md#state-directory). They do not need `jq`. `status` reads the [**event streams**](../glossary.md#event-stream) through the [**adapter**](../glossary.md#adapter) of the run, for the tokens and the activity of each agent. It does not need the adapter: see [a run with no stream reader](#a-run-with-no-stream-reader). `watch` needs no adapter.

Both commands find the journal in the state directory of the repository, in `runs/<run-id>/journal.jsonl`. See [the journal](run.md#the-journal).

Each command takes the full run id, or its short id: the part after the last `-`, as `abcd` of `20261016T030000Z-abcd`. When more than one run has the short id, the command does nothing. It prints an error that names each run with that short id, and exits 2.

## `delegate status`

```
delegate status [run-id] [--repo <dir>] [--json]
```

`status` prints the state of the run once, and exits. To follow a run while it goes on, use [`delegate watch`](#delegate-watch).

With no run id, `status` shows the one active run, or the newest run when no run is active. When more than one run is active, it prints the table of the active runs that [the run picker](#the-run-picker) of `watch` shows, with no prompt. See [the run with no run id](#the-run-with-no-run-id).

The first line gives the run id, the result, the [**mode**](../glossary.md#mode), and the adapter. The result is `running` until the journal holds `run-end`, and then `built` or `failed`. A run that ended and was [**resumed**](../glossary.md#resume) is `running` again: a `run-end` that a `resume` follows does not end the run. After `delegate pause`, the result is `pausing` while the request waits in the directory of the run and the run is [active](#the-run-with-no-run-id), and `paused` from the `paused` event until a `resume`. See [the pause](run.md#the-pause). A run can stop before the [**engine**](../glossary.md#engine) reads the request: for example, after Ctrl-C, a kill or a crash. The request then stays until the next resume, and the run has no live process. Such a run is not `pausing`: the result is the state of its journal, for example `running`. A second line then gives the note `note: a pause request waits; delegate run --resume removes it`. The next line gives the progress of the run, and the line after it gives the path of the journal. Under these lines and a blank line, a table has one row for each [**ticket**](../glossary.md#ticket) of the run, in plan order. It is the ticket table of the [live view](#the-live-view) of `watch`, on the same tracks, with three more columns: [**`verdict`**](../glossary.md#verdict) and `branch` after `after`, and `last event` at the end. Each further phase of a running ticket is on a sub-row, as in the live view. `status` prints one snapshot, so the table has no live tail. The example below is the output for a locale that is not UTF-8, with the ASCII glyphs. With a UTF-8 locale, the same cells hold the glyphs of the live view:

```
run 20261016T030000Z-abcd: running (mode assure, adapter claude-code)
progress: 45%, 1 of 4 ended, 18m20s used, ETA 21m40s, tokens 58k new, 0 cache
journal /path/to/repo/.git/delegate/runs/20261016T030000Z-abcd/journal.jsonl

  #      plan    state     phase          after     verdict  branch              used    new   cache  last event
  1      * a     + built                            ACCEPT   run/demo-a        10m00s    39k       0  2026-10-16T03:10:00+00:00
  2  |   > b     running   specialist +                      run/demo-b         8m20s    19k       0  2026-10-16T03:16:00+00:00
     |                     gates +
     |                     verifier *
     |                     fix-up o
  3  |   . c     pending
  4      . d     pending
```

The progress line comes from [the snapshot](#the-snapshot), and follows [the rules of the progress and the ETA](#the-progress-and-the-eta). It gives the percentage, the tickets that ended, the time used, the ETA, and the tokens as `tokens <new> new, <cache> cache`. See [the token counts](#the-token-counts). The ETA is the time from now, or `-` before the first ticket ends. A run that ended or paused shows no ETA. In [**`economy`**](../glossary.md#economy) mode, while the verification of the [**chain**](../glossary.md#chain) runs, the line starts with its phase. For example: `progress: verifier, 66%, 2 of 2 ended, 16m40s used, ETA 5m51s, tokens 39k new, 1.2M cache`.

The columns of the table:

| Column | Meaning |
|---|---|
| `#` | The position of the ticket in the plan. |
| (no header) | The rail `│` when the one [**blocker**](../glossary.md#blocker) of the ticket is the row directly above, as in the live view. |
| `plan` | The node glyph of the state, and the id of the ticket, as in the live view. |
| `state` | `pending` (no event yet), `running` (`step-start`, and no `step-end`; or a `retry` after the `step-end`), `built`, `failed`, or `skipped`. |
| `phase` | For a running ticket, the first phase on its row, and each further phase on a sub-row, as in the live view: `✓` for a phase that is done, `●` for the phase that runs, and `○` for a phase that is to come. Only phases go in this column. |
| `after` | The ids of the blockers of the ticket when the rail does not join it to its blocker, as in the live view. |
| `verdict` | The verdict of the newest `verdict` event of the ticket. Empty when there is none. A verdict of a [**chain**](../glossary.md#chain) in [**`economy`**](../glossary.md#economy) mode covers each ticket in its `tickets` field. |
| `branch` | The branch of the ticket, from `step-start`. Empty when the ticket has no [**step**](../glossary.md#step). |
| `used` | The time that the ticket used. Empty when the ticket has no step. |
| `new`, `cache` | The two [token counts](#the-token-counts) of the ticket. Empty when the ticket has no step, or has [a stream that cannot be read](#a-stream-that-cannot-be-read). For [a run with no stream reader](#a-run-with-no-stream-reader), the table has no such columns. |
| `last event` | The time of the newest event of the ticket, as the journal records it (ISO 8601, UTC). Empty when there is none. |
| (no header) | For a ticket that failed or was skipped, the reason, with no path. In a paused run, the row of the ticket that the pause stopped before gives `paused before this step`, `paused before the gate` or `paused before the verifier`. `status` has no live tail: the activity of an agent and the gate that runs are in [the snapshot](#the-snapshot) (`idle_seconds`, `gate`, `gate_idle_seconds`). |

Each column has the width of its track in the design: `#` 3 cells, the rail 2, `plan` 6, `state` 8, `phase` 13, `after` 8, `verdict` 7, `branch` 15, `used` 7, `new` 5 and `cache` 6. A column with a value that is wider than its track is as wide as its widest value. `last event` and the reason have no track. There are 2 cells between two columns. The numbers, and the headers `#`, `used`, `new` and `cache`, align right in their track. `status` does not cut a line to the width of the terminal, and drops no column. On a terminal, each cell of the table has the colour of its role, as in the live view, and the verdict word is bold. The header lines have no colour. When `NO_COLOR` is set and not empty, or when standard output is not a terminal, the output has no SGR code. The text of `status` is for a person, and it can change in a later version. A program reads `status --json`: see [the snapshot](#the-snapshot).

On a terminal, `status` sets the title of the terminal to `delegate status`. See [the terminal title](#the-terminal-title).

`status` exits 0 when it printed the run, the table of the active runs, or the line of [a newest run that failed at start](#the-newest-run-that-failed-at-start). It exits 2 when the path is not a git repository, when the repository has no run, when the run id is unknown, when more than one run has the short id, when a lock file cannot be read, when the journal is not valid, or with `--json` and no run id when more than one run is active or the newest run failed at start. The message on stderr names the repository, the run id, the journal, each active run, or the run that failed at start. Ctrl-C ends `status` with the code 130 and the line `delegate: interrupted` on stderr, and with no traceback. An event stream that cannot be read is not an error: see [a stream that cannot be read](#a-stream-that-cannot-be-read).

### The snapshot

`status --json` prints one snapshot of the run as one JSON object. Two plugins read it, so the fields below are a contract. A new field can come in a later version. A field does not change its type or its meaning. One exception is in the changelog: the fields `tokens_new` and `tokens_cache` replace the field `tokens` of version 1.2.0, for the run and for each ticket.

| Field | Type | Meaning |
|---|---|---|
| `run_id` | string | The id of the run. |
| `state` | string | `running` until the journal holds `run-end`, then the result of the run: `built` or `failed`. `pausing` while a pause request waits and the run is [active](#the-run-with-no-run-id), and `paused` from the `paused` event until a `resume`. See [the pause](run.md#the-pause). A pause request of a run with no live process does not make the run `pausing`: see `note`. |
| `time` | string | The time of the snapshot (ISO 8601, UTC, whole seconds). For a run that ended, it is the time of `run-end`: the clock of the run stops there. For a paused run, it is the time of `paused`. |
| `elapsed_seconds` | integer | The time that the run used: from `run-start` to `time`. |
| `tickets_total` | integer | The number of [**tickets**](../glossary.md#ticket) of the run. |
| `tickets_ended` | integer | The number of tickets that ended: `built`, `failed`, or `skipped`. |
| `percent` | integer | The part of the run that is complete, from 0 to 100. See [the progress and the ETA](#the-progress-and-the-eta). |

| `phase` | string or `null` | In [**`economy`**](../glossary.md#economy) mode, while the verification of the [**chain**](../glossary.md#chain) runs: its phase, `gates`, [**`verifier`**](../glossary.md#verifier) or [**`fix-up`**](../glossary.md#fix-up). | `plan` | list of objects or `null` | The newest plan of the run: one object for each ticket, in plan order, with its `id` (string) and its `blocked_by` (list of strings), the ids of its [**blockers**](../glossary.md#blocker) as the `plan` field of `run-start` or of the newest `plan-change` records them. The two token counts and the time of the newest event come from the method `activity` of the adapter of the run. See [the adapter interface](run.md#the-adapter-interface), and the activity of [the `claude-code` adapter](claude-code-adapter.md#the-activity) and [the `opencode` adapter](opencode-adapter.md#the-activity).

#### The token counts

`status` shows two token counts, for the run and for each ticket, in each form: the progress line and the ticket table of `status`, the JSON, and the run line, the ticket table and the feed of the [live view](#the-live-view) of `watch`. It shows no cost.

- **New** (`tokens_new`): the input tokens, the cache writes, and the output tokens, with the thinking tokens. These are the tokens that the model reads or writes for the first time.
- **Cache** (`tokens_cache`): the cache reads. Each turn of an agent reads its whole context again from the cache, so this count grows with the number of turns times the size of the context. A long [**session**](../glossary.md#session) has many cache reads, and they do not mean that the run is expensive.

The progress line of `status` gives the two counts in a short form: `tokens 302k new, 9.7M cache`. The feed of `watch` uses the same form. The ticket tables give each count in its own column, in the same short form: `302k` and `9.7M`. A count under 1000 shows as it is, a count under one million shows in thousands (`k`), and a larger count shows in millions (`M`) with one decimal.

Each adapter splits the counts of its stream:

| Adapter | New | Cache |
|---|---|---|
| `claude-code` | `input_tokens`, `cache_creation_input_tokens`, and `output_tokens` of a `usage` object | `cache_read_input_tokens` of a `usage` object |
| `opencode` | `input`, `output`, `reasoning`, and `cache.write` of the `part.tokens` of a `step_finish` event | `cache.read` of the `part.tokens` of a `step_finish` event. A step with no `cache` field gives 0. |

The token counts of a `claude-code` stream:

- The counts of one turn or one session come from its `usage` object, as the table above gives.
- When the stream holds a `result` event, the counts of that session are the `usage` of the `result` event. The `usage` of an `assistant` event is partial, so it does not give the counts of a session that ended.
- For a session that has no `result` event yet (an agent that runs now), the counts are the sums of its turns: one turn for each `message.id`, with the newest usage of that message.
- A resumed session writes its events in the same stream, after the `result` event of the earlier session. The counts of the stream add the counts of each session. The streams are the files that `agent-start` and the result events name. The stream of an agent that runs now can be missing for a short time, before the [**harness**](../glossary.md#harness) opens it: it then has 0 new tokens and 0 cache tokens. Any other stream that is missing is [a stream that cannot be read](#a-stream-that-cannot-be-read).

#### The newest activity

An agent can work for a long time and write no event with a time. For example, Claude Code writes a `tool_progress` heartbeat every 30 seconds while a long command runs in the foreground, and `thinking_tokens` events while the model thinks. These events have no `timestamp` field. The rule: when the newest event of the stream has no time and shows work, the time of the newest activity is the modification time of the stream file. So the last activity of an agent that runs a long command is never more than about 30 seconds old, and does not look like a stall. The [stall](#the-stall) check of `watch` also uses the modification time of the stream, so the two agree.

### A run with no stream reader

The `status` process can have no reader of the streams of a run:

- The adapter of the run is not known to the process. For example, a script registered the adapter in its own process.
- The adapter has no method `activity`. For example, an adapter of an earlier version.

Each form of `status` then works, and exits 0. It shows the progress and the ETA. It shows no tokens and no activity: in the JSON, `tokens_new`, `tokens_cache` and `idle_seconds` are `null`, and the ticket table of `status` and of the [live view](#the-live-view) of `watch` has no columns `new` and `cache`. The live view has no activity in the live tail. `status` does not read the streams of such a run. The running gate and the time since its log changed do not need the reader, so they show in the JSON and in the live view.

### A stream that cannot be read

`status` only shows data. Each form of `status` works, and exits 0, when an event stream of the run cannot be read. The rule: any error from the check that the stream exists, or from the method `activity` of the adapter, makes that stream a stream that cannot be read. For example, a stream cannot be read when:

- The file is missing. The stream of an agent that runs now is the exception: before the harness opens it, it has 0 tokens.
- The process cannot search a parent directory of the file.
- The process cannot read the file, for example because the file has no read permission.
- The path is a directory.
- The file is not UTF-8 text.
- A line before the last one is not JSON.
- A line is JSON, but it is not an event that the adapter can use. For example, a line is a number or a list, a `timestamp` is not a time, a usage value of a `claude-code` stream is not a number, or a `step_finish` event of an `opencode` stream has no `part.tokens.input` number.

`status` then shows no tokens and no activity for that agent:

- In the JSON, the `tokens_new` and the `tokens_cache` of its ticket are `null`. The counts of the other agents of the ticket would not be the counts of the ticket.
- When the agent runs now, the `idle_seconds` of its ticket is `null`.
- The `tokens_new` and the `tokens_cache` of the run are the sums of the other tickets.
- The row of the ticket in the table of `status` and in the live view of `watch` shows no tokens for the ticket. While the agent runs, the live view shows no activity for it.

Only `status` treats such a stream as no data. `delegate run` reads the stream of an agent for its [**end state**](../glossary.md#end-state), and a stream that it cannot read stays an error there.

### The progress and the ETA

The percentage:

- A ticket that ended (`built`, `failed`, or `skipped`) counts 1.
- A running ticket counts by its phase: `specialist` 0, `gates` 0.6, `verifier` 0.8, `fix-up` 0.8.
- A pending ticket counts 0.
- The percentage is the sum, divided by the number of units, times 100, rounded down. A unit is a ticket. In `economy` mode, the verification of the chain is one more unit. See [the verification of an `economy` chain](#the-verification-of-an-economy-chain).

The ETA:

- Before the first ticket ends, the ETA is `null`.
- After that, the ETA is `time` + M × N − R. M is the mean duration of the ended tickets. N is the number of units that did not end. R is the `elapsed_seconds` of the running ticket, and the time that the verification of an `economy` chain used.
- The mean uses the tickets that ended after a step (`built` or `failed`). A skipped ticket has no step and no duration, so it does not count in the mean. It counts as ended.
- The ETA is never earlier than `time`. For a run that ended, it is the time of `run-end`.

### The verification of an `economy` chain

In [**`economy`**](../glossary.md#economy) mode the verification of the [**chain**](../glossary.md#chain) runs after the last ticket ends: the gates on the chain tip, the verifier, and the fix-up rounds. For the percentage and the ETA, the verification, with its gates, is one more unit of the run, as a ticket is:

- The verification counts 0 until the journal holds `run-end`. After `run-end` it counts 1. Thus the percentage stays below 100 until the run ends.
- The verification starts at the first `gate-start` or `gate-skip` of the phase `chain`, or at the first `verify-start` when the journal holds no such gate event. While it runs, `phase` of the snapshot follows the newest `gate-start` or `gate-skip` of the phase `chain` (`gates`), `verify-start` (`verifier`), or `fixup-start` (`fix-up`). After a fix-up round the gates of the chain run again, so the phase is `gates` again.
- The ETA estimates the verification as one mean ticket: M. R holds the time from the start of the verification to `time`.
- The tickets of the chain stay `built`, with the `phase` `null`. The last ticket of each stack shows the tokens and the `idle_seconds` of the verifier of its stack.

For example, two tickets of 600 and 300 seconds ended, and the gates of the chain started 99 seconds ago. The percentage is 2 ÷ 3 × 100, rounded down: 66. The ETA is `time` + 450 × 1 − 99.

## `delegate watch`

```
delegate watch [run-id] [--repo <dir>] [--until verdict] [--stall-minutes N] [--max-minutes N] [--from <position>] [--poll-seconds N] [--raw]
```

`watch` follows the run: it reads the journal at each poll, shows each new event, and exits when it has a reason. The form of the output depends on standard output:

- When standard output is a terminal, `watch` shows [the live view](#the-live-view): the run line and a table of the tickets at the top, and below them a short line for each event of the ticket that runs now.
- When standard output is not a terminal, or with `--raw`, `watch` prints [the raw lines](#the-raw-lines): one line for each event. A [**coordinator**](../glossary.md#coordinator) can run `watch` as a background task, read the lines, and act on the exit code.

The exit codes, the options, and the last line `position <seq>` are the same in the two forms. The position is the `seq` of the last event that `watch` reported.

With no run id, `watch` follows the one active run of the repository, also with `--from`. When no run is active, it prints one line for the newest run, and no event. With `--from`, it replays the journal of the newest run from the position. When more than one run is active, it shows [the run picker](#the-run-picker) on a terminal. Otherwise it prints one line on stderr that names each active run, follows none, and exits 2. See [the run with no run id](#the-run-with-no-run-id).

On a terminal, `watch` also shows the progress of the run in the title of the terminal, in the two forms. See [the terminal title](#the-terminal-title).

### The run with no run id

`status` and `watch` with no run id choose the run from the active runs of the repository. `watch` uses this rule also when it gets `--from`, so `watch --from <position>` with no run id follows the same run as `watch` with no run id. When no run is active, `watch` with `--from` replays the journal of the newest run from the position, and does not print the one line of the newest run.

A run is active when these two conditions are true:

- Its journal has no `run-end` after its newest `resume`. This is the rule of the state of `status`: a run that ended and was resumed works again.
- The lock of its [**run branch**](../glossary.md#run-branch) names the run and a process that exists. This is the lock check of `delegate run` and `delegate pause`. See [the run lock](run.md#the-run-lock).

A run with no `run-end` and no live process is not active: its process stopped. A crash, a kill, Ctrl-C and a pause stop the process of a run.

A run directory with a `run.log` and no journal is the directory of a [detached run](run.md#the-detached-run) whose journal does not exist. When a lock names its run id and a process that exists, the run process works, and it has not written its journal yet. When its log is empty, the run process has not written to it yet. Otherwise the run failed at start. A run that failed at start has no `run-start` event, so the time of the last change of its log is its start time when the commands find the newest run.

| Active runs | `status` | `watch` |
|---|---|---|
| One | Shows the active run, also when a newer run ended. | Follows the active run, also when a newer run ended. |
| None | Shows the newest run. When the newest run failed at start, prints its line, and exits 0. With `--json`, it exits 2, and the message is the line. | Prints one line for the newest run, and exits. With `--from`, replays the journal of the newest run from the position, when that run has a journal. See [the newest run that ended](#the-newest-run-that-ended), [the newest run that stopped](#the-newest-run-that-stopped) and [the newest run that failed at start](#the-newest-run-that-failed-at-start). |
| More than one | Prints the table of the active runs, with no prompt, and exits 0. With `--json`, it exits 2, and the message names each active run. | On a terminal, shows [the run picker](#the-run-picker), and follows the run that you choose. Otherwise, prints one line on stderr that names each active run, follows none, and exits 2. |

### The run picker

When `watch` gets no run id, more than one run is active, and standard input and standard output are terminals, `watch` shows the run picker. It shows the run picker also with `--from`, and goes on from the position in the run that you choose. It prints the number of the active runs, a table with one row for each active run, the newest run first, and the prompt `watch which? [1]`. The example below is for a locale that is not UTF-8, with the ASCII glyphs. With a UTF-8 locale, the same cells hold `·` (the separator) and `▶` (a running ticket):

```
2 runs are active in this repository
#  run                    run branch    mode     since  progress          now
1  20261019T051148Z-ff1a  run/fix-auth  economy  18:11  0/1 ended . 30%   > 12 gates . active 12s
2  20261019T040911Z-d636  run/plan      assure   17:09  6/13 ended . 46%  > 7 specialist . active 1m05s
watch which? [1]
```

Type the number of a run, and push Enter. Enter alone takes 1, the newest run. `watch` then follows that run, as it follows a run that you name. An answer that is not the number of a row gets one line on stderr, and the prompt again. At the end of the input (Ctrl-D), `watch` follows no run, and exits 2. Ctrl-C at the prompt prints `delegate: interrupted` on stderr, and `watch` exits 130. See [Ctrl-C](#ctrl-c).

`status` with no run id prints the same lines, with no prompt, and exits 0. It does not ask, so a script can read it. The columns of the table:

| Column | Meaning |
|---|---|
| `#` | The number to type at the prompt. |
| `run` | The run id. On a terminal, its short id is bold. |
| `run branch` | The [**run branch**](../glossary.md#run-branch) of the run. |
| `mode` | The [**mode**](../glossary.md#mode) of the run. |
| `since` | The local time of the `run-start` event. A run that did not start today also has the day of the week, as `Mon 17:09`. |
| `progress` | The tickets that ended, of all the tickets, and the percentage of [the snapshot](#the-snapshot). |
| `now` | Each running ticket and its phase, separated by `, `. While the verification of an `economy` chain runs, `chain <phase>`. When no ticket runs, `no ticket running`. Before them, the state of a run that is not `running`, as `pausing`. Then `active <time>`: the time since the newest change of the journal, of the event streams and of the gate logs that the journal names. The [stall](#the-stall) check of `watch` uses the same files. |

When standard input or standard output is not a terminal, nobody can answer the prompt, for example a coordinator that runs `watch` as a background task. `watch` then follows no run. It prints one line on stderr that gives each active run, the newest run first, with its run branch and its state, and it exits 2:

```
delegate watch: 2 runs are active in this repository; give a run id: 20261019T051148Z-ff1a (run/fix-auth, running), 20261019T040911Z-d636 (run/plan, running)
```

`watch` replays no event, and prints no line `position <seq>`. Give the run id, or its short id, to follow one of the runs.

### The newest run that ended

When `watch` gets no run id and no `--from`, no run is active, and the newest event of the journal of the newest run is `run-end`, `watch` shows no event of that run. It prints one line, and no line `position <seq>`:

```
no run is active; the newest run 20261016T030000Z-abcd ended failed at 2026-10-16 17:06; first problem: ticket a: the step failed: no commit
```

The line gives the run id, the result, and the local date and time of the newest `run-end` event. When the run failed and its journal holds a [problem](#the-problem-events), the line also gives the ticket and the reason of the first problem. Then `watch` exits with the code of the result: 0 for `built`, and 1 for `failed`. See [the exit codes](#exit-codes). The line has the same words on a terminal and with `--raw`, and `watch` draws no live view. On a terminal, the result is bold and has the colour of its role: `built` is green and `failed` is red. The time is faint, and the first problem is red. A paused run has `paused` in yellow. An error line of `watch` on stderr is red when stderr is a terminal. When `NO_COLOR` is set and not empty, when the stream is not a terminal, or with `--raw`, the lines have no colour code. With `--raw`, the lines are the same as before the colours.

A retry continues a run that ended: the journal gets `retry`, then a new `step-end` and a new `run-end`, and the newest of each wins, as for `delegate status`. While a retry goes on, an event follows the newest `run-end`, so the run is active, and `watch` follows it. When `watch` follows or replays a journal, a `run-end` that another event follows does not end the watch. An event of a ticket that a later `retry` of the same ticket follows is no problem: the retry continues the step of that ticket. The first problem of the line is the first problem that is not before a `retry` of its ticket.

To see the events of a run that ended, give its run id or `--from`. `watch` then replays the journal, as it does for a run that goes on. When the repository has no run, `watch` exits 2.

### The newest run that stopped

When `watch` gets no run id and no `--from`, no run is active, and the newest event of the journal of the newest run is not `run-end`, the process of that run stopped. `watch` shows no event of that run, and it prints no line `position <seq>`. It prints one line that tells how to go on with the run:

- When the run is paused, the line goes to stdout, and `watch` exits 7. A run is paused when its newest `paused` event comes after its newest `resume`, as for `status`.
- When the run stopped in a different way, for example after a crash or a kill, the line goes to stderr, and `watch` exits 2: there is no run to follow.

```
no run is active; the newest run 20261016T030000Z-abcd paused at 2026-10-16 17:06; go on with delegate run --resume 20261016T030000Z-abcd
delegate watch: no run is active; the newest run 20261016T030000Z-abcd stopped at 2026-10-16 17:06 with no run-end, and no process works on it; go on with delegate run --resume 20261016T030000Z-abcd
```

The line gives the run id, the local date and time of the newest event of the journal, and the command that resumes the run. See [the resume](run.md#the-resume).

### The newest run that failed at start

When `status` or `watch` gets no run id, no run is active, and the newest run [failed at start](#the-run-with-no-run-id), the run has no journal. The command prints one line on stdout, and no line `position <seq>`:

```
no run is active; the newest run 20261019T070133Z-b937 failed at start: delegate run: git branch run/watch-chain e0dbee4 failed: fatal: a branch named 'run/watch-chain' already exists; log /path/to/.git/delegate/runs/20261019T070133Z-b937/run.log
```

The line gives the run id, the last line of the log that holds text, and the path of the log. In the example, another process made the run branch after the checks of the run. `watch` exits 1: the run failed. `status` exits 0. With `--json`, `status` exits 2, and the message on stderr is the line: the run has no snapshot. Since `delegate run --detach` makes [the checks that need no agent](run.md#the-detached-run) before it starts the run process, a run fails at start only after those checks.

### The live view

On a terminal, `watch` draws a frame at each poll, in place of the frame before it. The frame has the run line, a blank line, the ticket table, a divider, and the feed of the ticket that runs now. The example below is the frame for a locale that is not UTF-8, with the ASCII glyphs. With a UTF-8 locale, the same cells hold the glyphs `█ ░` (the bar), `● ▶ · ✗ –` (the nodes), `│` (the rail), `✓ ● ○` (the phases) and `─` (the divider):

```
run abcd  running  #############... 82%  5/7 ended  58m20s used  ETA 11m40s  213k new . 0 cache

  #      plan    state       phase          after        used    new   cache
  1      * 66    + built                               10m00s    39k       0
  2  |   * 72    + built                               10m00s    39k       0
  3  |   * 67    + built                               10m00s    39k       0
  4      * 68    + built                               10m00s    39k       0
  5      * 69    + built                               10m00s    39k       0
  6  |   > 70    running     specialist +               8m20s    19k       0  active 2m20s
     |                       gates +
     |                       verifier *
     |                       fix-up o
  7  |   . 71    pending
------------------------------------------------------------------------------------------------------------------------
16:50  #70  started · python-specialist
16:55  #70  specialist finished · 5m · tokens 19k new, 0 cache · report ok
16:56  #70  gates green (pytest 1m)
16:56  #70  verifier started
16:58  #70  verifier running · 2m · 0 new · 0 cache · active 2m20s
```

The run line and the table come from the snapshot of `status` (see [the snapshot](#the-snapshot)), drawn again at each poll:

- The run line gives the [**short run id**](../glossary.md#short-run-id), the state, a bar of 16 cells, the percentage, the tickets that ended, the time used, the ETA, and the two [token counts](#the-token-counts). The ETA is the time from now, or `-` before the first ticket ends. A run that ended or paused shows no ETA. While the verification of an `economy` chain runs, its phase comes after the state: `running · verifier`.
- The table has one row for each ticket, flat and in plan order. The columns are `#` (the position in the plan), the rail (no header), `plan`, `state`, `phase`, `after`, `used`, `new`, `cache`, and a live tail with no header. The node glyph in `plan` gives the state: `●` built, `▶` running, `·` pending, `✗` failed, and `–` skipped.
- The rail and `after` show the [**blockers**](../glossary.md#blocker) of the plan, from `blocked_by` in the plan of `run-start` or of the newest `plan-change`. When the one blocker of a ticket is the row directly above it, the rail `│` joins the two rows, and `after` is empty. Otherwise `after` gives the id of each blocker: a ticket after a row that is not the row above has no rail, and `after` names that row, as `66`. A join names each blocker, as `126 132`. The depth of the plan never makes the table wider: a chain of 40 tickets has the columns of a chain of 3. A journal of an earlier version of the engine records no plan, and then no row has a rail or an `after` cell.
- The row of a running ticket gives its first phase, and each further phase is a sub-row under it, with only the rail, the phase and a detail in the live tail. The rail runs through the sub-rows when the next row has it. A phase shows `✓` when it is done, `●` when it runs, and `○` when it is to come. While a gate runs, the phase gives its count, as `gates ● 2/3`: the gate that runs, and the gates of the stack. The count shows when the journal holds an earlier run of the gates of the same stack that ended. A fix-up round shows its round and the limit, as `fix-up ● 1/2`. In `economy` mode a ticket has the phases `specialist` and `gates` only. Only phases go in the `phase` column.
- The live tail of the row of a running ticket gives `active <time>` since the last activity of its agent. While a gate runs, the sub-row of its phase gives `gate <name> · log <time> ago` in its live tail. After an agent or a gate log has no change for the stall time, the tail gives `⚠ idle <time>`. The stall time is `--stall-minutes`, or 5 minutes. After a [**continuation**](../glossary.md#continuation), the tail starts with `cont <count>/<limit>`.
- The live tail of a ticket that failed or was skipped gives the reason, with no path. While the run is `pausing`, the live tail of the next row gives `pauses before this step`: the first pending ticket after the running ticket, or the first pending ticket when no ticket runs. In a paused run, the live tail of the ticket that the pause stopped before gives `paused before this step`, `paused before the gate` or `paused before the verifier`.
- For [a run with no stream reader](#a-run-with-no-stream-reader), the table has no columns `new` and `cache`, and the live tail gives no activity.

Each column has the width of its track in the design: `#` 3 cells, the rail 2, `plan` 6, `state` 10, `phase` 13, `after` 8, `used` 7, `new` 5 and `cache` 6, so the live tail starts at the same cell for each plan. A column with a value that is wider than its track is as wide as its widest value. The live tail has no track. There are 2 cells between two columns. The numbers, and the headers `#`, `used`, `new` and `cache`, align right in their track. The bar drops first: on a terminal of fewer than 100 columns, the run line has no bar. When a line of the table, with the live tail of a running ticket, is wider than the terminal, the columns drop in this order: `new` and `cache`, then `used`. The labels of the phases stay, because the phases stack. A reason in the live tail does not make a column drop: the cut at the width of the terminal ends it.

The feed holds only the lines of the ticket that runs now. The `step-start` of a ticket, or a `retry`, starts the feed again. So the lines of a ticket that ended, and a problem of it, stay until the next ticket starts. Before the first step, the feed holds the line of the start of the run. In `economy` mode, the verification of the chain is one group, and its lines name the stack: `stack python verifier started (#a, #b)`. A line starts with the local time of the event (`HH:MM`), then the ticket (`#<id>`), and then what happened. The ticket, or the stack, has a track as wide as the widest of the feed, and at least 3 cells, with 2 cells before and after it. A line with no ticket, as a problem, starts what happened on the track of the ticket. A line shows no path and no `None`: it shows only the name of a file. The feed joins the events that belong together into one line:

| Line | The events |
|---|---|
| `#a specialist finished · 36m · tokens 19k new, 980k cache · report ok` | The result of an agent (`adapter-result`, `fixup-result` or `verify-result`) and the event of its [**report**](../glossary.md#report). It gives the role, the end state, the time from its `agent-start`, and the two token counts of its stream. |
| `#a gates green (pytest 16m, zensical 1s)` | The `gate-result` and `gate-skip` events of one round of gates. Each gate has the short name of its command and its time. The name is the first word of the command that is not a launcher (such as `nix develop -c` or `python3 -m`), with no version. A red gate has the word `red`. |
| `#a ✓ ACCEPT · built` | A verdict, or the gates, with the `step-end` that follows them. A [**REJECT**](../glossary.md#reject) gives the number of findings. |
| `stack python ✓ ACCEPT · run built · 16m · tokens 39k new, 1.1M cache` | The verdict of the chain of a stack in `economy` mode, with the `run-end` that follows it. |
| `run built · 1h06m · tokens 50k new, 1.3M cache` | The `run-end`: the result, the time of the run, and its two token counts. |
| `paused · before ticket d · go on with delegate run --resume ab12` | The `paused` event: where the run stopped, and the command that goes on with it, with the short run id. |

The events `agent-start`, `gate-start`, `idle-timeout`, `run-branch-advance`, `lock-broken` and `pause-requested` have no line of their own. Each other event has a short line. While an agent runs, the last line of a frame tells it, as `16:58  #70  verifier running · 2m · 43k new · 1.1M cache · active 2m20s`. The line gives the role, the time from its `agent-start`, the two token counts of its stream in faint text, and the time since its last activity. A stream that the harness has not opened yet has 0 tokens. For [a run with no stream reader](#a-run-with-no-stream-reader), and for a stream that cannot be read, the line has no token counts. The last frame has no such line.

A [problem](#the-problem-events) and a [stall](#the-stall) are lines that start with `✗`. For example, `16:36  ✗ #a the specialist returned no valid result: report missing: a.specialist.json`, or `17:40  ✗ stall · no change for 30m`. The line of the time limit is `<time>  time limit · <N>m used · the run goes on`.

Each part of the frame has the colour of its role, from the 16 ANSI colours of the theme of the terminal: green for a result that is good (`✓`, `●` built, `gates green`, the done phases, the bar), cyan for the ticket that runs now, yellow for `REJECT`, a fix-up, a continuation, a pause and `⚠ idle`, red for a failure, a problem and `gates red`, and blue for the rail and the ids in `after`. Faint text (SGR 2) is for the facts to read second: the times, the tokens, the header, the divider, and the rows that ended or are pending. Bold marks the short run id, the ticket that runs now, the verdict word, and the result of the run. The view sets no background colour. Each state also has a glyph or a word, so the view reads the same with no colour. When `NO_COLOR` is set and not empty, the frame has no SGR code. When the locale is not UTF-8 (`LC_ALL`, `LC_CTYPE`, `LANG`), the run line, the table, the divider and the glyph of a problem line use the ASCII glyphs `+ x > . * o - # . | - !`, in the same columns. The ids in `after` stay as they are. The lines of the feed and the title keep the separator `·`.

The view cuts each line to the width of the terminal. A frame fits the height of the terminal, with the last line free for the cursor. The table gets the rows that are left after the run line, the blank line, the header, the divider and 4 lines of the feed. When the plan has more rows than that, rows fold:

1. The rows show from the top, in plan order, and the rows of the tail fold into one last row, directly above the divider. The row gives the count and the state of the folded tickets, as `· 13 pending`, the range of their ids in `after`, as `126–144`, and the range of their rows, as `rows 28–40 folded`.
2. When the tail fold does not keep 3 rows after the running ticket (or each row after it), the rows in the middle also fold into one row. The first 3 rows and the 3 rows before the running ticket stay. The fold row gives `✓ <count> built`, the range of the ids in `after`, the sums of `used`, `new` and `cache`, and the range of the rows in the live tail, as `rows 4–20 folded`. A fold of one row saves no row, so a fold holds 2 rows or more. The rail runs through it when the row under it has the rail. Then the rows after the running ticket show, the nearest first, as many as fit, and the rest fold into the tail.

The rows of the running ticket and its sub-rows never fold. When no ticket runs, the ticket that the pause stopped before, or else the first pending ticket, takes its place. When a fold holds tickets in more than one state, it gives the count of each state, as `✓ 15 built, 1 failed, 1 skipped`. With the ASCII glyphs, a range is `104-120`. The example below is a plan of 40 tickets on a terminal of 120 columns and 24 rows, with the ASCII glyphs:

Then the feed gets the rows that the table does not use, and keeps its newest lines. When the terminal does not give its size, no row folds, and the frame keeps each line of the feed. The last frame keeps the whole feed, and the terminal scrolls it. Then `watch` prints the line `position <seq>`.

### The raw lines

When standard output is not a terminal, or with `--raw`, `watch` prints one line for each event. A line has the position (`seq`), the time, the event name, and then each field of the event that is not a list or an object, as `name=value`. The field `output_tail` is not printed. When a problem, a verdict, a stall or the time limit ends the watch, `watch` prints the reason on a line that starts with `watch:`. At `run-end` and at `paused`, the line of that event is the last event line. Then `watch` prints the line `position <seq>`. An error and Ctrl-C give no line `position <seq>`.

### Exit codes

<!-- generated:begin watch-exit-codes -->
<!-- Generated by `delegate docs`. Do not edit this section by hand. -->

| Code | Reason | When |
|---|---|---|
| 0 | run succeeded | The journal holds `run-end` with the result `built`. |
| 1 | run failed | The journal holds `run-end` with the result `failed`, or, with no run id, [the newest run failed at start](#the-newest-run-that-failed-at-start) when no run is active. |
| 2 | error | A usage error, a repository with no run, an unknown run id, a journal that is not valid, a `--from` position beyond the end of the journal, or, with no run id, [a newest run that stopped](#the-newest-run-that-stopped) when no run is active, or [more than one active run](#the-run-picker) when standard input or standard output is not a terminal, or no answer at the prompt. |
| 3 | problem | An event is a problem. See [the problem events](#the-problem-events). |
| 4 | verdict | `--until verdict` is set and the journal holds a `verdict` event. |
| 5 | stall | `--stall-minutes` is set and nothing changed for that time. |
| 6 | time limit | `--max-minutes` is set and the time is used. |
| 7 | run paused | The journal holds `paused`: a pause request stopped the run at a step boundary. |
| 130 | interrupted | Ctrl-C stopped the watch. The run goes on. See [Ctrl-C](#ctrl-c). |

<!-- generated:end watch-exit-codes -->

Code 2 is also the code that `argparse` gives for a usage error.

`watch` checks the events in order. The first event that gives a reason ends the watch, so a run that failed exits 3 at its first problem, and not 1. The code 1 follows when `watch` goes on from the position of that problem. This rule is for a run that `watch` follows or replays. With no run id, [the newest run that ended](#the-newest-run-that-ended) exits with the code of its result, [the newest run that stopped](#the-newest-run-that-stopped) exits 7 or 2, and [the newest run that failed at start](#the-newest-run-that-failed-at-start) exits 1.

A run that ended and was resumed has a `resume` event after its old `run-end`. The events before the first `resume` after its newest `run-end` that a `resume` follows are the history of the run: `watch` prints them, but a problem, a `verdict` for `--until verdict`, or a `run-end` there does not end the watch. A run that stopped with no `run-end` and was resumed has no such history, so a problem before its `resume` still ends the watch. `watch` then follows the resumed run to its new `run-end`.

A `paused` event ends the watch with the code 7: a pause request stopped the run process at a step boundary. See [the pause](run.md#the-pause). A `paused` that another event follows, for example the `resume` of the run, is history, and it does not end the watch.

### The problem events

A problem is one of these events. The raw line `watch: problem: ticket <id>: <reason>` names the ticket and the reason.

| Problem | The event | Reason in the line |
|---|---|---|
| A step ends blocked or partial | `report-validation` or `fixup-report` with a `status` other than `committed` | `the step ended <status>: <blocked_reason>` (`report-validation`), or `the fix-up specialist ended <status>: <blocked_reason>` (`fixup-report`). With no `blocked_reason`, the reason stops after `<status>`. |
| A step ends with [**gates**](../glossary.md#gate) that are not green | `step-end` with the state `failed`, when the newest result of a gate command of the ticket is red | `the gates are not green: <commands>` |
| An agent fails | `adapter-result`, `fixup-result` or `verify-result` with the [**end state**](../glossary.md#end-state) `failed`, or (for a [**fix-up**](../glossary.md#fix-up) [**specialist**](../glossary.md#specialist) and a [**verifier**](../glossary.md#verifier)) the end state `capped` | `the <role> ended <end state> with exit status <n>` |
| A permission mode refused a tool | `adapter-result`, `fixup-result` or `verify-result` with a `refused` field | `the <role> was refused <tools> in <mode> mode; give the agents a settings file with DELEGATE_AGENT_SETTINGS` |
| An agent returns no result | `report-validation`, `fixup-report` or `verify-report` with `valid` false | `the <role> returned no valid result: <reason>` |
| A second [**continuation**](../glossary.md#continuation) of a step | `continuation` with a `count` of 2 or more | `the step continued <n> times (limit <n>, trigger <trigger>)` |
| A step fails for any other reason | `step-end` with the state `failed`, and no red gate | `the step failed: <reason>` |

A specialist that ends `capped` continues, so it is not a problem. The first continuation of a step is also not a problem. A gate that is red and turns green after a continuation is not a problem.

An agent that ends `finished` with an exit status other than 0 is not a problem at its result event. With a valid report, the step continues. Without a valid report, the next report event or the `step-end` gives the problem. An agent that `delegate run` ended at the idle timeout is also not a problem. The journal records `idle-timeout` before its result event, and `watch` does not check that result event. See [the end of an agent session](run.md#the-end-of-an-agent-session).

### The verdict

With `--until verdict`, `watch` exits at the first `verdict` event that is not history: a verdict before the resume of a run that ended, or a verdict of a ticket that a later `retry` of that ticket follows, does not end the watch. The raw line is `watch: verdict: ticket <id> round <n>: <verdict>: <findings>`. For the verdict of a chain in `economy` mode, the raw line is `watch: verdict: stack <name> (tickets <ids>) round <n>: <verdict>: <findings>`. The [**findings**](../glossary.md#finding) are separated by `; `. Without the option, `watch` goes past each verdict.

### The stall

`--stall-minutes N` compares the time now with the newest modification time of the journal, of the event-stream files that the events name (`event_stream`), and of the gate log files that the events name (`gate_log`). If the difference is N minutes or more, `watch` exits. The raw line is `watch: stall: the journal, the event streams and the gate logs have not changed for N minutes; last event: <the line of the last event>`. A run that has ended is not a stall.

The journal names the [**event stream**](../glossary.md#event-stream) of an agent in `agent-start`, before the agent starts. While an agent runs, its own stream therefore shows a change too. A tool heartbeat of Claude Code is such a change, so an agent that runs a long command in the foreground is not a stall. For a stream that ends with such events, `status` uses the same modification time as [the newest activity](#the-newest-activity). The journal names the log file of a gate in `gate-start`, before the gate runs, and the gate runner appends the output of the gate to it. A long gate that writes output is therefore not a stall. A gate that writes no output for N minutes is a stall. A journal of an earlier version names a stream only when the agent has ended: for such a run, set N to more than the longest time of one agent run.

### The position

`--max-minutes N` ends the watch before a [**harness**](../glossary.md#harness) kills the background task. The raw line is `watch: time limit: N minutes are used; the run is not at its end`. Each exit after `watch` follows a run prints `position <seq>`. Ctrl-C prints the position in its own line, and an error prints no position. See [Ctrl-C](#ctrl-c). `watch --from <seq>` goes on after that event:

- It prints no event with a position of `<seq>` or less, so no event is reported twice.
- It reads the earlier events for the problem rules. A step-end after the position still finds the red gate before the position.
- If the journal ended or paused at or before the position, it exits with the result of the run, or with 7 for a pause.
- If the journal holds fewer events than `<seq>`, it exits 2.

### Ctrl-C

Ctrl-C stops the watch. It does not stop the run. `watch` then does these steps:

1. On a terminal, it draws the last frame of the live view, shows the cursor, and sets the title to `delegate watch · <short run id> · interrupted`. Thus the terminal is clean also when Ctrl-C comes while `watch` draws a frame. See [the terminal title](#the-terminal-title).
2. It prints one line on stderr, and no line `position <seq>`. See the line below.
3. It exits with the code 130, as a shell gives for SIGINT. It shows no traceback.

```
watch: stopped at position <seq>; the run goes on. Resume with delegate watch <run id> --from <seq>
```

The position is the `seq` of the last event that `watch` reported. `watch <run id> --from <seq>` goes on after that event. See [the position](#the-position). When Ctrl-C comes before `watch` finds the run, for example at the prompt of [the run picker](#the-run-picker), `watch` prints `delegate: interrupted` on stderr and exits 130.

## The terminal title

When standard output is a terminal, each `delegate` command sets the title of the terminal with the OSC 2 sequence: `ESC ] 2 ; <title> BEL`. The tab of the terminal then shows the command, and not the name of the Python process.

- `status` sets the title `delegate status`.
- `watch` sets the title `delegate watch · <short run id> · <percent>% · ETA <HH:MM>` at each poll. It writes the title again only when the title changes. The percentage is the percentage of [the snapshot](#the-snapshot). The ETA is the local time of the estimated end of the run, or `-` before the first ticket ends. See [the progress and the ETA](#the-progress-and-the-eta).
- When `watch` exits, the title is `delegate watch · <short run id> · <result>`. At the end of the run, the result is `built` or `failed`. At a pause, it is `paused`. When the watch ends before the run, the result is the reason: `problem`, `verdict`, `stall`, `time limit` or `interrupted`.
- `delegate run` sets the title `delegate run · <short run id>`. See [the output of `delegate run`](run.md#output-and-exit-codes).
- Each other subcommand of `delegate` sets the title `delegate <subcommand>`, for example `delegate render`.

The short run id is the part of the run id after the last `-`: `abcd` for the run id `20261016T030000Z-abcd`. A run id with no `-` is its own short form. A title holds no control character.

A terminal does not show the title sequence as text, so the frames of the live view and the raw lines do not change. `watch` sets the title also with `--raw`. `watch` sets no title when it cannot find the run.

When standard output is not a terminal, `delegate` writes no title sequence. To turn the title off on a terminal, set the environment variable `DELEGATE_NO_TITLE` to `1`. `delegate` does not set the title back when it exits. The shell or the terminal can set it again.
