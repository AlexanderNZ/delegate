# Reference: `delegate status` and `delegate watch`

`delegate status` and `delegate watch` show the state of a [**run**](../glossary.md#run). They read only the [**journal**](../glossary.md#journal) of the run, and the event-stream files and the [**gate**](../glossary.md#gate) log files that the journal names. They need no [**workflow**](../glossary.md#workflow) file, and no tool beyond git, which finds the [**state directory**](../glossary.md#state-directory). They do not need `jq`. `status` reads the [**event streams**](../glossary.md#event-stream) through the [**adapter**](../glossary.md#adapter) of the run, for the tokens and the activity of each agent. It does not need the adapter: see [a run with no stream reader](#a-run-with-no-stream-reader). `watch` needs no adapter.

Both commands find the journal in the state directory of the repository, in `runs/<run-id>/journal.jsonl`. See [the journal](run.md#the-journal).

## `delegate status`

```
delegate status [run-id] [--repo <dir>] [--json]
```

`status` prints the state of the run once, and exits. To follow a run while it goes on, use [`delegate watch`](#delegate-watch).

With no run id, `status` shows the one active run, or the newest run when no run is active. When more than one run is active, it prints one line for each active run. See [the run with no run id](#the-run-with-no-run-id).

The first line gives the run id, the result, the [**mode**](../glossary.md#mode), and the adapter. The result is `running` until the journal holds `run-end`, and then `built` or `failed`. A run that ended and was [**resumed**](../glossary.md#resume) is `running` again: a `run-end` that a `resume` follows does not end the run. After `delegate pause`, the result is `pausing` while the request waits in the directory of the run and the run is [active](#the-run-with-no-run-id), and `paused` from the `paused` event until a `resume`. See [the pause](run.md#the-pause). A run can stop before the [**engine**](../glossary.md#engine) reads the request: for example, after Ctrl-C, a kill or a crash. The request then stays until the next resume, and the run has no live process. Such a run is not `pausing`: the result is the state of its journal, for example `running`. A second line then gives the note `note: a pause request waits; delegate run --resume removes it`. The next line gives the progress of the run, and the line after it gives the path of the journal. Then each [**ticket**](../glossary.md#ticket) of the run has one line, in plan order:

```
run 20261016T030000Z-abcd: running (mode assure, adapter claude-code)
progress: 50%, 1 of 2 ended, 10m50s used, ETA 9m10s, tokens 302k new, 9.7M cache
journal /path/to/repo/.git/delegate/runs/20261016T030000Z-abcd/journal.jsonl
ticket a: state built, verdict ACCEPT, branch run/demo-a, last event 2026-10-16T03:10:00+00:00
  progress: 10m00s used, tokens 290k new, 9.5M cache
ticket b: state running, verdict -, branch run/demo-b, last event 2026-10-16T03:10:00+00:00
  progress: specialist, 50s used, tokens 12k new, 205k cache, last activity 12s ago
```

The line of a ticket has this form:

```
ticket <id>: state <state>, verdict <verdict>, branch <branch>, last event <time>
```

| Part | Meaning |
|---|---|
| `state` | `pending` (no event yet), `running` (`step-start`, and no `step-end`; or a `retry` after the `step-end`), `built`, `failed`, or `skipped`. |
| [**`verdict`**](../glossary.md#verdict) | The verdict of the newest `verdict` event of the ticket, or `-` when there is none. A verdict of a [**chain**](../glossary.md#chain) in [**`economy`**](../glossary.md#economy) mode covers each ticket in its `tickets` field. |
| `branch` | The branch of the ticket, from `step-start`, or `-` when the ticket has no [**step**](../glossary.md#step). |
| `last event` | The time of the newest event of the ticket, or `-` when there is none. |

The progress comes from [the snapshot](#the-snapshot), and follows [the rules of the progress and the ETA](#the-progress-and-the-eta):

- The progress line of the run gives the percentage, the tickets that ended, the time used, the ETA, and the tokens as `tokens <new> new, <cache> cache`. See [the token counts](#the-token-counts). The ETA is the time from now, or `-` before the first ticket ends. A run that ended or paused shows no ETA. In [**`economy`**](../glossary.md#economy) mode, while the verification of the [**chain**](../glossary.md#chain) runs, the line starts with its phase. For example: `progress: verifier, 66%, 2 of 2 ended, 16m40s used, ETA 5m51s, tokens 39k new, 1.2M cache`.
- A ticket with a [**step**](../glossary.md#step) has a line `  progress: ...` under its line. It gives the phase of a running ticket, the time used, and the tokens. While an agent of the ticket runs, it also gives the time since the last activity of the agent. While a gate of the ticket runs, it also gives `gate <command>` and `gate log changed <time> ago`: the gate command, and the time since the log file of the gate last changed. For example: `  progress: gates, 3m50s used, tokens 19k new, 610k cache, gate python3 -m pytest -q, gate log changed 30s ago`.
- A pending ticket and a skipped ticket have no progress line.

A ticket that failed or was skipped has the line `  reason: <reason>`, after its progress line.

On a terminal, `status` sets the title of the terminal to `delegate status`. See [the terminal title](#the-terminal-title).

`status` exits 0 when it printed the run, or the lines of the active runs. It exits 2 when the repository has no run, when the run id is unknown, when the journal is not valid, or with `--json` and no run id when more than one run is active. The message on stderr names the repository, the run id, the journal, or each active run. Ctrl-C ends `status` with the code 130 and the line `delegate: interrupted` on stderr, and with no traceback. An event stream that cannot be read is not an error: see [a stream that cannot be read](#a-stream-that-cannot-be-read).

### The snapshot

`status --json` prints one snapshot of the run as one JSON object. Two plugins read it, so the fields below are a contract. A new field can come in a later version. A field does not change its type or its meaning. One exception is in the changelog: the fields `tokens_new` and `tokens_cache` replace the field `tokens` of version 1.2.0, for the run and for each ticket.

|---|---|---|
| `run_id` | string | The id of the run. |
| `state` | string | `running` until the journal holds `run-end`, then the result of the run: `built` or `failed`. `pausing` while a pause request waits and the run is [active](#the-run-with-no-run-id), and `paused` from the `paused` event until a `resume`. See [the pause](run.md#the-pause). A pause request of a run with no live process does not make the run `pausing`: see `note`. |
| `time` | string | The time of the snapshot (ISO 8601, UTC, whole seconds). For a run that ended, it is the time of `run-end`: the clock of the run stops there. For a paused run, it is the time of `paused`. |

| `tickets_total` | integer | The number of [**tickets**](../glossary.md#ticket) of the run. |
| `tickets_ended` | integer | The number of tickets that ended: `built`, `failed`, or `skipped`. |
| `percent` | integer | The part of the run that is complete, from 0 to 100. See [the progress and the ETA](#the-progress-and-the-eta). |
| `eta` | string or `null` | The estimated time of the end of the run (ISO 8601, UTC), or `null` before the first ticket ends and while the run is paused. See [the progress and the ETA](#the-progress-and-the-eta). |

| `tokens_cache` | integer or `null` | The cache tokens of the run: the sum of `tokens_cache` of all tickets. A ticket whose `tokens_cache` is `null` adds nothing. `null` for [a run with no stream reader](#a-run-with-no-stream-reader). |
| `phase` | string or `null` | In [**`economy`**](../glossary.md#economy) mode, while the verification of the [**chain**](../glossary.md#chain) runs: its phase, `gates`, [**`verifier`**](../glossary.md#verifier) or [**`fix-up`**](../glossary.md#fix-up). See [the verification of an `economy` chain](#the-verification-of-an-economy-chain). `null` before the verification starts, after `run-end`, while the run is paused, and in [**`assure`**](../glossary.md#assure) mode. |
| `note` | string or `null` | `a pause request waits; delegate run --resume removes it` when a pause request waits in the directory of the run and the run is not [active](#the-run-with-no-run-id): its process stopped before the engine read the request. `null` otherwise. |
| `tickets` | list of objects | One object for each ticket, in plan order. See the table below. |

| `phase` | string or `null` | For a running ticket, the phase of its [**step**](../glossary.md#step): [**`specialist`**](../glossary.md#specialist), [**`gates`**](../glossary.md#gate), [**`verifier`**](../glossary.md#verifier), or [**`fix-up`**](../glossary.md#fix-up). `null` for a ticket that does not run. |

The phase of a running ticket follows its newest event:

| Event | Phase |
|---|---|
| `step-start`, [**`continuation`**](../glossary.md#continuation), or `agent-start` with the role `specialist` | `specialist` |
| `report-validation` that is valid, `rebase`, or `gate-start`, `gate-result` or `gate-skip` of the phase `build` or `rebase` | `gates` |
| `verify-start`, or `agent-start` with the role `verifier` | `verifier` |
| `fixup-start`, or `agent-start` with the role `fix-up` | `fix-up`. The gates of a fix-up round of [**`assure`**](../glossary.md#assure) mode stay in the phase `fix-up`. |

The two token counts and the time of the newest event come from the method `activity` of the adapter of the run. See [the adapter interface](run.md#the-adapter-interface), and the activity of [the `claude-code` adapter](claude-code-adapter.md#the-activity) and [the `opencode` adapter](opencode-adapter.md#the-activity).

#### The token counts

`status` shows two token counts, for the run and for each ticket, in each form: the lines of `status`, the JSON, and the live block and the feed of `watch`. It shows no cost.

- **New** (`tokens_new`): the input tokens, the cache writes, and the output tokens, with the thinking tokens. These are the tokens that the model reads or writes for the first time.
- **Cache** (`tokens_cache`): the cache reads. Each turn of an agent reads its whole context again from the cache, so this count grows with the number of turns times the size of the context. A long [**session**](../glossary.md#session) has many cache reads, and they do not mean that the run is expensive.

The lines give the two counts in a short form: `tokens 302k new, 9.7M cache`. The feed of `watch` uses the same form. A count under 1000 shows as it is, a count under one million shows in thousands (`k`), and a larger count shows in millions (`M`) with one decimal.

Each adapter splits the counts of its stream:

| Adapter | New | Cache |
|---|---|---|
| `claude-code` | `input_tokens`, `cache_creation_input_tokens`, and `output_tokens` of a `usage` object | `cache_read_input_tokens` of a `usage` object |
| `opencode` | `input`, `output`, `reasoning`, and `cache.write` of the `part.tokens` of a `step_finish` event | `cache.read` of the `part.tokens` of a `step_finish` event. A step with no `cache` field gives 0. |

The token counts of a `claude-code` stream:

- The counts of one turn or one session come from its `usage` object, as the table above gives.
- When the stream holds a `result` event, the counts of that session are the `usage` of the `result` event. The `usage` of an `assistant` event is partial, so it does not give the counts of a session that ended.
- For a session that has no `result` event yet (an agent that runs now), the counts are the sums of its turns: one turn for each `message.id`, with the newest usage of that message.
- A resumed session writes its events in the same stream, after the `result` event of the earlier session. The counts of the stream add the counts of each session. The streams are the files that `agent-start` and the result events name. The stream of an agent that runs now can be missing for a short time, before the [**harness**](../glossary.md#harness) opens it: it then has 0 new tokens and 0 cache tokens. Any other stream that is missing is [a stream that cannot be read](#a-stream-that-cannot-be-read).

#### The newest activity

An agent can work for a long time and write no event with a time. For example, Claude Code writes a `tool_progress` heartbeat every 30 seconds while a long command runs in the foreground, and `thinking_tokens` events while the model thinks. These events have no `timestamp` field. The rule: when the newest event of the stream has no time and shows work, the time of the newest activity is the modification time of the stream file. So the last activity of an agent that runs a long command is never more than about 30 seconds old, and does not look like a stall. The [stall](#the-stall) check of `watch` also uses the modification time of the stream, so the two agree.

### A run with no stream reader

The `status` process can have no reader of the streams of a run:

- The adapter of the run is not known to the process. For example, a script registered the adapter in its own process.
- The adapter has no method `activity`. For example, an adapter of an earlier version.

Each form of `status` then works, and exits 0. It shows the progress and the ETA. It shows no tokens and no activity: in the JSON, `tokens_new`, `tokens_cache` and `idle_seconds` are `null`, and the lines of `status` and of the [live block](#the-live-view) of `watch` have no tokens and no last activity. `status` does not read the streams of such a run. The running gate and the time since its log changed do not need the reader, so they show.

### A stream that cannot be read

`status` only shows data. Each form of `status` works, and exits 0, when an event stream of the run cannot be read. The rule: any error from the check that the stream exists, or from the method `activity` of the adapter, makes that stream a stream that cannot be read. For example, a stream cannot be read when:

- The file is missing. The stream of an agent that runs now is the exception: before the harness opens it, it has 0 tokens.
- The process cannot search a parent directory of the file.
- The process cannot read the file, for example because the file has no read permission.
- The path is a directory.
- The file is not UTF-8 text.
- A line before the last one is not JSON.
- A line is JSON, but it is not an event that the adapter can use. For example, a line is a number or a list, a `timestamp` is not a time, a usage value of a `claude-code` stream is not a number, or a `step_finish` event of an `opencode` stream has no `part.tokens.input` number.

`status` then shows no tokens and no activity for that agent:

- In the JSON, the `tokens_new` and the `tokens_cache` of its ticket are `null`. The counts of the other agents of the ticket would not be the counts of the ticket.
- When the agent runs now, the `idle_seconds` of its ticket is `null`.
- The `tokens_new` and the `tokens_cache` of the run are the sums of the other tickets.
- The lines of `status` and of the live block of `watch` show no tokens for the ticket. While the agent runs, they show no last activity for it.

Only `status` treats such a stream as no data. `delegate run` reads the stream of an agent for its [**end state**](../glossary.md#end-state), and a stream that it cannot read stays an error there.

### The progress and the ETA

The percentage:

- A ticket that ended (`built`, `failed`, or `skipped`) counts 1.
- A running ticket counts by its phase: `specialist` 0, `gates` 0.6, `verifier` 0.8, `fix-up` 0.8.
- A pending ticket counts 0.
- The percentage is the sum, divided by the number of units, times 100, rounded down. A unit is a ticket. In `economy` mode, the verification of the chain is one more unit. See [the verification of an `economy` chain](#the-verification-of-an-economy-chain).

The ETA:

- Before the first ticket ends, the ETA is `null`.
- After that, the ETA is `time` + M × N − R. M is the mean duration of the ended tickets. N is the number of units that did not end. R is the `elapsed_seconds` of the running ticket, and the time that the verification of an `economy` chain used.
- The mean uses the tickets that ended after a step (`built` or `failed`). A skipped ticket has no step and no duration, so it does not count in the mean. It counts as ended.
- The ETA is never earlier than `time`. For a run that ended, it is the time of `run-end`.

### The verification of an `economy` chain

In [**`economy`**](../glossary.md#economy) mode the verification of the [**chain**](../glossary.md#chain) runs after the last ticket ends: the gates on the chain tip, the verifier, and the fix-up rounds. For the percentage and the ETA, the verification, with its gates, is one more unit of the run, as a ticket is:

- The verification counts 0 until the journal holds `run-end`. After `run-end` it counts 1. Thus the percentage stays below 100 until the run ends.
- The verification starts at the first `gate-start` or `gate-skip` of the phase `chain`, or at the first `verify-start` when the journal holds no such gate event. While it runs, `phase` of the snapshot follows the newest `gate-start` or `gate-skip` of the phase `chain` (`gates`), `verify-start` (`verifier`), or `fixup-start` (`fix-up`). After a fix-up round the gates of the chain run again, so the phase is `gates` again.
- The ETA estimates the verification as one mean ticket: M. R holds the time from the start of the verification to `time`.
- The tickets of the chain stay `built`, with the `phase` `null`. The last ticket of each stack shows the tokens and the `idle_seconds` of the verifier of its stack.

For example, two tickets of 600 and 300 seconds ended, and the gates of the chain started 99 seconds ago. The percentage is 2 ÷ 3 × 100, rounded down: 66. The ETA is `time` + 450 × 1 − 99.

## `delegate watch`

```
delegate watch [run-id] [--repo <dir>] [--until verdict] [--stall-minutes N] [--max-minutes N] [--from <position>] [--poll-seconds N] [--raw]
```

`watch` follows the run: it reads the journal at each poll, shows each new event, and exits when it has a reason. The form of the output depends on standard output:

- When standard output is a terminal, `watch` shows [the live view](#the-live-view): the progress of the run at the top, and a short line for each event that matters below it.
- When standard output is not a terminal, or with `--raw`, `watch` prints [the raw lines](#the-raw-lines): one line for each event. A [**coordinator**](../glossary.md#coordinator) can run `watch` as a background task, read the lines, and act on the exit code.

The exit codes, the options, and the last line `position <seq>` are the same in the two forms. The position is the `seq` of the last event that `watch` reported.

With no run id and no `--from`, `watch` follows the one active run of the repository. When no run is active, it prints one line for the newest run, and no event. When more than one run is active, it prints one line for each active run, follows none, and exits 8. See [the run with no run id](#the-run-with-no-run-id).

On a terminal, `watch` also shows the progress of the run in the title of the terminal, in the two forms. See [the terminal title](#the-terminal-title).

### The run with no run id

`status` and `watch` with no run id choose the run from the active runs of the repository. `watch` uses this rule only when it also gets no `--from`. With `--from` and no run id, `watch` goes on in the newest run.

A run is active when these two conditions are true:

- Its journal has no `run-end` after its newest `resume`. This is the rule of the state of `status`: a run that ended and was resumed works again.
- The lock of its [**run branch**](../glossary.md#run-branch) names the run and a process that exists. This is the lock check of `delegate run` and `delegate pause`. See [the run lock](run.md#the-run-lock).

A run with no `run-end` and no live process is not active: its process stopped. A crash, a kill, Ctrl-C and a pause stop the process of a run.

| Active runs | `status` | `watch` |
|---|---|---|
| One | Shows the active run, also when a newer run ended. | Follows the active run, also when a newer run ended. |
| None | Shows the newest run. | Prints one line for the newest run, and exits. See [the newest run that ended](#the-newest-run-that-ended) and [the newest run that stopped](#the-newest-run-that-stopped). |
| More than one | Prints the list of the active runs, and exits 0. With `--json`, it exits 2, and the message names each active run. | Prints the list of the active runs, follows none, and exits 8. It replays no event, and prints no line `position <seq>`. |

The list has one line with the number of the active runs, and then one line for each active run, the oldest run first:

```
2 runs are active; give a run id to follow one of them:
20261019T040911Z-d636 · started 2026-10-19 17:09 · assure · 6 of 13 ended, 46% · ticket 7 specialist · last activity 1m05s ago · workflow /path/to/workflow.toml · delegate watch 20261019T040911Z-d636
20261019T051148Z-ff1a · started 2026-10-19 18:11 · economy · 0 of 1 ended, 0% · ticket 12 gates · last activity 12s ago · workflow /path/to/other.toml · delegate watch 20261019T051148Z-ff1a
```

The first line of `status` is `2 runs are active; give a run id to show one of them:`. The other lines are the same for the two commands. The parts of the line of an active run:

| Part | Meaning |
|---|---|
| The run id | The id of the run. |
| `started <date> <time>` | The local date and time of the `run-start` event. |
| The mode | The [**mode**](../glossary.md#mode) of the run. |
| `<n> of <total> ended, <percent>%` | The tickets that ended, and the percentage of [the snapshot](#the-snapshot). |
| `ticket <id> <phase>` | Each running ticket and its phase, separated by `, `. While the verification of an `economy` chain runs, `chain <phase>`. When no ticket runs, `no ticket running`. |
| `last activity <time> ago` | The time since the newest change of the journal, of the event streams and of the gate logs that the journal names. The [stall](#the-stall) check of `watch` uses the same files. |
| `workflow <path>` | The workflow file of the `run-start` event. A journal that names no workflow file gives `run branch <branch>`. |
| `delegate watch <run-id>` | The command that follows the run. |

### The newest run that ended

When `watch` gets no run id and no `--from`, no run is active, and the newest event of the journal of the newest run is `run-end`, `watch` shows no event of that run. It prints one line, and no line `position <seq>`:

```
no run is active; the newest run 20261016T030000Z-abcd ended failed at 2026-10-16 17:06; first problem: ticket a: the step failed: no commit
```

The line gives the run id, the result, and the local date and time of the newest `run-end` event. When the run failed and its journal holds a [problem](#the-problem-events), the line also gives the ticket and the reason of the first problem. Then `watch` exits with the code of the result: 0 for `built`, and 1 for `failed`. See [the exit codes](#exit-codes). The line is the same on a terminal and with `--raw`, and `watch` draws no live view.

A retry continues a run that ended: the journal gets `retry`, then a new `step-end` and a new `run-end`, and the newest of each wins, as for `delegate status`. While a retry goes on, an event follows the newest `run-end`, so the run is active, and `watch` follows it. When `watch` follows or replays a journal, a `run-end` that another event follows does not end the watch. An event of a ticket that a later `retry` of the same ticket follows is no problem: the retry continues the step of that ticket. The first problem of the line is the first problem that is not before a `retry` of its ticket.

To see the events of a run that ended, give its run id or `--from`. `watch` then replays the journal, as it does for a run that goes on. When the repository has no run, `watch` exits 2.

### The newest run that stopped

When `watch` gets no run id and no `--from`, no run is active, and the newest event of the journal of the newest run is not `run-end`, the process of that run stopped. `watch` shows no event of that run, and it prints no line `position <seq>`. It prints one line that tells how to go on with the run:

- When the run is paused, the line goes to stdout, and `watch` exits 7. A run is paused when its newest `paused` event comes after its newest `resume`, as for `status`.
- When the run stopped in a different way, for example after a crash or a kill, the line goes to stderr, and `watch` exits 2: there is no run to follow.

```
no run is active; the newest run 20261016T030000Z-abcd paused at 2026-10-16 17:06; go on with delegate run --resume 20261016T030000Z-abcd
delegate watch: no run is active; the newest run 20261016T030000Z-abcd stopped at 2026-10-16 17:06 with no run-end, and no process works on it; go on with delegate run --resume 20261016T030000Z-abcd
```

The line gives the run id, the local date and time of the newest event of the journal, and the command that resumes the run. See [the resume](run.md#the-resume).

### The live view

On a terminal, `watch` draws a frame at each poll, in place of the frame before it. The frame has the live block at the top, a blank line, and the feed below:

```
run 20261016T030000Z-abcd running 50%, 1 of 2 ended, 1h00m used, ETA 59m10s, tokens 50k new, 1.3M cache
  a built, 1h00m used, tokens 39k new, 1.1M cache
  b running specialist, 50s used, tokens 12k new, 205k cache, last activity 12s ago

16:00  run 20261016T030000Z-abcd started · assure · 2 tickets
16:00  #a started · python-specialist
16:36  #a specialist finished · 36m · tokens 19k new, 980k cache · report ok
16:52  #a gates green (pytest 16m, zensical 1s)
16:52  #a verifier started
17:00  #a verifier finished · 7m · tokens 19k new, 140k cache · report ok
17:00  #a ✓ ACCEPT · built
17:00  #b started · python-specialist
```

The live block is the snapshot of `status` (see [the snapshot](#the-snapshot)), drawn again at each poll:

- The run line gives the run id, the state, the percentage, the tickets that ended, the time used, the ETA, and the two [token counts](#the-token-counts). The ETA is the time from now, or `-`. A run that ended or paused shows no ETA. While the verification of an `economy` chain runs, its phase comes after the state: `run <run id> running verifier, 66%, ...`.
- A ticket line gives the id, the state, the phase of a running ticket, the time used, and the two token counts. While an agent of the ticket runs, it also gives the time since its last activity. While a gate of the ticket runs, it also gives the gate command and the time since the log of the gate changed, as the lines of `status` do.
- For [a run with no stream reader](#a-run-with-no-stream-reader), the lines have no tokens and no last activity.

The feed has one short line for each event that matters. A line starts with the local time of the event (`HH:MM`), then the ticket (`#<id>`), and then what happened. A line shows no path and no `None`: it shows only the name of a file. The feed joins the events that belong together into one line:

| Line | The events |
|---|---|
| `#a specialist finished · 36m · tokens 19k new, 980k cache · report ok` | The result of an agent (`adapter-result`, `fixup-result` or `verify-result`) and the event of its [**report**](../glossary.md#report). It gives the role, the end state, the time from its `agent-start`, and the two token counts of its stream. |
| `#a gates green (pytest 16m, zensical 1s)` | The `gate-result` and `gate-skip` events of one round of gates. Each gate has the short name of its command and its time. The name is the first word of the command that is not a launcher (such as `nix develop -c` or `python3 -m`), with no version. A red gate has the word `red`. |
| `#a ✓ ACCEPT · built` | A verdict, or the gates, with the `step-end` that follows them. A [**REJECT**](../glossary.md#reject) gives the number of findings. |
| `stack python ✓ ACCEPT · run built · 16m · tokens 39k new, 1.1M cache` | The verdict of the chain of a stack in `economy` mode, with the `run-end` that follows it. |
| `run built · 1h06m · tokens 50k new, 1.3M cache` | The `run-end`: the result, the time of the run, and its two token counts. |

The events `agent-start`, `gate-start`, `idle-timeout`, `run-branch-advance` and `lock-broken` have no line of their own. Each other event has a short line.

A [problem](#the-problem-events) and a [stall](#the-stall) are lines that start with `✗`. For example, `16:36  ✗ #a the specialist returned no valid result: report missing: a.specialist.json`, or `17:40  ✗ stall · no change for 30m`. The line of the time limit is `<time>  time limit · <N>m used · the run goes on`.

The view cuts each line to the width of the terminal. A frame of a run that goes on fits the height of the terminal: it keeps the newest lines of the feed. The last frame keeps the whole feed, and the terminal scrolls it. Then `watch` prints the line `position <seq>`.

### The raw lines

When standard output is not a terminal, or with `--raw`, `watch` prints one line for each event. A line has the position (`seq`), the time, the event name, and then each field of the event that is not a list or an object, as `name=value`. The field `output_tail` is not printed. Before it exits, `watch` prints the reason on a line that starts with `watch:`, and then the line `position <seq>`.

### Exit codes

<!-- generated:begin watch-exit-codes -->
<!-- Generated by `delegate docs`. Do not edit this section by hand. -->

| Code | Reason | When |
|---|---|---|
| 0 | run succeeded | The journal holds `run-end` with the result `built`. |
| 1 | run failed | The journal holds `run-end` with the result `failed`. |
| 2 | error | A usage error, a repository with no run, an unknown run id, a journal that is not valid, a `--from` position beyond the end of the journal, or, with no run id, [a newest run that stopped](#the-newest-run-that-stopped) when no run is active. |
| 3 | problem | An event is a problem. See [the problem events](#the-problem-events). |
| 4 | verdict | `--until verdict` is set and the journal holds a `verdict` event. |
| 5 | stall | `--stall-minutes` is set and nothing changed for that time. |
| 6 | time limit | `--max-minutes` is set and the time is used. |
| 7 | run paused | The journal holds `paused`: a pause request stopped the run at a step boundary. |
| 8 | choose a run | With no run id and no `--from`, more than one run is active. `watch` follows none. See [the run with no run id](#the-run-with-no-run-id). |
| 130 | interrupted | Ctrl-C stopped the watch. The run goes on. See [Ctrl-C](#ctrl-c). |

<!-- generated:end watch-exit-codes -->

Code 2 is also the code that `argparse` gives for a usage error.

`watch` checks the events in order. The first event that gives a reason ends the watch, so a run that failed exits 3 at its first problem, and not 1. The code 1 follows when `watch` goes on from the position of that problem. This rule is for a run that `watch` follows or replays. With no run id, [the newest run that ended](#the-newest-run-that-ended) exits with the code of its result, and [the newest run that stopped](#the-newest-run-that-stopped) exits 7 or 2.

A run that ended and was resumed has a `resume` event after its old `run-end`. The events before the first `resume` after its newest `run-end` that a `resume` follows are the history of the run: `watch` prints them, but a problem, a `verdict` for `--until verdict`, or a `run-end` there does not end the watch. A run that stopped with no `run-end` and was resumed has no such history, so a problem before its `resume` still ends the watch. `watch` then follows the resumed run to its new `run-end`.

A `paused` event ends the watch with the code 7: a pause request stopped the run process at a step boundary. See [the pause](run.md#the-pause). A `paused` that another event follows, for example the `resume` of the run, is history, and it does not end the watch.

### The problem events

A problem is one of these events. The raw line `watch: problem: ticket <id>: <reason>` names the ticket and the reason.

| Problem | The event | Reason in the line |
|---|---|---|
| A step ends blocked or partial | `report-validation` or `fixup-report` with a `status` other than `committed` | `the step ended <status>: <blocked_reason>` |
| A step ends with [**gates**](../glossary.md#gate) that are not green | `step-end` with the state `failed`, when the newest result of a gate command of the ticket is red | `the gates are not green: <commands>` |
| An agent fails | `adapter-result`, `fixup-result` or `verify-result` with the [**end state**](../glossary.md#end-state) `failed`, or (for a [**fix-up**](../glossary.md#fix-up) [**specialist**](../glossary.md#specialist) and a [**verifier**](../glossary.md#verifier)) the end state `capped` | `the <role> ended <end state> with exit status <n>` |
| A permission mode refused a tool | `adapter-result`, `fixup-result` or `verify-result` with a `refused` field | `the <role> was refused <tools> in <mode> mode; give the agents a settings file with DELEGATE_AGENT_SETTINGS` |
| An agent returns no result | `report-validation`, `fixup-report` or `verify-report` with `valid` false | `the <role> returned no valid result: <reason>` |
| A second [**continuation**](../glossary.md#continuation) of a step | `continuation` with a `count` of 2 or more | `the step continued <n> times (limit <n>, trigger <trigger>)` |
| A step fails for any other reason | `step-end` with the state `failed`, and no red gate | `the step failed: <reason>` |

A specialist that ends `capped` continues, so it is not a problem. The first continuation of a step is also not a problem. A gate that is red and turns green after a continuation is not a problem.

An agent that ends `finished` with an exit status other than 0 is not a problem at its result event. With a valid report, the step continues. Without a valid report, the next report event or the `step-end` gives the problem. An agent that `delegate run` ended at the idle timeout is also not a problem. The journal records `idle-timeout` before its result event, and `watch` does not check that result event. See [the end of an agent session](run.md#the-end-of-an-agent-session).

### The verdict

With `--until verdict`, `watch` exits at the first `verdict` event that is not history: a verdict before the resume of a run that ended, or a verdict of a ticket that a later `retry` of that ticket follows, does not end the watch. The raw line is `watch: verdict: ticket <id> round <n>: <verdict>: <findings>`. For the verdict of a chain in `economy` mode, the raw line is `watch: verdict: stack <name> (tickets <ids>) round <n>: <verdict>: <findings>`. The [**findings**](../glossary.md#finding) are separated by `; `. Without the option, `watch` goes past each verdict.

### The stall

`--stall-minutes N` compares the time now with the newest modification time of the journal, of the event-stream files that the events name (`event_stream`), and of the gate log files that the events name (`gate_log`). If the difference is N minutes or more, `watch` exits. The raw line is `watch: stall: the journal, the event streams and the gate logs have not changed for N minutes; last event: <the line of the last event>`. A run that has ended is not a stall.

The journal names the [**event stream**](../glossary.md#event-stream) of an agent in `agent-start`, before the agent starts. While an agent runs, its own stream therefore shows a change too. A tool heartbeat of Claude Code is such a change, so an agent that runs a long command in the foreground is not a stall. For a stream that ends with such events, `status` uses the same modification time as [the newest activity](#the-newest-activity). The journal names the log file of a gate in `gate-start`, before the gate runs, and the gate runner appends the output of the gate to it. A long gate that writes output is therefore not a stall. A gate that writes no output for N minutes is a stall. A journal of an earlier version names a stream only when the agent has ended: for such a run, set N to more than the longest time of one agent run.

### The position

`--max-minutes N` ends the watch before a [**harness**](../glossary.md#harness) kills the background task. The raw line is `watch: time limit: N minutes are used; the run is not at its end`. Each exit prints `position <seq>`, but Ctrl-C prints the position in its own line. See [Ctrl-C](#ctrl-c). `watch --from <seq>` goes on after that event:

- It prints no event with a position of `<seq>` or less, so no event is reported twice.
- It reads the earlier events for the problem rules. A step-end after the position still finds the red gate before the position.
- If the journal ended at or before the position, it exits with the result of the run.
- If the journal holds fewer events than `<seq>`, it exits 2.

### Ctrl-C

Ctrl-C stops the watch. It does not stop the run. `watch` then does these steps:

1. On a terminal, it draws the last frame of the live view, shows the cursor, and sets the title to `delegate watch · <short run id> · interrupted`. Thus the terminal is clean also when Ctrl-C comes while `watch` draws a frame. See [the terminal title](#the-terminal-title).
2. It prints one line on stderr, and no line `position <seq>`. See the line below.
3. It exits with the code 130, as a shell gives for SIGINT. It shows no traceback.

```
watch: stopped at position <seq>; the run goes on. Resume with delegate watch <run id> --from <seq>
```

The position is the `seq` of the last event that `watch` reported. `watch <run id> --from <seq>` goes on after that event. See [the position](#the-position). When Ctrl-C comes before `watch` finds the run, `watch` prints `delegate: interrupted` on stderr and exits 130.

## The terminal title

When standard output is a terminal, each `delegate` command sets the title of the terminal with the OSC 2 sequence: `ESC ] 2 ; <title> BEL`. The tab of the terminal then shows the command, and not the name of the Python process.

- `status` sets the title `delegate status`.
- `watch` sets the title `delegate watch · <short run id> · <percent>% · ETA <HH:MM>` at each poll. It writes the title again only when the title changes. The percentage is the percentage of [the snapshot](#the-snapshot). The ETA is the local time of the estimated end of the run, or `-` before the first ticket ends. See [the progress and the ETA](#the-progress-and-the-eta).
- When `watch` exits, the title is `delegate watch · <short run id> · <result>`. At the end of the run, the result is `built` or `failed`. When the watch ends before the run, the result is the reason: `problem`, `verdict`, `stall`, `time limit` or `interrupted`.
- `delegate run` sets the title `delegate run · <short run id>`. See [the output of `delegate run`](run.md#output-and-exit-codes).
- Each other subcommand of `delegate` sets the title `delegate <subcommand>`, for example `delegate render`.

The short run id is the part of the run id after the last `-`: `abcd` for the run id `20261016T030000Z-abcd`. A run id with no `-` is its own short form. A title holds no control character.

A terminal does not show the title sequence as text, so the frames of the live view and the raw lines do not change. `watch` sets the title also with `--raw`. `watch` sets no title when it cannot find the run.

When standard output is not a terminal, `delegate` writes no title sequence. To turn the title off on a terminal, set the environment variable `DELEGATE_NO_TITLE` to `1`. `delegate` does not set the title back when it exits. The shell or the terminal can set it again.
