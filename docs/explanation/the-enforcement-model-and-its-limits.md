# The enforcement model and its limits

The kit says that a [**specialist**](../glossary.md#specialist) never pushes, that a [**verifier**](../glossary.md#verifier) never writes to the [**worktree**](../glossary.md#worktree) of the [**ticket**](../glossary.md#ticket), and that only the [**coordinator**](../glossary.md#coordinator) edits a [**hotspot**](../glossary.md#hotspot). This page says how the kit makes those rules hold, and where it stops. A guard deserves trust exactly as far as it goes, and not further.

## Why git, and not the harness

Each [**harness**](../glossary.md#harness) guards in its own way, and some harnesses do not guard at all in a [**headless**](../glossary.md#headless) run. A rule that depends on a [**harness hook**](../glossary.md#harness-hook) is as strong as that hook. In a headless [**session**](../glossary.md#session) the hook may not run.

So the first guard is the same in every harness. A pre-push hook, a diff and a snapshot work with every harness that the [**engine**](../glossary.md#engine) drives, because they are git and the file system.

The harness hooks in the agent files stay. A harness that supports hooks gets a second guard from them: a [**push guard**](../glossary.md#push-guard) for the specialist, and a command guard for the verifier. I count them as a second line, not as the first.

## What the engine enforces

The engine builds the first guard from git, a diff and a snapshot. It has four checks.

- **A pre-push hook in each worktree.** The engine makes each worktree itself, and it sets a `pre-push` hook for that worktree only. The hook refuses every push. The main checkout and the other worktrees keep their own hooks.
- **A diff check against the hotspot paths.** After a specialist reports, and before the [**gates**](../glossary.md#gate) run, the engine compares the changed paths with the hotspot patterns of the [**stack**](../glossary.md#stack). A match stops the [**step**](../glossary.md#step). No gate runs and no verifier starts.
- **An unchanged-worktree check around the verifier.** The engine records the HEAD and the status of the real worktree before the verifier runs, and again after. A difference is an [**invariant**](../glossary.md#invariant) violation, and the [**run**](../glossary.md#run) halts, whatever [**verdict**](../glossary.md#verdict) the verifier wrote.
- **Gates outside the specialist.** The engine runs the gates itself. The verifier works in a [**temporary copy**](../glossary.md#temporary-copy) that the engine prepares, and the [**verifier guard**](../glossary.md#verifier-guard) keeps that copy read-only. For a [**red proof**](../glossary.md#red-proof), the verifier breaks a second copy in another temp directory, and not the branch. In a `delegate run`, the engine makes that copy, the proof copy, with no `.git` entry, so the verifier needs no `cp` and no `rm` (#153). The rendered verifier and the [**brief**](../glossary.md#brief) give a binding rule for a verifier that cannot make the copy, because the harness refuses a step of the recipe or a step fails (#152): do not break a check, a test or a file in the worktree under review, and do not make the red proof there. The verifier puts the red proof in `unverified`, with the refused command and its message. It can still run the gates in the worktree. A gate can write build output there, for example `dist/` or `build/`, and the verifier changes no source file there. The worktree is the work under review. In a `delegate run`, the engine checks that the verifier left it as it was (the [**worktree invariant**](../glossary.md#worktree-invariant)). Outside a run, the rule is the same, and nothing checks it.

The reference describes each check in detail. See [the guards in the `delegate run` reference](../reference/run.md#the-guards).

## What the engine does not stop

- The push hook does not stop `git push --no-verify`, because git skips every `pre-push` hook then. It does not stop a push from a clone, or from another directory. It holds against the plain push command of a specialist in its worktree.
- The unchanged-worktree check covers the worktree of the ticket. It does not cover the main checkout, which a person can change at any time, and it does not cover a path outside the repository.
- The snapshot ignores a file that git ignores. A verifier that writes only to an ignored file in the worktree does not show in the snapshot.
- None of this is a container. A specialist runs as the person who started it, with their permissions, in a worktree. If a policy needs stronger isolation, the kit is not the right tool by itself.

## The limits of the guards

The command guards of the harnesses have limits of their own. The [**skill**](../glossary.md#skill) that renders the agents lists them, and I list every one here, in the order of the skill, with the reason I accept it. The full text is in [the Limits section of the agent-definitions skill](https://github.com/AlexanderNZ/delegate/blob/main/skills/agent-definitions/SKILL.md#limits).

1. No harness composes agent files. A project agent is a complete file, never an extension of a global one, so a project agent must carry everything it needs. Claude Code and Codex replace on a name collision, and OpenCode merges per key, which the [**renderer**](../glossary.md#renderer) does not rely on.
2. Docs cannot be attached by path. I put reference material in a skill and list the skill. On OpenCode, the prompt names it.
3. Both Claude Code guards read the hook input with `python3`, which the kit requires already, so they need no `jq`. They [**fail closed**](../glossary.md#fail-closed): with no `python3`, or with input that holds no command text, the guard blocks the call. See [ADR 0005](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0005-guards-read-the-hook-input-with-python3.md).
4. The [**verifier guard**](../glossary.md#verifier-guard) reads the command as text. `python3` and `bash -c` are on the allow list because the gates need them, and each of them can write through the guard. `env` is a prefix, not a read (#158): the guard removes `env` and its options `-i`, `-0`, `-u <name>`, `-` and `--`, and it tests the rest as its own command. It denies each other option of `env`, a word before the command with a quote, a backslash, an expansion or a pattern character, an assignment before a command (`GIT_EXTERNAL_DIFF=touch git diff` writes files), and `bash -c` or `python3` after `env`. After `find` it denies `-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-rm`, `-fprint`, `-fprint0`, `-fprintf` and `-fls`, and after `rg` it denies `--pre` and `--hostname-bin`, because they run a command or write a file. A sed script can run a command (the GNU `e` command) or write a file (`w`), so the guard permits `sed -n` only as a line range, `sed -n '<start>,<end>p' <path>`. It does not parse Python and it does not parse a nested shell. This is a contract for the verifier, not a sandbox. It is why I also check the worktree after the verifier. So the rule against a wrapper is in the text that the verifier reads, not in the guard (#124): a command that the guard refuses is not run in another form, through `bash -c`, `python3 -c`, `sh -c`, `env`, `xargs` or a script file. The rendered verifier of each harness and the verifier brief state this rule, and the verifier reports the refusal in `unverified`, with the command and the message of the guard. The guard does not enforce the rule, because it does not parse a nested shell, and the verifiers need `bash -c` and `python3` for probes. I accept this because a `delegate run` checks the tree under review after the verifier.
5. The verifier guard divides a command at `&&`, `||`, `;`, `|`, `&` and a newline, but not inside quotes. An `&` in a redirection (`2>&1`, `&>file`) does not divide. It reads single quotes, double quotes, a backslash and a comment as bash and zsh do. It does not parse a `$(` or backtick substitution, a parameter expansion with braces, an ANSI-C quote (`$'`) or a here-document, because each of these forms reads quotes in its own way. In a command that holds one of these forms, a separator inside a quoted argument divides the command, and the parts that are not commands are denied. A quote that is not closed denies the command. The guard fails closed in each case, so the cost is a lost convenience.
6. The guard uses the bash string operators. Under `bash` and macOS `/bin/sh` it behaves as the table says. Under `zsh` it first turns on sh emulation, so that zsh divides a command into words as bash does, and it gives the verdicts of `bash`. Under `dash` it exits 2 on a syntax error. That is a deny, so the guard stays closed.
7. An assignment prefix is not on the allow list. A command substitution or a process substitution runs a command that the guard cannot examine, so a command that holds `$(`, a backtick, `<(`, `>(` or the zsh `=(` is denied, also inside single quotes. The one exception is an exact gate of the [**declaration**](../glossary.md#declaration), given as the full command. `T=$(mktemp -d)` is denied. The workaround is to run `mktemp -d` and then use a literal path.
8. The destination-flag rule is wider than the flags it must stop, because the guard does not know which flags a command takes. It also denies `cp --preserve=timestamps`, which moves no destination. The copy runs without the flag, so no capability is lost.
9. A temp path is a text prefix and a path with no `..` component. The guard rejects `..`, and does not resolve it, because a resolution needs the file system. A path that needs `..` must be written out in full.
10. The copy allow reads the source and does not examine it. A `cp` source can be any path the agent can read, secrets included, and the copy then sits in a temp directory. The temp directory is the boundary, not the source.
11. The Write guard reads the file path as text, as the verifier guard reads a command. It permits the Write tool only for an absolute path in a temp directory, with no `..` component. It does not resolve a symbolic link, so a link in a temp directory that points to a directory below the toplevel of a repository is a write into that repository. It takes `$TMPDIR` from its own environment, and the Bash guard takes the same value for an absolute path (#166). Only a safe value counts: an absolute path with at least two components, that is not the home directory or a parent of it, and that is not inside a git tree. So a host that sets `$TMPDIR` to `/`, to the home directory or to a directory in a repository opens nothing. I accept this because the verifier needs one write that a verdict with code in it cannot break, and the worktree check after the verifier still holds.
12. Both guards deny a write inside the tree under review or another git tree, or a write that holds one, also when the tree is in a temp directory. A git tree is a directory with a `.git` entry. The guards look for that entry from the working directory of the hook, and from each write target up and in it (#125), so a verifier whose working directory is a copy with no `.git` entry cannot write into the worktree. The search goes along the path as the command gives it: a symbolic link to a directory below the toplevel of a tree hides that tree. The walk in a directory reads at most 2000 directories, and a target that it could not search to the end is a deny (#132): leave a large temp copy in place, or first remove the parts that hold no git tree, one directory at a time, each with fewer than 2000 directories. The rule reads `.git` entries and not the git configuration, so `GIT_DIR` and `GIT_WORK_TREE` do not change a tree. I accept this because the worktree check after the verifier still holds.
13. The `cd` rule reads the path as text (#121). It permits a `cd` into the git toplevel of the working directory of the hook, or into a temp path. A relative path counts from the working directory, so in a temp copy with no `.git` entry, `cd app` goes to a temp path and is permitted (#131). It denies a `..` component, a path that starts with `~` or `=`, and a path with `*`, `?`, `[`, `{` or `$`. It does not resolve a symbolic link, so a link in the tree that points out of the tree takes a `cd` out of the tree. It does not read `CDPATH`, so in a shell that has `CDPATH` set, a relative `cd` can go to a directory of `CDPATH`. A submodule or a nested repository has its own `.git` entry, so after a `cd` into it, a later `cd` may go only into that directory. I accept this because a `cd` writes nothing: the guard still denies each write outside a temp directory and each write inside a git tree.
14. The git option rule reads each word as text (#140). After a git read command, the guard denies `--output` and each prefix of it down to `--o`, whether or not git accepts that prefix, unless its path is a temp path, and after `git grep` it denies `-O`, `-O<cmd>` and `--open-files-in-pager` in each form, because they run a command on the files that match. It does not know which option takes the next word, or where the pathspecs start after `--`, so a pattern or a pathspec that looks like a denied option also denies: `git grep -e -Ocat`. I accept this because the Grep tool and `grep` search for such a text.
15. The OpenCode write rules have no `$TMPDIR` prefix, because an OpenCode pattern holds no variable. On a host whose temp directory is not under `/tmp/`, `/private/tmp/` or `/var/folders/`, OpenCode denies the write of the verdict. In a directory with no version control, OpenCode takes `/` as the worktree, and it denies the write too. Each of these is a deny, and the engine then reads the verdict from the final text of the verifier.
16. The OpenCode maps cannot deny each write in the tree that the verifier reviews. OpenCode takes the real path of the project, with each symbolic link resolved, and compares it as text with the path that the agent gives. A path through a link to the project starts with `../` relative to the project, so the `edit` map allows it, and the `external_directory` map allows its temp prefix. An OpenCode pattern holds no variable that names the project, and the path of the tree changes in each run, so no rule can deny that spelling. Measured on OpenCode 1.15.10 on 2026-10-19 on macOS: in a repository at `/var/folders/<x>/copy`, whose real path starts with `/private/var/folders`, the write tool wrote a file in the tree through `/var/folders`, and it denied the same write through the real path and through a relative path. A repository under `/private/tmp` gave the same result through `/tmp`. On macOS the engine gives the verifier its temporary copy under `/var/folders`, so the rendered OpenCode verifier states this limit and tells the verifier not to use it. I accept this because the copy is not the branch, and the worktree check after the verifier still covers the real worktree.
17. The OpenCode verifier map has no `cp` rule, no `cd` rule and no `git -C <path>` rule, because an OpenCode pattern cannot examine a path argument. A wider `git -C` pattern would also match a push in a compound command. See [ADR 0002](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0002-narrow-opencode-push-pattern.md). An OpenCode verifier cannot make the copy, and it reports the [**red proof**](../glossary.md#red-proof) as a command it cannot run.
18. The OpenCode verifier allows no `getOnlyCommands` entry, because an OpenCode pattern cannot examine the arguments of a GET-only rule. A [**GET-only command**](../glossary.md#get-only-command) is a deny there. On Claude Code the guard also cannot see an argument that a shell expansion builds.
19. The OpenCode verifier map has no `nix develop` rule, because a pattern cannot test the command after `-c`, and a loose pattern would permit every command in a dev shell. An OpenCode verifier reports a dev-shell gate as a command it cannot run.
20. The OpenCode verifier map does not divide a compound command, for the same reason as the specialist map: OpenCode hands the permission check the raw command. `git status && git commit -m x` is one deny on Claude Code and one allow on OpenCode.
21. The OpenCode verifier map cannot deny each redirection to a file. Before #123, the read pattern `echo *` also matched `echo x > /Users/<user>/x`, and each other read pattern had the same gap. The map now ends with three deny rules, `*>*`, `*| tee *` and `*|tee *`, and OpenCode keeps the last rule that matches, so they win over the read allows. The source of that rule is `evaluate` in `packages/core/src/permission.ts` of OpenCode at tag v1.15.10, a `findLast` over the rules, read on 2026-10-20. OpenCode checks each simple command of a line on its own, with the text of a redirection that follows that command (`source` in `packages/opencode/src/tool/shell.ts` at the same tag). A redirection after a group (`{ cat f; } > x`), a subshell, a loop, or the last command of a pipeline (`cat f | grep x > y`) is not in that text, so no glob can deny it. Measured on OpenCode 1.15.10 on 2026-10-20 with `opencode debug agent <verifier> --tool bash`: the map denied `echo x > /tmp/<x>/e`, `cat f >> /tmp/<x>/c`, `ls &> /tmp/<x>/l`, `grep x f | tee /tmp/<x>/t` and `git status 2>/dev/null`, and it permitted and wrote `{ cat f; } > /tmp/<x>/g` and `cat f | grep h > /tmp/<x>/p`. Because of this limit, the OpenCode map has no `echo` rule and no `printf` rule: a verifier needs them only to write. The rendered OpenCode verifier states the limit and tells the verifier not to use it. The `*>*` rule also denies `2>&1` and `2>/dev/null`, because a glob cannot tell a file from a file descriptor. I accept this because the copy is not the branch, and the worktree check after the verifier still covers the real worktree.
22. The OpenCode verifier map has no `git grep` rule (#140). A pattern matches the text of the command, and the shell makes `-O` from other text: `-iOcat` and `-'O'cat` are `-O`, and `-eFOO` is not. A deny pattern wide enough for each form also denies most searches, so the map leaves `git grep` out, and the verifier searches with its grep tool. The map keeps `git diff *`, `git log *` and `git show *`, and a pattern cannot examine the path of `--output=<file>`, so the map permits that write. The rendered OpenCode verifier states this and tells the verifier not to use that option. I accept this because the worktree check after the verifier still covers the real worktree.
23. Frontmatter hooks in a project-scope agent run only after the workspace trust dialog is accepted for the folder, and a `-p` session does not count as accepting it. A project verifier in a folder that is not trusted has a Bash tool with no guard. The global [**tier**](../glossary.md#tier) is not affected.
24. The two push guards are not equal, and no pattern makes them equal. The Claude Code hook applies an unanchored expression to the raw command. An OpenCode pattern is an anchored glob, so OpenCode allows `git add . && git push`, a push with two spaces, and a push after an environment assignment. I do not widen the OpenCode pattern to `*git push*`. The residual risk is an OpenCode specialist that pushes from inside a compound command. The pre-push hook of the engine closes that gap in a run.
25. Two files with one name in one directory resolve by read order. The renderer refuses to produce that, and the [**validator**](../glossary.md#validator) reports it in hand-written sets.
26. A [**turn cap**](../glossary.md#turn-cap) is a cost stop, not a lost deliverable. At the cap, Claude Code gives only a harness note and the agent id, and the agent's own text is absent. Resuming the agent keeps its context, and the cap applies again on each [**resume**](../glossary.md#resume). OpenCode writes a summary and documents no resume. I set a cap to bound cost, and I resume the agent when it hits the cap.

## How I read the limits

Most of these limits fail closed. The cost is a command that a guard denies and that has to run another way. A few fail open: the OpenCode push patterns, the missing guard in an untrusted folder, the read of a source path, a symbolic link that the Write guard does not resolve, a link to the project that the OpenCode maps cannot deny, and a redirection that the OpenCode bash map cannot see. For those, the guards of the engine are the answer. A pre-push hook, a hotspot diff and an unchanged-worktree check do not depend on the harness, so they cover the places where a harness guard is weak.

I do not claim that the two layers together are a sandbox. They are a posture with evidence: a rule is checked by something other than the agent that must follow it. For the reasons the verifier is blind and the gates run outside the specialist, see [why the verifier is blind](why-the-verifier-is-blind.md).
