# The enforcement model and its limits

The kit says that a [**specialist**](../glossary.md#specialist) never pushes, that a [**verifier**](../glossary.md#verifier) never writes to the [**worktree**](../glossary.md#worktree) of the [**ticket**](../glossary.md#ticket), and that only the [**coordinator**](../glossary.md#coordinator) edits a [**hotspot**](../glossary.md#hotspot). This page says how the kit makes those rules hold, and where it stops. A guard deserves trust exactly as far as it goes, and not further.

## Why git, and not the harness

Each [**harness**](../glossary.md#harness) guards in its own way, and some harnesses do not guard at all in a [**headless**](../glossary.md#headless) run. A rule that depends on a [**harness hook**](../glossary.md#harness-hook) is as strong as that hook. In a headless [**session**](../glossary.md#session) the hook may not run.

So the first guard is the same in every harness. A pre-push hook, a diff and a snapshot work with every harness that the [**engine**](../glossary.md#engine) drives, because they are git and the file system.

The harness hooks in the agent files stay. A harness that supports hooks gets a second guard from them: a [**push guard**](../glossary.md#push-guard) for the specialist, and a command guard for the verifier. I count them as a second line, not as the first.

## What the engine enforces

The engine builds the first guard from git, a diff and a snapshot. It has seven checks.

- **A pre-push hook in each worktree.** The engine makes each worktree itself, and it sets a `pre-push` hook for that worktree only, for each process that the engine starts for the ticket. The hook refuses every push. The main checkout and the other worktrees keep their own hooks.
- **A diff check against the hotspot paths.** After a specialist reports, and before the [**gates**](../glossary.md#gate) run, the engine compares the changed paths with the hotspot patterns of the [**stack**](../glossary.md#stack) and with two built-in hotspots, `.claude/agents/` and `.opencode/agents/` (#188). An agent definition is never part of the work that the engine builds. A match stops the [**step**](../glossary.md#step). No gate runs and no verifier starts.
- **An unchanged-worktree check around the verifier.** The engine records the HEAD and the status of the real worktree before the verifier runs, and again after. A difference is an [**invariant**](../glossary.md#invariant) violation, and the [**run**](../glossary.md#run) halts, whatever [**verdict**](../glossary.md#verdict) the verifier wrote.
- **A check of the tip before each move.** The [**run branch**](../glossary.md#run-branch) moves only when the engine advances it after an [**ACCEPT**](../glossary.md#accept). A commit that moves it from outside the engine (a specialist with a shell, a person, or another tool) would land with no verification, and the verifier diff would not show it. So the engine keeps the tip that the [**journal**](../glossary.md#journal) says: the `to_commit` of the newest `run-branch-advance`, or the base commit of the [**run**](../glossary.md#run). It compares that tip with the real tip before each rebase onto the run branch, before each fast-forward, before the [**chain**](../glossary.md#chain) verification of [**economy**](../glossary.md#economy) [**mode**](../glossary.md#mode), and at each [**resume**](../glossary.md#resume). A difference writes `run-branch-moved` and halts the run as an invariant violation does, so the run cannot be resumed (#186). The check finds a move. It does not undo it: the run branch keeps the commit, and you look at it by hand.
- **Gates outside the specialist.** The engine runs the gates itself. The verifier works in a [**temporary copy**](../glossary.md#temporary-copy) that the engine prepares, and the [**verifier guard**](../glossary.md#verifier-guard) keeps that copy read-only. For a [**red proof**](../glossary.md#red-proof), the verifier breaks a second copy in another temp directory, and not the branch. In a `delegate run`, the engine makes that copy, the proof copy, with no `.git` entry, so the verifier needs no `cp` and no `rm` (#153). The rendered verifier and the [**brief**](../glossary.md#brief) give a binding rule for a verifier that cannot make the copy, because the harness refuses a step of the recipe or a step fails (#152): do not break a check, a test or a file in the worktree under review, and do not make the red proof there. The verifier puts the red proof in `unverified`, with the refused command and its message. It can still run the gates in the worktree. A gate can write build output there, for example `dist/` or `build/`, and the verifier changes no source file there. The worktree is the work under review. In a `delegate run`, the engine checks that the verifier left it as it was (the [**worktree invariant**](../glossary.md#worktree-invariant)). Outside a run, the rule is the same, and nothing checks it.
- **One seal for each run.** At the start of a run, the engine copies each agent that a role names from the main checkout into the run directory, outside each tree, and each session starts from that copy, the [**sealed agent**](../glossary.md#sealed-agent). Before each session, the engine hashes each file of the seal, and a difference fails the step. So the tree under review cannot change the prompt, the tools or the guard of an agent. On Claude Code, the seal is a plugin, and the session runs with `--setting-sources user`, so a committed settings file cannot turn off its guard. The reason is in [ADR 0007](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0007-the-engine-runs-each-agent-from-a-sealed-agent.md). The project settings and the project `CLAUDE.md` do not apply to an engine session, on purpose. The seal holds the text of `CLAUDE.md` instead (see [the sealed agent](../reference/claude-code-adapter.md#the-sealed-agent)).
- **A probe before the first session.** A guard that does not run writes no event, and nothing shows it. So before the first agent session, the engine starts one [**guard probe**](../glossary.md#guard-probe): one session for each verifier, from its seal, on the [**tier**](../glossary.md#tier) `cheap`. The session must run one command that the guard denies, `touch delegate-guard-probe`. Only the [**event stream**](../glossary.md#event-stream) shows a denial: a call of the tool with that command, and a tool result that is an error from the guard. A final text that tells of a denial is not a proof, because a model can decline the command and write that it is not permitted, so that result is `inconclusive`. A result other than a denial ends the run, and a dry run reports it (see [the guard probe](../reference/run.md#the-guard-probe)). The `claude-code` [**adapter**](../glossary.md#adapter) has the probe. The `opencode` adapter has none (see [the limit of OpenCode](#what-the-harnesses-do-with-a-project-agent)).

The reference describes each check in detail. See [the guards in the `delegate run` reference](../reference/run.md#the-guards).

## What the engine does not stop

- The push guard and `core.fsmonitor=false` hold for the processes that the engine starts: each agent session and each gate command of a ticket. The engine gives them through the environment of those processes (#221). A shell of a person or an IDE in a ticket worktree gets neither: a push from it runs the hooks of the repository, and git can start a file watcher there.
- The push hook does not stop `git push --no-verify`, because git skips every `pre-push` hook then. It does not stop a push from a clone, or from another directory. It holds against the plain push command of a specialist in its worktree.
- The unchanged-worktree check covers the worktree of the ticket. It does not cover the main checkout, which a person can change at any time, and it does not cover a path outside the repository.
- The snapshot ignores a file that git ignores. A verifier that writes only to an ignored file in the worktree does not show in the snapshot.
- The specialist can write the [**state directory**](../glossary.md#state-directory) and the [**journal**](../glossary.md#journal) of the run, and the seal of the agents in it (`<run directory>/agents/`). They are in a user state directory, `~/.local/state/delegate` by default, and the specialist runs as the person who started it. The engine reads the journal to resume a run, so a specialist that changes the journal changes what a resume believes. No check covers this. The agent check detects a change of a file of the seal before the next session, and the step fails. It does not prevent the change, and it does not detect a change of the journal that matches a changed file.
- The specialist can move a ref. A ref is a file in the git directory, and `git update-ref` or `git branch -f` moves it. The check of the tip (#186) catches a move of the run branch, because the engine compares the real tip with the tip that the journal says. It does not cover another ref, such as the branch of a ticket or a tag.
- The seal holds the agent file of the main checkout as it is when the run starts. A person or a tool that changes that file before the run starts changes the seal, and no check compares the file with a commit. The adapter finds the project file first and then the user file, so a project file in the main checkout wins over a user file of the same name. The guard probe shows that the harness denies one command. It does not show that each rule of the guard works.
- On OpenCode, the resolution of the sealed agent was measured, and the enforcement of its permission map in a session was not (decision D-e of #213). The `opencode` adapter has no guard probe, so nothing shows that the harness refuses a call that the map denies. The permission rules of the sealed agent come after the rules of the tree, so the map is the best evidence, and it is not a measured guard.
- None of this is a container. A specialist runs as the person who started it, with their permissions, in a worktree. If a policy needs stronger isolation, the kit is not the right tool by itself.

## What the harnesses do with a project agent

I measured how each [**harness**](../glossary.md#harness) loads a project agent that has the same name as a user agent. The results are the reason for the [sealed agent](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0007-the-engine-runs-each-agent-from-a-sealed-agent.md). They are true for the versions that I name, and a new version can change them. The probes used an agent `m187-probe` with the same name in the user directory (`~/.claude/agents/`, `~/.config/opencode/agents/`) and in the project directory of a new `git init` clone. Each probe agent wrote its own marker word, and each Claude Code probe agent had a `PreToolUse` hook on `Bash` that appended its own word to a log file (#187).

### Claude Code

Measured on 2026-10-31 on Claude Code 2.1.287 on macOS, with the command of the adapter and the model `haiku` for the probe:

```
cd <clone> && echo "Do your task." | claude --print --output-format stream-json --verbose --model haiku \
  --agent m187-probe --strict-mcp-config --disallowedTools Monitor,TaskStop --allowedTools 'Bash(pwd)'
```

| Case | Agent that loaded | Hooks that ran |
|---|---|---|
| User agent only, clone in a new temporary directory | user | user hook |
| Project agent only, clone in a new temporary directory | project | none |
| Both, clone in a new temporary directory | project | none |
| Project agent only, clone under a trusted directory | project | none |
| Both, clone under a trusted directory | project | none |

- The project agent replaces the user agent of the same name, and the guard hooks of the user agent do not run.
- A `--print` session does not run the frontmatter hooks of a project agent. Trust does not change this: the result is the same under a directory with `hasTrustDialogAccepted`, and the session adds no trust entry for the new directory.
- The journals of this repository hold 6 verifier guard denials, all in run `20261016T032643Z-a910`. That run started before the committed pair (`54eed32`, 2026-10-16). After that commit, no verifier stream holds a denial. So from 2026-10-16 to 2026-10-31 the verifier of this repository ran without its guard. The same holds for each repository that commits its rendered pair, which is what [**`bootstrap`**](../glossary.md#bootstrap) tells the owner to do.
- The first line of the model, in git and the file system, held in that time. The gap lost the second line.

Issue 213 measured the fixes on 2026-11-01, on the same version, with the command above and a committed `.claude/settings.json` with `{"disableAllHooks": true}`. `--setting-sources user` is necessary for each option: without it, that file turns off each guard, also one from `--agents` or `--settings`. It also removes the project agents and the project skills of the tree. A plugin from `--plugin-dir` gives its agent as `<plugin>:<agent>`, ignores `hooks` in the frontmatter of the agent, and runs the hooks of its `hooks/hooks.json`, also in that clone. The engine uses the plugin (see [ADR 0007](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0007-the-engine-runs-each-agent-from-a-sealed-agent.md)).

### OpenCode

Measured on 2026-10-31 on OpenCode 1.15.10 on macOS. The free models of the `opencode` provider gave no answer in 90 seconds (exit 124), so no probe ran a model. The answers come from the resolution of the agent, which happens before a model call: `opencode debug agent m187-probe`, and the start of `opencode run --agent m187-probe`.

- The project agent replaces the prompt of the user agent of the same name.
- OpenCode has no hooks in the frontmatter of an agent and no trust gate. The guard is the `permission` map.
- The permission rules of a project agent merge after the rules of the user agent. The resolved list holds the rules of the user agent first, and then the rules of the project agent. A later rule wins, so a project agent in the clone can make the guard of the user agent less strict for each permission that it names.
- `opencode run --agent <name>` refuses an agent with `mode: subagent`. It writes `agent "<name>" is a subagent, not a primary agent. Falling back to default agent` on standard error and runs its default agent (#214).

The limit: the resolution of the sealed agent was measured, and the enforcement of its permission map in a session was not.

### The skills of an agent

A rendered agent lists its [**skills**](../glossary.md#skill), with the [**context skill**](../glossary.md#context-skill) of the repository first, and the context skill reads the reference documents of the repository at load time. A subagent of the Agent tool preloads them. The engine does not start a subagent: it starts each agent as the main agent of a session. I measured whether a harness preloads a skill for that agent (#215). The probe was an agent that lists a project skill whose text holds a code word, and a question for the code word with no tool call.

- **Claude Code 2.1.287**, on 2026-11-01, with the model `haiku`: `echo "<question>" | claude --print --output-format stream-json --verbose --model haiku --agent probe --disallowedTools Bash,Read,Grep,Glob,Skill` gave `UNKNOWN`. The skill was in the skill list of the `init` event, but its text was not in the context. A prompt that starts with the line `/<skill>` gave the code word with no tool call, but with two such lines, only the first skill loaded. In the default permission mode, the load-time block of a skill that the line loads failed with `Shell command permission check failed`.
- **OpenCode 1.15.10**, on 2026-11-01, with a `qwen` model of a [**gateway**](../glossary.md#gateway): `echo "<question>" | opencode run --format json --model <provider>/qwen --agent probe --dir <directory>` gave `UNKNOWN`, and so did a prompt that starts with `/<skill>`. `opencode run --command <skill> "<question>"` gave the code word with no tool call, but the option takes one skill only.

No option of either harness preloads each skill that an agent lists. So each adapter puts the text of each skill of the sealed agent in the prompt of a new session, before the [**brief**](../glossary.md#brief). It runs each load-time block in the working directory of the session and puts the output in the place of the block, as the harness does when it loads a skill. Through the `claude-code` adapter, a `haiku` session of this repository's specialist listed the hotspot paths of `docs/agents/delegation.md`, which only the load-time block of its context skill holds, in one turn and with no tool call. A rendered OpenCode agent has no `skills` field, so the `opencode` adapter reads the list from the sentence of the body that names the skills (#234). See [the skills of the agent](../reference/claude-code-adapter.md#the-skills-of-the-agent) for Claude Code and [for OpenCode](../reference/opencode-adapter.md#the-skills-of-the-agent).

One limit stays. The adapter runs a load-time block itself, so the permission rules of the harness do not apply to it. It runs only one plain command with no shell, from a skill of the seal or of the user directory, never from the tree under review, and it leaves each other block for the agent.

## The limits of the guards

The command guards of the harnesses have limits of their own. The [**skill**](../glossary.md#skill) that renders the agents lists them, and I list every one here, in the order of the skill, with the reason I accept it. The full text is in [the Limits section of the agent-definitions skill](https://github.com/AlexanderNZ/delegate/blob/main/skills/agent-definitions/SKILL.md#limits).

1. No harness composes agent files. A project agent is a complete file, never an extension of a global one, so a project agent must carry everything it needs. Claude Code and Codex replace on a name collision, and OpenCode merges per key, which the [**renderer**](../glossary.md#renderer) does not rely on.
2. Docs cannot be attached by path. I put reference material in a skill and list the skill. On OpenCode, the prompt names it.
3. Both Claude Code guards read the hook input with `python3`, which the kit requires already, so they need no `jq`. They [**fail closed**](../glossary.md#fail-closed): with no `python3`, or with input that holds no command text, the guard blocks the call. See [ADR 0005](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0005-guards-read-the-hook-input-with-python3.md).
4. The [**verifier guard**](../glossary.md#verifier-guard) reads the command as text. `python3` and `bash -c` are on the allow list because the gates need them, and each of them can write through the guard. `env` is a prefix, not a read (#158): the guard removes `env` and its options `-i`, `-0`, `-u <name>`, `-` and `--`, and it tests the rest as its own command. It denies each other option of `env`, a word before the command with a quote, a backslash, an expansion or a pattern character, an assignment before a command (`GIT_EXTERNAL_DIFF=touch git diff` writes files), and `bash -c` or `python3` after `env`. After `find` it denies `-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-rm`, `-fprint`, `-fprint0`, `-fprintf` and `-fls`, and after `rg` it denies `--pre` and `--hostname-bin`, because they run a command or write a file. A sed script can run a command (the GNU `e` command) or write a file (`w`), so the guard permits `sed -n` only as a line range, `sed -n '<start>,<end>p' <path>`. It does not parse Python and it does not parse a nested shell. This is a contract for the verifier, not a sandbox. It is why I also check the worktree after the verifier. So the rule against a wrapper is in the text that the verifier reads, not in the guard (#124): a command that the guard refuses is not run in another form, through `bash -c`, `python3 -c`, `sh -c`, `env`, `xargs` or a script file. The rendered verifier of each harness and the verifier brief state this rule, and the verifier reports the refusal in `unverified`, with the command and the message of the guard. The guard does not enforce the rule, because it does not parse a nested shell, and the verifiers need `bash -c` and `python3` for probes. I accept this because a `delegate run` checks the tree under review after the verifier. A gate in `gateCommands` that ends with ` *` takes free arguments (#169): the guard permits each word after it, except a word that the shell can expand (#175), and the OpenCode map permits each word after it, also a word that the shell can expand. A task name or a flake ref is not a path, so the check of #163 cannot permit `./gradlew test -x processTestAot` or `nix eval --raw .#x`, and such a gate needs this form. The rendered verifier names each such gate, and it states the rule: do not put a word after such a gate that can make the gate write. I accept this for the same reason.
5. The verifier guard divides a command at `&&`, `||`, `;`, `|`, `&` and a newline, but not inside quotes. An `&` in a redirection (`2>&1`, `&>file`) does not divide. It reads single quotes, double quotes, an ANSI-C quote (`$'...'`), a backslash and a comment as bash and zsh do. It does not parse a `$(` or backtick substitution or a here-document, because each of these forms reads quotes in its own way. In a command that holds one of these forms, a separator inside a quoted argument divides the command, and the parts that are not commands are denied. A word with an ANSI-C quote or with a parameter expansion with braces (`${`) holds `$`, so the guard denies it, and the message names the full word (#238): a `|`, `;` or `&` in its quotes does not divide the command. The guard then tests a command with `${` or `$'` a second time, and divides it at each separator, also inside quotes, as before #238, so `git grep 'a${b}|c'` still denies. A quote that is not closed denies the command. The guard fails closed in each case, so the cost is a lost convenience.
6. The guard uses the bash string operators. Under `bash` and macOS `/bin/sh` it behaves as the table says. Under `zsh` it first turns on sh emulation, so that zsh divides a command into words as bash does, and it gives the verdicts of `bash`. Under `dash` it exits 2 on a syntax error. That is a deny, so the guard stays closed.
7. An assignment prefix is not on the allow list. A command substitution or a process substitution runs a command that the guard cannot examine, so a command that holds `$(`, a backtick, `<(`, `>(` or the zsh `=(` is denied, also inside single quotes. The one exception is an exact gate of the [**declaration**](../glossary.md#declaration), given as the full command. `T=$(mktemp -d)` is denied. The workaround is to run `mktemp -d` and then use a literal path.
8. The destination-flag rule is wider than the flags it must stop, because the guard does not know which flags a command takes. It also denies `cp --preserve=timestamps`, which moves no destination. The copy runs without the flag, so no capability is lost.
9. A temp path is a text prefix and a path with no `..` component. The guard rejects `..`, and does not resolve it, because a resolution needs the file system. A path that needs `..` must be written out in full.
10. The copy allow reads the source and does not examine it. A `cp` source can be any path the agent can read, secrets included, and the copy then sits in a temp directory. The temp directory is the boundary, not the source.
11. The Write guard reads the file path as text, as the verifier guard reads a command. It permits the Write tool only for an absolute path in a temp directory, with no `..` component. It does not resolve a symbolic link, so a link in a temp directory that points to a directory below the toplevel of a repository is a write into that repository. It takes `$TMPDIR` from its own environment, and the Bash guard takes the same value for an absolute path (#166). Only a safe value counts: an absolute path with at least two components, that is not the home directory or a parent of it, and that is not inside a git tree. So a host that sets `$TMPDIR` to `/`, to the home directory or to a directory in a repository opens nothing. I accept this because the verifier needs one write that a verdict with code in it cannot break, and the worktree check after the verifier still holds.
12. Both guards deny a write inside the tree under review or another git tree, or a write that holds one, also when the tree is in a temp directory. A git tree is a directory with a `.git` entry. The guards look for that entry from the working directory of the hook, and from each write target up and in it (#125), so a verifier whose working directory is a copy with no `.git` entry cannot write into the worktree. The search goes along the path as the command gives it: a symbolic link to a directory below the toplevel of a tree hides that tree. The walk in a directory reads at most 2000 directories, and a target that it could not search to the end is a deny (#132): leave a large temp copy in place, or first remove the parts that hold no git tree, one directory at a time, each with fewer than 2000 directories. The rule reads `.git` entries and not the git configuration, so `GIT_DIR` and `GIT_WORK_TREE` do not change a tree. I accept this because the worktree check after the verifier still holds.
13. The `cd` rule reads the path as text (#121). It permits a `cd` into the git toplevel of the working directory of the hook, or into a temp path. A relative path counts from the working directory, so in a temp copy with no `.git` entry, `cd app` goes to a temp path and is permitted (#131). It denies a `..` component, a path that starts with `~` or `=`, and a path with `*`, `?`, `[`, `{` or `$`. It does not resolve a symbolic link, so a link in the tree that points out of the tree takes a `cd` out of the tree. It does not read `CDPATH`, so in a shell that has `CDPATH` set, a relative `cd` can go to a directory of `CDPATH`. A submodule or a nested repository has its own `.git` entry, so after a `cd` into it, a later `cd` may go only into that directory. I accept this because a `cd` writes nothing: the guard still denies each write outside a temp directory and each write inside a git tree.
14. The git option rule reads each word as text (#140). After a git read command, the guard denies `--output` and each prefix of it down to `--o`, whether or not git accepts that prefix, unless its path is a temp path, and after `git grep` it denies `-O`, `-O<cmd>` and `--open-files-in-pager` in each form, because they run a command on the files that match. It does not know which option takes the next word, or where the pathspecs start after `--`, so a pattern or a pathspec that looks like a denied option also denies: `git grep -e -Ocat`. I accept this because the Grep tool and `grep` search for such a text.
15. The OpenCode write rules have no `$TMPDIR` prefix, because an OpenCode pattern holds no variable. On a host whose temp directory is not under `/tmp/`, `/private/tmp/` or `/var/folders/`, OpenCode denies the write of the verdict. In a directory with no version control, OpenCode takes `/` as the worktree, and it denies the write too. Each of these is a deny, and the engine then reads the verdict from the final text of the verifier.
16. The OpenCode maps cannot deny each write in the tree that the verifier reviews. OpenCode takes the real path of the project, with each symbolic link resolved, and compares it as text with the path that the agent gives. A path through a link to the project starts with `../` relative to the project, so the `edit` map allows it, and the `external_directory` map allows its temp prefix. An OpenCode pattern holds no variable that names the project, and the path of the tree changes in each run, so no rule can deny that spelling. Measured on OpenCode 1.15.10 on 2026-10-19 on macOS: in a repository at `/var/folders/<x>/copy`, whose real path starts with `/private/var/folders`, the write tool wrote a file in the tree through `/var/folders`, and it denied the same write through the real path and through a relative path. A repository under `/private/tmp` gave the same result through `/tmp`. On macOS the engine gives the verifier its temporary copy under `/var/folders`, so the rendered OpenCode verifier states this limit and tells the verifier not to use it. I accept this because the copy is not the branch, and the worktree check after the verifier still covers the real worktree.
17. The OpenCode verifier map has no `cp` rule, no `cd` rule and no `git -C <path>` rule, because an OpenCode pattern cannot examine a path argument. A wider `git -C` pattern would also match a push in a compound command. See [ADR 0002](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0002-narrow-opencode-push-pattern.md). An OpenCode verifier cannot make the copy, and it reports the [**red proof**](../glossary.md#red-proof) as a command it cannot run.
18. The subcommand rule of a `getOnlyCommands` entry (#164) does not know which option takes a value. It reads the word after each option with no `=` as the value of that option. So with the entry `tea issues`, `tea issues --comments create` passes. The rule reads the words as the shell does (#173), so a quoted value with a space is one word, but it does not expand a word: a word that holds `$` or a backtick denies, and so does a word with an unquoted pattern or expansion character, for example `{a,create}` or `*` (#175).
19. The OpenCode verifier allows no `getOnlyCommands` entry, because an OpenCode pattern cannot examine the arguments of a GET-only rule. A [**GET-only command**](../glossary.md#get-only-command) is a deny there. On Claude Code the guard also cannot see an argument that a shell expansion builds.
20. The OpenCode verifier map has no `nix develop` rule, because a pattern cannot test the command after `-c`, and a loose pattern would permit every command in a dev shell. An OpenCode verifier reports a dev-shell gate as a command it cannot run.
21. The OpenCode verifier map does not divide a compound command, for the same reason as the specialist map: OpenCode hands the permission check the raw command. `git status && git commit -m x` is one deny on Claude Code and one allow on OpenCode.
22. The OpenCode verifier map cannot deny each redirection to a file. Before #123, the read pattern `echo *` also matched `echo x > /Users/<user>/x`, and each other read pattern had the same gap. The map now ends with three deny rules, `*>*`, `*| tee *` and `*|tee *`, and OpenCode keeps the last rule that matches, so they win over the read allows. The source of that rule is `evaluate` in `packages/core/src/permission.ts` of OpenCode at tag v1.15.10, a `findLast` over the rules, read on 2026-10-20. OpenCode checks each simple command of a line on its own, with the text of a redirection that follows that command (`source` in `packages/opencode/src/tool/shell.ts` at the same tag). A redirection after a group (`{ cat f; } > x`), a subshell, a loop, or the last command of a pipeline (`cat f | grep x > y`) is not in that text, so no glob can deny it. Measured on OpenCode 1.15.10 on 2026-10-20 with `opencode debug agent <verifier> --tool bash`: the map denied `echo x > /tmp/<x>/e`, `cat f >> /tmp/<x>/c`, `ls &> /tmp/<x>/l`, `grep x f | tee /tmp/<x>/t` and `git status 2>/dev/null`, and it permitted and wrote `{ cat f; } > /tmp/<x>/g` and `cat f | grep h > /tmp/<x>/p`. Because of this limit, the OpenCode map has no `echo` rule and no `printf` rule: a verifier needs them only to write. The rendered OpenCode verifier states the limit and tells the verifier not to use it. The `*>*` rule also denies `2>&1` and `2>/dev/null`, because a glob cannot tell a file from a file descriptor. I accept this because the copy is not the branch, and the worktree check after the verifier still covers the real worktree.
23. The OpenCode verifier map has no `git grep` rule (#140). A pattern matches the text of the command, and the shell makes `-O` from other text: `-iOcat` and `-'O'cat` are `-O`, and `-eFOO` is not. A deny pattern wide enough for each form also denies most searches, so the map leaves `git grep` out, and the verifier searches with its grep tool. The map keeps `git diff *`, `git log *` and `git show *`, and a pattern cannot examine the path of `--output=<file>`, so the map permits that write. The rendered OpenCode verifier states this and tells the verifier not to use that option. I accept this because the worktree check after the verifier still covers the real worktree.
24. Frontmatter hooks in a project-scope agent do not run under `--print`, also in a trusted directory (Claude Code 2.1.287, #187). The harness documents that an interactive session runs them only after the workspace trust of the folder, and a `-p` session does not count as accepting it. The measurement shows that trust does not help: a `--print` session in a directory with `hasTrustDialogAccepted` ran no hook of a project agent. A project verifier that a `--print` session loads from a tree has a Bash tool with no guard. A `delegate run` session does not load it from the tree: it starts from the sealed agent, whose guard is a plugin hook, and the guard probe shows that the guard runs (see [ADR 0007](https://github.com/AlexanderNZ/delegate/blob/main/docs/adr/0007-the-engine-runs-each-agent-from-a-sealed-agent.md)). The global [**tier**](../glossary.md#tier) is not affected.
25. The two push guards are not equal, and no pattern makes them equal. The Claude Code hook applies an unanchored expression to the raw command. An OpenCode pattern is an anchored glob, so OpenCode allows `git add . && git push`, a push with two spaces, and a push after an environment assignment. I do not widen the OpenCode pattern to `*git push*`. The residual risk is an OpenCode specialist that pushes from inside a compound command. The pre-push hook of the engine closes that gap in a run.
26. Two files with one name in one directory resolve by read order. The renderer refuses to produce that, and the [**validator**](../glossary.md#validator) reports it in hand-written sets.
27. A [**turn cap**](../glossary.md#turn-cap) is a cost stop, not a lost deliverable. At the cap, Claude Code gives only a harness note and the agent id, and the agent's own text is absent. Resuming the agent keeps its context, and the cap applies again on each [**resume**](../glossary.md#resume). OpenCode writes a summary and documents no resume. I set a cap to bound cost, and I resume the agent when it hits the cap.

## How I read the limits

Most of these limits fail closed. The cost is a command that a guard denies and that has to run another way. A few fail open: the OpenCode push patterns, the missing guard of a project agent under `--print`, the read of a source path, a symbolic link that the Write guard does not resolve, a link to the project that the OpenCode maps cannot deny, a redirection that the OpenCode bash map cannot see, and the permission map of a sealed OpenCode agent, whose enforcement in a session is not measured. For those, the guards of the engine are the answer. A pre-push hook, a hotspot diff and an unchanged-worktree check do not depend on the harness, so they cover the places where a harness guard is weak.

I do not claim that the two layers together are a sandbox. They are a posture with evidence: a rule is checked by something other than the agent that must follow it. For the reasons the verifier is blind and the gates run outside the specialist, see [why the verifier is blind](why-the-verifier-is-blind.md).
