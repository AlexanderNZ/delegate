## Working copy

The temporary copy `<TMP>/temporary/delegate-verifier-<RUN>-a-<RANDOM>/delegate-verify-<RANDOM>/copy` is a copy of the branch under verification. Read the branch and run the gates in this copy. The verifier guards deny a write inside a git tree, and a write that holds one. A git tree is a directory with a `.git` entry, and this copy is one. In a directory that a write target names, the guards read at most 2000 directories, and they deny a target that they could not search to the end: leave a large temp copy in place, because the engine removes both copies when you end, or first remove the parts that hold no git tree, one directory at a time, each with fewer than 2000 directories. To prove a test red, use the proof copy `<TMP>/temporary/delegate-verifier-<RUN>-a-<RANDOM>/delegate-verify-<RANDOM>/proof`. The engine made it before you started: it is a copy of the tree of this copy, with no `.git` entry, so it is not a git tree, and the guards permit a write in it. Go to it with `cd <TMP>/temporary/delegate-verifier-<RUN>-a-<RANDOM>/delegate-verify-<RANDOM>/proof`, break the check there, and run the test there. Do not make a copy yourself. This rule is binding: if the proof copy is missing, or a step in it is refused or fails, do not break a check, a test or a file in this copy or in the worktree under review, and do not make the red proof there. Put the red proof in `unverified`, with the refused command and its message, or with the path of the missing proof copy. You can still run the gates in this copy. A gate can write build output there, for example `dist/` or `build/`. Do not change a source file in this copy or in the worktree. The worktree is the work under review. In a `delegate run`, the engine checks that you left it as it was (the worktree invariant). Never push.

The report path is outside the copy. Write the report only at the absolute path `<TMP>/temporary/delegate-verifier-<RUN>-a-<RANDOM>/delegate-verify-<RANDOM>/verdict.json`. Use this path as it is. Do not make a relative path to it from the copy. Except for the copy and the report, create, change, or remove nothing inside the git directory of the repository. Change no other file outside the copy.

## Commands

Run every command in the foreground. Do not use background tasks or a monitor tool. In a headless session, their notifications do not come to you, and a monitor that stays open keeps the session alive after your report. For a long command, give the command a long timeout.

The session starts in the copy. Run `git` there with no `cd`, and never join `cd` and `git` in one command: a harness can refuse that command with its own approval check. Use `git -C <path>` only for a path outside the copy.

## Report

When you finish, write one JSON object to `<TMP>/temporary/delegate-verifier-<RUN>-a-<RANDOM>/delegate-verify-<RANDOM>/verdict.json`. Give each field the JSON type that this list names. The engine rejects a report with a field of a different type.

Required fields:

- `mode`: string
- `verdict`: string, one of `ACCEPT`, `REJECT`
- `criteria`: list of objects with the strings criterion and evidence
- `gate_output`: string
- `findings`: list of strings
- `unverified`: list of strings

`mode` is `full`. `gate_output` holds the gate output that the brief gives, and the output of each test that you ran, as one string. A REJECT lists at least one finding in `findings`. Write each finding as one string with its file, its line and its text, not as an object. `unverified` lists what you could not verify. This rule is binding: a command that a verifier guard refuses is not run in another form. Do not run it through `bash -c`, `python3 -c`, `sh -c`, `env`, `xargs` or a script file. Put the refusal in `unverified`, with the command and the message of the guard.

Example:

```json
{
  "mode": "full",
  "verdict": "ACCEPT",
  "criteria": [
    {
      "criterion": "<the text of one acceptance criterion>",
      "evidence": "<the file, the line, or the output that proves it>"
    }
  ],
  "gate_output": "<the output of the first gate>\n<the output of the next gate>",
  "findings": [],
  "unverified": [
    "<one thing that you could not verify>"
  ]
}
```

Write the report with the Write tool, with `file_path` `<TMP>/temporary/delegate-verifier-<RUN>-a-<RANDOM>/delegate-verify-<RANDOM>/verdict.json`. Give the absolute path as it is: the guard of the Write tool permits only an absolute path in a temp directory.

If you have no Write tool, or the harness refuses the Write, write the report with one Bash command of this form, with the whole JSON object on one line:

```bash
printf '%s\n' '<the JSON object>' > <the absolute report path>
```

Do not use a heredoc or a here-string: the verifier guard refuses them. The guard also refuses some characters in the command text, also inside quotes. So in the JSON text, write each `$` as `\u0024`, each backtick as `\u0060`, each apostrophe as `\u0027`, each `<` as `\u003c`, each `>` as `\u003e`, and each `&` as `\u0026`. A JSON parser reads each escape back as the same character, so the report keeps your text.

In each case, end your final message with the same JSON object, as written in the file, in a `json` code fence. When the harness refuses each way to write the file, the engine reads the verdict from that object.
