## [1.10.0] - 2026-10-22

### Added

- The command `delegate clean [<run-id>...] [--ended] [--merged] [--dry-run] [--repo <repo>]` removes what ended runs left behind (#168). Before, a run that ended before the clean-up of #167, or with `keep-worktrees = true`, kept its ticket worktrees, its ticket branches and their fsmonitor daemons, and no command removed them or a run branch that the coordinator had merged. Now `clean` takes run ids or the short run ids, and `--ended` selects each run of the repository. It cleans a run only when the newest `run-end` of its journal after its newest `resume` has the result `built`, and no live process holds the lock of its run branch; a run that is active, failed, paused or stopped keeps everything, and its line names the reason. For a run that it cleans, it applies the rules of the clean-up of #167: it stops the fsmonitor daemon of each ticket worktree, removes each worktree with no change that is not committed, with its hooks directory, and deletes each ticket branch that the run branch holds with `git branch -d`. It also removes each verifier copy and proof copy that the journal names and that a killed run process left. `--merged` also deletes the run branch when the base branch holds it, with `git branch -d`; when the run branch is gone already, the base branch is the holder of the ticket branches. The command holds the lock of the run branch while it cleans the run, and runs `git worktree prune` before the runs and at the end, so a ticket branch whose worktree directory a person removed by hand can go too. It prints one line for each run, with the worktrees removed, the branches deleted, each item kept with its reason, and the space freed. `--dry-run` prints what it would remove and keep, and changes nothing. The command exits 0 when it removed or kept each item by the rules, 1 on an error, and 2 with no run id and no `--ended`. The journal of each run where something went gets one `cleanup` event after its `run-end`, with the fields of the engine's event, `copies_removed` and `bytes_freed`; `delegate watch` and `delegate status` still read the run as ended. The version-control port gets `prune_worktrees`. `docs/reference/commands.md`, `docs/reference/run.md`, `docs/how-to/watch-and-resume-a-run.md` and the `agent-delegation` skill describe the command: a coordinator runs `delegate clean --ended --merged` after it merges a run.

### Changed

- A run that ends `built` removes its ticket worktrees and the ticket branches that the run branch holds (#167). Before, the engine removed nothing that a run made, so a repository collected worktree directories, registered worktrees, `run/*` branches and, with `core.fsmonitor` on, one `git fsmonitor--daemon` for each worktree that did not stop by itself. Now, before `run-end` with the result `built`, the engine stops the fsmonitor daemon of each ticket worktree and removes the worktree with `git worktree remove`, with its hooks directory. A worktree with a change that is not committed stays; a file that a gate made and that git does not ignore, for example `__pycache__/`, is such a change. The engine then deletes each ticket branch whose commits the run branch holds with `git branch -d`, never `-D`; a ticket branch that the run branch does not hold stays, and so does the branch of a worktree that stays. The run branch, the journal, the reports and the gate logs stay. The journal records one `cleanup` event with the worktrees removed, the branches deleted, and each one kept with its reason; `delegate status` and `watch` show no line for it. A run that ends `failed`, a paused run and a stopped run keep everything, because `--retry` and a resume need the worktrees. A plan change that goes on with a run that ended `built` makes new worktrees, and in `economy` mode a new ticket after the chain starts from the run branch when its predecessor's branch is gone; the clean-up runs again at the next `run-end` with the result `built`. The new workflow field `keep-worktrees = true` turns the clean-up off for a run. `docs/reference/run.md`, `docs/reference/workflow.md` and `docs/reference/layout.md` describe the clean-up and the field.

### Fixed

- Security fix of the verifier guard: a word after a gate cannot make the gate write (#163). Before, the guard matched a gate by its first words and did not examine the words after it, so `cd app && npm run lint -- --fix` (it rewrites source files), `cd app && npm test -- -u` (it updates snapshots), `cd app && npx tsc --outDir /Users/x/o` (it writes outside a temp directory) and `cd api && ./gradlew test spotlessApply` (it runs a task that formats the source) passed the guard (1.8.0 and 1.9.0). Now, after a plain gate, the guard permits only a path that exists in the git toplevel of the working directory or in a temp directory, for example a test file, the separator `--`, a number (all digits, #169), a redirection, and a flag of the new declaration key `gateExtraFlags`. Each other word denies, and the message names the word and the gate. A relative path counts from the directory of the last `cd` of the command. A flag of `gateExtraFlags` is permitted alone or with `=` and a value in the same word, and an entry `"<flag> <value>"` also permits the next word as the value of the flag, unless that word starts with `-`: a parser such as yargs (Jest) takes no such word as a value, so the guard tests it as a word of its own, and `npm test -- -t -u` denies. The declaration parser checks each entry; `bootstrap` has no flag for the key. `gateExtraFlags` is one list for the declaration: it applies to each gate with no ` *`. A gate with no word after it stays permitted. A gate in `gateCommands` that ends with ` *`, for example `"./gradlew *"` or `"nix eval *"`, takes free arguments (#169): the guard permits each word after it, as before this fix, so `./gradlew test jacocoTestReport -x processTestAot` and `nix eval --raw .#x` pass. The rules for redirections, temp writes and git trees still apply to it. The guard does not check the words after such a gate, so the rendered verifier names each such gate and tells the verifier not to put a word there that can make the gate write. The verdicts are the same in bash, `/bin/sh` and zsh. The OpenCode verifier map now permits each plain gate only as its exact text, with no ` *`, because a pattern cannot tell a path from a word that writes: declare each form of a gate that an OpenCode verifier needs. A gate that ends with ` *` becomes the rule `<gate> *` (#169). To upgrade: if your verifiers run a gate with arguments that are not paths, for example task names, flake refs or subcommands, add ` *` to that gate in `gateCommands`, or list its read-only flags in `gateExtraFlags`, and render the agents again. The example declaration sets `gateExtraFlags = ["--info"]`, and the declaration of this repository names its test gate in full, `nix develop -c python3 -m pytest -rs -n auto`. `docs/reference/opencode-adapter.md`, the enforcement page, ADR 0004 and the `agent-definitions` skill describe the rules, and the skill tells how to choose between a gate with no ` *`, `gateExtraFlags` and ` *`.
- Security fix of the verifier guard: a read command of a declaration does not permit a write subcommand after it (#164). Before, the guard matched a `getOnlyCommands` entry by its words and permitted each word after it, except a method, body or output flag, so with the entry `tea issues` it permitted `tea issues create -t x` and `tea issues close 12`, which write to the issue tracker, and with `gh issue` it permitted `gh issue create` (1.9.0). Now, after the words of an entry, the guard permits only an option (a word that starts with `-`), the word after an option with no `=`, a number, a path (a word with a `/`) and a redirection. Each other word can be a subcommand, so it denies, and the message names the word and the entry. `tea issues`, `tea issues 12` and `tea issues --state open` stay permitted, and `./scripts/api /health` stays permitted. An entry that ends with ` *`, for example `"tea issues list *"`, is a prefix on purpose: the guard permits each word after it, as before, the declaration parser accepts it, and the rendered Claude Code verifier states that the entry is a prefix. The verdicts are the same in bash, `/bin/sh` and zsh. The OpenCode verifier map permits no `getOnlyCommands` entry, as before. The guard cannot tell an option that takes a value from one that takes none, so it reads the word after each option as a value; the `agent-definitions` skill states this limit. The committed verifier pair of this repository is rendered again. ADR 0004 and the `agent-definitions` skill describe the rule.
- The verifier guard reads `--o` and `--ou` as `--output`, and a write target with a `..` component has its own deny message (#165). First, the rendered Claude Code verifier said that the hook denies `--output` and each prefix of it, but the guard read the prefixes only down to `--ou` after a git read command, so `git diff --o /Users/x/o` passed (git 2.54.0 rejects `--o=` as ambiguous), and only down to `--out` after a GET-only command. A command built on argparse accepts a unique prefix of a long option, so `agent-definitions render <file> --ou /Users/x/o` writes to `/Users/x/o`, and with `getOnlyCommands = ["agent-definitions render"]` the guard permitted it (1.9.0). Now the guard reads each prefix of `--output` down to `--o` as the output option, after a git read command and after a GET-only command: the path must be a temp path. After `git grep`, `--o` stays a run option, and the guard denies it with each path. The rendered Claude Code verifier, the committed verifier, the `agent-definitions` skill and the enforcement page state the shortest prefix, `--o`. Second, `touch ../x` in a temp copy was denied with the message "A path argument is outside a temp directory.", but the guard denies it for the `..` component. Now the deny message of a temp write, a `cp` destination or a redirection target with a `..` component is "The write target [<path>] has a .. component." and it tells the verifier to give the path with no `..` component. The verdicts are the same in bash, `/bin/sh` and zsh. The committed verifier pair of this repository is rendered again.
- The Bash guard of the verifier accepts a path under the runtime value of `$TMPDIR`, as the Write guard does (#166). Before, the Bash guard accepted only `/tmp/`, `/private/tmp/`, `/var/folders/` and the literal word `$TMPDIR`, so on a host with `TMPDIR=/home/agent/.tmp`, `mktemp -d` gave `/home/agent/.tmp/tmp.X`, and a `cd`, a `touch` or an `rm` on that absolute path was denied, while the Write guard permitted the same path (1.9.0). Now the two guards use one rule: a path that starts with the value of `$TMPDIR` in the environment of the hook and a `/` is a temp path, when that value is safe. A safe value is an absolute path with at least two components, with no empty, `.` or `..` component, that is not the home directory or a parent of it, and that is not inside a git tree. Otherwise only the fixed prefixes count. So the Write guard no longer permits a path under a `$TMPDIR` that is the home directory, a parent of it, or a directory with one component. A path under the value obeys each other rule of a temp path: no `..` component, not inside a git tree, and not holding one. The verdicts are the same in bash, `/bin/sh` and zsh. The OpenCode maps cannot follow the runtime value, because an OpenCode pattern holds no variable; `docs/reference/opencode-adapter.md` states this. The committed verifier pair of this repository is rendered again.

## [1.9.0] - 2026-10-21

### Added

- A stack of a workflow can name `prepare`: a list of commands that the engine runs itself in each tree before an agent starts in it (#155). A tree that git makes holds no ignored file, so before, the worktree of a ticket, the temporary copy of a verifier and the proof copy held no installed dependencies, for example no `node_modules`, and the gates of a JavaScript stack failed there. The verifier guard permits only the gate commands, so the only workaround was `npm ci` in the gates. Now the engine runs the `prepare` commands in order, through the gate runner and with the environment of a gate: in the worktree after it makes it and before the specialist starts (again when a resume or a retry makes the worktree again, or when a stop or a failure came before the last command was green), and in the temporary copy of each verifier before it makes the proof copy, so the proof copy holds what the commands made. The journal records `prepare-start` and `prepare-result` for each command, with the tree, the directory, the exit status and the path of its log file, `runs/<run id>/gates/<ticket id>/prepare-<tree>-<round>.log`. A command that fails ends the step `failed` with the reason `prepare failed: <command>`; it is not a gate, and it starts no continuation and no fix-up round. The check of the workflow checks the field as it checks `gates`, and `delegate run --dry-run` prints `stack <name> prepare: <command>` for each command. With no field, nothing changes. The log of a running `prepare` command counts as activity for `delegate watch --stall-minutes` and for `delegate status`. `docs/reference/workflow.md`, `docs/reference/run.md` and the `agent-delegation` skill describe the field.
- A stack of a workflow can name `specialist-notes` and `verifier-notes`: text that the engine adds to each brief of the stack (#156). Before, setup text that each agent of a stack needs, for example how the repository is set up or that the host has no visual gate, had to go into each ticket. Each field is a string, or the path of a file relative to the workflow file: `specialist-notes-file`, `verifier-notes-file`. A stack gives at most one field of each pair. The engine adds the text as the section `## Notes of this stack`: the specialist notes to the specialist brief, the continuation brief and the fix-up brief of the specialist; the verifier notes to the full verifier brief, the fix-up verifier brief and the chain brief. The section says that the notes do not replace the ticket and do not change the rules of the brief, and that the ticket and the rules of the brief win where they differ. The check of the workflow checks the type of each field, that a stack gives at most one field of each pair, and that a notes file exists and is not empty; the message names the stack and the field. `delegate run --dry-run` prints the notes of each stack. With no field, nothing changes. `docs/reference/workflow.md` and `docs/reference/run.md` describe the fields.

### Changed

- In `assure` mode, the verifier brief gives the output of the gates that the engine ran green on the commit under verification, as the brief of a chain verifier does in `economy` mode (#157). Before, the engine ran the gates after the build and again on the rebased tree, but the verifier got only the gate commands, so it ran the full gates once more in its copy. On a host where one Bash call has a time cap, for example 10 minutes, a long suite did not fit. Now the `## Gates` section of the full verifier brief gives the gate commands, the rebased commit and the output of the green gates, and tells the verifier not to run the gates again. The verifier runs the tests of its own red proof and its own probes, and its `gate_output` holds the gate output of the brief and the output of each test that it ran. The scoped verifier of a fix-up round gets the output of the gates that the engine ran green on the fix-up commit, also in a retry that goes on at the scoped verifier. `docs/reference/run.md` describes the verifier step and the fix-up round.

### Fixed

- Security fix of the verifier guard: `env` is a prefix that the guard tests through, not a read command (#158). Before, `env` was in the read list, and the guard matches a read command by its first word, so `env touch <file>`, and each other command after `env`, passed the guard (1.7.1 and 1.8.0). Now the guard removes `env` and its options `-i`, `-0`, `-u <name>`, `-` and `--`, and it tests the rest of the segment as its own command, with every rule, in bash, `/bin/sh` and zsh. `env`, `env -0` and `env | grep PATH` stay permitted, and so does `env` with only options and `NAME=value` assignments. The guard denies `env touch <file>`, `env -i touch <file>`, `env A=1 rm <file>` and `env bash -c '<cmd>'`. It also denies an assignment before a command, as it denies an assignment prefix without `env` (`env GIT_EXTERNAL_DIFF=touch git diff` writes files), each other option of `env` (`-S` runs a string as a command), a word before the command with a quote, a backslash, an expansion or a pattern character, and `bash -c` or `python3` after `env`. The check of the other read commands for the same shape found three more, and the guard now examines their words: after `find` it denies `-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-rm`, `-fprint`, `-fprint0`, `-fprintf` and `-fls`; after `rg` it denies `--pre` and `--hostname-bin`; and it permits `sed -n` only as a line range, `sed -n '<start>,<end>p' <path>`, because a GNU sed script runs a command with `e` and writes a file with `w`, and `-i` edits a file in place. The OpenCode verifier map has no `env` rule, because a pattern `env *` also matches `env touch <file>`. `docs/reference/commands.md`, `docs/reference/opencode-adapter.md`, the enforcement page and the `agent-definitions` skill describe the rules.
- The verifier guard resolves a relative write target against the working directory of the hook input, as it resolves the path of a `cd` (#159). Before, the guard resolved a relative path only for `cd` (#131), and it tested the path of a write as text, so in a temp copy with no `.git` entry, for example the proof copy of a verifier (#153), `touch app/x` and `echo x > app/x` were denied. Now, when the working directory is in no git tree, the guard puts the working directory and a `/` before a relative write target, and applies each rule of an absolute target to the result: a temp path, no `..` component, not inside a git tree, and not holding one. So `touch ../../x` stays denied, and so does a write into a nested repository of the copy. When the working directory is in a git tree, each relative write target is in that tree, so it stays denied. A relative path with a pattern or an expansion character, a quote or a backslash inside the path, or a leading `~` or `=`, stays denied. After a `cd` in the same command, a relative write target stays denied, because the guard does not follow the `cd`. The verdicts are the same in bash, `/bin/sh` and zsh.
- Three sentences of the verifier prose are exact (#160). They are in the rendered Claude Code and OpenCode verifiers, the verifier brief, the committed verifier pair, the two skills and the enforcement page. First, the guard denies `--output` and each prefix of it after a git read command, whether or not git accepts that prefix. Before, the Claude Code verifier said that the guard denies each prefix that git can accept, but git 2.54.0 rejects `--outp=` for `git log`, `git show` and `git diff`. Second, the engine checks the worktree invariant only in a `delegate run`. Outside a run, the rule is the same, and nothing checks it. Before, the text said that the engine checks it, also for a verifier that a person or a coordinator spawns. The text, and the deny message of the walk limit, also no longer say that the system removes temp directories: no source showed it. Third, a verifier that cannot make its copy can still run the gates in the worktree, a gate can write build output there, for example `dist/` or `build/`, and the verifier changes no source file there. Before, the text called the gates read-only checks.
- Security fix of the verifier guard: `mktemp` and `file -C` cannot write outside a temp directory (#161). Before, `mktemp` and `file` were in the read list with each argument, so the guard permitted `mktemp /Users/x/fXXXXXX` and `file -C -m a.txt` in bash, `/bin/sh` and zsh (1.8.0). `mktemp <template>` makes the file of the template, and `file -C` writes a compiled magic file in the working directory. Now the guard permits `mktemp` only when the file is in a temp directory: with no template (`mktemp`, `mktemp -d`), with `-t` and one name with no `/`, with `-p <dir>`, `--tmpdir` or `--tmpdir=<dir>` where `<dir>` is a temp path and each name has no `/`, or with templates that are temp paths, not inside a git tree. It denies each other form, for example `mktemp /Users/x/fXXXXXX`, `mktemp -p /Users/x` and `mktemp fXXXXXX` in a git tree. macOS `mktemp` makes one more file for each template, in the working directory, also with `-t`, so `-t` permits one name only. After `-p`, `--tmpdir` or `-t`, at any position, the guard denies each template with a `/`, also an absolute one: `mktemp` makes the template in that directory or in the system temp directory, so `mktemp -p /tmp/par wt/fXXXXXX` can write into a git tree there. After `file`, the guard denies `-C` and `--compile`, also in a cluster of short options such as `-bC`. `file a.txt` stays a read. The verdicts are the same in bash, `/bin/sh` and zsh. The OpenCode verifier map has no `file` rule, and it permits `mktemp` only as `mktemp` and `mktemp -d`, because a pattern cannot examine a template or a directory. `docs/reference/commands.md`, `docs/reference/opencode-adapter.md` and the rendered OpenCode verifier state the rules.

## [1.8.0] - 2026-10-20

### Added

- A declaration key, `contextLoad`, selects how the context skill loads its references (#148). `contextLoad = "blocks"` is the default, as before. With `contextLoad = "read"`, the context skill has no load-time block: its first instruction tells the agent to read each reference document with the Read tool before any other step, in the order of the references, and to stop and report when a reference is missing. Use it on a host where a load-time block cannot run. `agent-definitions bootstrap` takes `--context-load read` (and `--context-load blocks`), and any other value exits 1. The skill carries the line `<!-- agent-definitions:context-load read -->`, and `validate` gives the new finding `LOAD_BLOCK_IN_READ_SKILL` for each load-time block in a skill with that line. Without the flag, `bootstrap` writes the same bytes as before. The `agent-delegation` skill and ADR 0006 record a measurement of 2026-10-20 on Claude Code 2.1.283: a coordinator that called `EnterWorktree` and then spawns an agent with worktree isolation cannot load the context skill of that agent, so the coordinator calls `ExitWorktree` first.
- `delegate docs` also writes the terminal figures: six frames of `delegate watch` and `delegate status` as SVG files in `docs/assets/terminal/`, one light and one dark file for each frame (#138). The figures are `watch-live` (frame 3a of turn 3 of the design of #114), `watch-picker` (the run picker, frame 2b), `status-table` (frame 1i), `watch-fixup` (a REJECT and a fix-up round, frame 1d), `watch-paused` (a paused run) and `watch-fit` (a plan of 40 tickets fitted to 24 rows, frame 3b). Each figure is the output of the code, not a picture of the design: the command renders the frame from journals in `src/delegate/docs/figures/` with a fixed clock and a fixed terminal size, on the path of `watch` and `status` with the SGR codes on. A frame of `watch` is the first frame that the live view draws. Each line of the frame is one `<text>` row in the code font of the site, and each run of one paint role is one `<tspan>`. The colours are the tokens of the docs theme as hex values, not the colours of the design mock. Each file has `role="img"`, a `<title>` and a `<desc>`, and no script. `delegate docs --check` names each figure file that is missing or differs from the code and exits 1, and a drift test in the suite runs it for each file. `docs/reference/docs.md` lists the figures and their journals.

### Changed

- The live view of `delegate watch` shows a spinner while an agent is active, and a snapshot gives `active <time> ago` (#147). Before, the live tail of the running row and the end of the waiting line gave `active 2s`, which read as a duration ("active for 2 seconds"), but it is the time since the last activity of the agent. Now, on a terminal, the liveness has three states. Under 30 seconds since the last activity, a spinner in cyan, `⠋ ⠙ ⠹ ⠸ ⠼ ⠴ ⠦ ⠧ ⠇ ⠏` (`| / - \` with a locale that is not UTF-8), steps one frame in approximately 125 ms: between two reads of the journal, the frame is drawn again in place from the snapshot that it has, and the time between two reads does not change. The spinner turns only while the agent is active. From 30 seconds to the stall time, the tail gives `quiet <time>` in faint text, with no animation. Past the stall time, it gives `⚠ idle <time>`, as before. With `NO_COLOR` set, there is no animation, and the tail gives `active <time> ago`. The run picker of `delegate watch` and `delegate status`, and the status line entry of the Claude Code plugin, give `active <time> ago`. `gate <name> · log <time> ago`, `⚠ idle <time>`, `watch --raw` and `status --json` do not change. A sink of `delegate.run.watch.follow` now has the method `wait(seconds)`, which waits between two reads of the journal.
- The pane of the `/delegate` command of the Claude Code plugin gives the plan index and `after <id>`, as in frame 1m of turn 3 of the design of #114 (#145). It replaces the tree of #120. Before, a ticket sat under its deepest blocker with `└─`, two cells deeper for each level. Now each row starts with its plan index and its id, with no tree prefix. When the one blocker of a ticket is the ticket of the row above, the row names no blocker. Otherwise, the row ends with `after` and each blocker, as `after 90` or `after 82 89`, as the `after` column of `delegate watch` does. A blocker that is not in the plan does not count. The rows of the tickets that ended stay dim. The status line, the band and the toasts do not change.
- The live view of `delegate watch` fits the height of the terminal as in frame 3b of turn 3 of the design of #114 (#144). Before, when the frame did not fit, the rows of the built tickets folded to one line with their ids, and the table could hide the work that remains. Now the table gets the rows of the terminal, less the line of the cursor, the run line, the blank line, the header, the divider and 4 lines of the feed. When the plan has more rows, the rows show from the top in plan order, and the tail folds into one last row above the divider, as `· 13 pending  126–144  rows 28–40 folded`. When that does not keep 3 rows after the running ticket, the rows in the middle also fold into one row, as `✓ 17 built  104–120  2h50m  657k  0  rows 4–20 folded`, with the sums of `used`, `new` and `cache`. The first 3 rows and the 3 rows before the running ticket stay, and the rail runs through the fold. The rows of the running ticket never fold, and the pending rows nearest to it fold last. When the terminal does not give its size, no row folds. While a run is `pausing`, the live tail of the next row gives `pauses before this step` in yellow, and once the run is paused, `paused before this step`. At 80 columns, the bar drops first, then `new` and `cache`, then `used`, and the labels of the phases stay. With the ASCII glyphs, a range is `104-120`. `delegate status`, `watch --raw` and `status --json` do not change.
- The ticket table of the live view of `delegate watch` and of `delegate status` is flat and in plan order, as in frame 3a of turn 3 of the design of #114 (#143). It replaces the tree of `blocked_by` of #115 and the tracks of #130. Before, a ticket sat two cells deeper than its blocker for each level, so a chain of 15 tickets made the `plan` column 35 cells wide. Now the tracks are `#` 3, a rail 2, `plan` 6, `state` 10, `phase` 13, `after` 8, `used` 7, `new` 5, `cache` 6 and the live tail, so the table has the same width for each plan. A column is wider than its track only when a value is wider. The rail `│` (`|` in the ASCII set) joins a row to the row directly above when that row is its one blocker. Otherwise the new column `after` names each blocker, as `66`, and a join names each one, as `126 132`. The phases of the running ticket stack: its row gives the first phase, and each further phase is a sub-row with the rail, the phase and a detail in the live tail. While a gate runs, its phase gives the gate count, as `gates ● 2/3`, when the journal holds an earlier run of the gates of the same stack, and the sub-row gives `gate <name> · log <time> ago`. The reason of a ticket that failed or was skipped, and `paused before this step`, are in the live tail, not in the `phase` column. At 80 columns, `new` and `cache` drop, then `used`. The labels of the phases stay. The folded built rows read `✓ <count> built`. The table of `status` has the same tracks with `state` 8, `verdict` 7 and `branch` 15 after `after`, and `last event` at the end. It has no live tail: the activity of an agent and the running gate are only in `status --json`, and the reason of a row comes after `last event`. `plan_links(events)` replaces `plan_tree(events)`. The feed of #130, `watch --raw`, the lines of `watch` to a pipe, and `status --json` do not change.

### Fixed

- The agents and the gates of a `delegate run` do not get the `PYTHONPATH` entry of the `delegate` package of the engine (#154). Before, the `claude-code` adapter, the `opencode` adapter and the gates gave each process the full environment of the engine. - `agent-definitions validate --skills-dir` reads each skill that a Claude Code agent preloads, in `--skills-dir` and in `--user-skills-dir`, and checks each load-time block (a fenced block that opens with `` ```! ``). A block that holds `$(`, a backtick, `;`, `&&`, a double pipe, a pipe, `if` or a redirection outside quotes gives the new finding `LOAD_BLOCK_NOT_PLAIN`, with the file and the line: `LOAD_BLOCK_NOT_PLAIN <file>:<line>: <message>`. Claude Code cannot analyse such a block, so a subagent that preloads the skill does not start (ADR 0006). One plain command passes. Before, only the template of `bootstrap` was tested, and a context skill that a person changed by hand showed the failure only when an agent started (#95). `bootstrap` runs the same check on each skill that the new agent preloads: the context skill that it writes, and also each hand-written skill in the skills root of the project and in the user skills directory (`--user-skills-dir`, default `~/.claude/skills`). So a preloaded skill with a load-time block that is not plain now makes `bootstrap` exit 1, and `bootstrap` writes no agent file.
- The neutrality check also scans `plugins/` and `.claude-plugin/`, with the same denylist and allowlist rules. It skips `plugins/<name>/.claude-plugin/types/`, which Claude Code writes when it loads a plugin from a folder (#102).

### Changed

- `delegate watch` with no run id and no `--from` reports an ended newest run in one line, `no run is active; the newest run <id> ended <result> at <local time>`, with the ticket and the reason of its first problem when it failed, and exits with the code of the result. It replays no event. The run has ended only when the newest event of its journal is `run-end`, so a run that a retry built gives the result of that retry. An explicit run id or `--from` keeps the replay (#99).
- The context-skill template, the `agent-definitions` skill and the bootstrap reference cite ADR 0006 for the load-time block rule of Claude Code: one plain command, measured on Claude Code 2.1.283 on 2026-09-26 in the manual, acceptEdits and auto modes. No Claude Code documentation states the rule (#94).

### Fixed

- The plugin files name no person: the owner of `.claude-plugin/marketplace.json` and the author of the Claude Code plugin are "The delegate maintainers", and the plugin README adds the marketplace from the root of a clone. The neutrality check, which now scans the plugins (#102), found the names.
- In an `economy` chain with more than one stack, the verifier of a later stack sees each fix-up of an earlier stack that changes a file of its tickets: the chain brief holds the delta of those fix-ups and names the files (#93).
- `delegate status` and `delegate watch` follow a run that ended and was resumed. Before, `status` gave the old result and `100%`, and the retried ticket as `failed`, and `watch` exited at once at the old `run-end`. Now a `run-end` that a `resume` follows does not end the run, a ticket with a `retry` event is `running`, and `watch` treats the events before the first `resume` after the newest `run-end` that a `resume` follows as history (#103).
- When the verifier guard denies a file descriptor as the last word inside quotes, such as `bash -c "ls 2>&1"`, its message now tells the agent to put a space before the closing quote: under bash and `/bin/sh`, `bash -c "ls 2>&1 "` is permitted. The guard still denies the first form, because a quote after the descriptor can make the target a file name: `ls >&1")"` writes the file `1)` (#104).
- The verifier guard permits a redirection to `/dev/null`, such as `ls src 2>/dev/null`, and under bash and `/bin/sh` also `> /dev/null` with a space. Before, it denied the target as a write outside a temp directory. Only the exact path counts: `/dev/nullx`, a path under `/dev/null` and another device stay denied, and a write command such as `cp` or `tee` keeps the temp rule (#105).
- The verifier guard checks each redirection target of a word, not only the last one, also in the word after a sign that stands alone. Before, `ls >x>/tmp/y` passed in bash, `/bin/sh` and zsh, `ls > /tmp/y>x` passed in bash and `/bin/sh`, and `ls >x 2>/tmp/y` passed in zsh. Each one wrote the file `x` outside a temp directory (#105).
- While `delegate watch` follows or replays a journal, an event of a ticket that a later `retry` of that ticket follows is no problem, a `run-end` that another event follows does not end the watch, and `--until verdict` does not exit at a verdict of such a ticket (#99).

### Changed

The lines give `tokens 302k new, 9.7M cache`, and the feed of `delegate watch` uses the same form. Before, one count added the cache reads to the new tokens. Each turn reads the whole context again from the cache, so that count was mostly cache reads, and a normal run looked expensive (#86). `status` shows no cost.

The `claude-code` adapter adds `--strict-mcp-config` to every command, so the agent does not get the MCP servers of the user, of the project, or of the plugins, and it passes the servers of the stack with `--mcp-config`. The `opencode` adapter adds the servers of the stack to `OPENCODE_CONFIG_CONTENT`; OpenCode has no option that removes the servers of the user (#87).
- The specialist brief, the fix-up brief and the continuation brief tell the specialist not to run a gate command, and to run only the tests of the code that it changes. The engine runs the gates after the report, and their result decides the step. Before, each ticket ran the full suite two times (#82).

### Added

- A Claude Code plugin in `plugins/claude-code/` shows the progress of a run of the repository (#60). While a run is active, a status line entry shows the short run id, the percentage, the ETA, the running ticket and its phase, the time since the last activity, and the two token counts: `delegate 1638 · 84% · ETA 13:12 · ▶ 60 specialist · active 18s · 1.9M new · 53.0M cache`. When no agent activity occurs for the minutes of the option `stall_minutes` (default 5), the entry shows `⚠ idle` and a band above the prompt shows the warning in the warning colour. A toast shows when a ticket ends and when the run ends. The `/delegate` command opens a pane with one row for each ticket: the state, the phase, the time used, and the tokens. The plugin runs only `<command> status --json` every 5 seconds, in the working directory of the session. The option `command` (default `delegate`) names the command. When the command fails, or its JSON has no `percent` field, the plugin shows nothing. The repository root holds `.claude-plugin/marketplace.json`, which lists the plugin.

The command prints `run <run id>` and `log <path>`, and exits 0. A harness that stops its tool shell, or a background task at a time limit, then does not stop the run. `--detach` also works with `--resume` and `--retry`, and the resumed run appends to the same log (#76). The protocol skill and the how-to page on watch and resume start and resume a run with `--detach`.

- A stack of a workflow file can name MCP servers in its new `mcp-servers` table. The engine gives them to the specialist and the verifier of that stack (#87).

### Fixed

- One run has one base: the commit of `base-branch` at the start of the run. The journal records it in the new field `base_commit` of `run-start`, the run branch starts at it, and a resume uses it, not the tip of `base-branch`. No ticket branch starts from `base-branch` itself. Before, a ticket branch that the engine made after a commit landed on `base-branch` started from that newer commit. The rebase onto the run branch then copied the commits of `base-branch` onto the ticket branch, and the verifier diff and the hotspot guard saw them as the work of the ticket (#90). A resume of a journal of 1.2.0 or earlier, which has no `base_commit`, takes the base of the run from the first `run-branch-advance`, or from the tip of the run branch.
- In `assure` mode, a ticket with `blocked-by` starts from the tip of the run branch, also with the default `ticket-start = "base-branch"`. Its blockers are accepted before its step starts, so its branch holds their commits, and its specialist sees their work. Before, the branch started from `base-branch`, and a ticket that changed the files of its blocker stopped with a conflict at the rebase onto the run branch (#91). A ticket with no `blocked-by` keeps the rule of `ticket-start`.
- A resume of a step that the engine rebased onto the run branch counts the commits of the ticket from the commit that the branch was rebased onto. So the hotspot guard and the continuation brief do not see the commits of the run branch under the ticket.
- A specialist that commits its work and writes no report does not fail the step at once. The engine sends a continuation that asks only for the report, as for a report that is not valid. The journal records the trigger `report-missing`, and the continuation counts against the continuation limit of the mode. A missing report on a branch with no commit of the ticket still fails the step (#85).
- `delegate run --resume <run-id> --retry <ticket>` also goes on with a failed step of `economy` mode. It uses the worktree and the commits of the step again. The specialist continues, with the continuation limit of the mode again, or, after a valid report that says `committed`, the engine checks the step again. The journal records the `retry` phase `specialist` or `gates`. The skipped tickets after the step are checked again, and the chain then goes on to the chain verification, which covers only the built tickets whose work the run branch does not hold. A step that the chain verification failed, a step that a later built ticket went past, and a step whose chain start moved cannot be retried (#85).
- `delegate run --resume <run-id>` takes over a lock that names the same run id and a process that no longer exists, with no flag. The journal records `lock-broken`, and stderr names the old process. A lock whose process is alive still stops the resume, and a lock of another run still needs `--break-lock` (#92).
- The verifier guard denies a redirection with `&` to a file: `>&word`, `>& word`, `n>&word` and each `>>&`. It permits `>&` and `n>&` only before a file descriptor number or `-` (#89).
- `delegate watch` and a resume give a text, not `None`, for a report or a step end with a null reason (#89).
- The engine keeps the push guard and the `core.fsmonitor` rule of a worktree in the include file `delegate.config` in the git directory of the worktree, and no longer sets `extensions.worktreeConfig`, which go-git tools such as `tea` refuse. A worktree of an earlier version moves its settings to the include file (#84).
- A `tool_progress` heartbeat and a `thinking_tokens` event of Claude Code count as activity. These events have no `timestamp`, so `delegate status` showed an old last activity for an agent that worked. When the newest event of the stream is one of them, the time is the modification time of the stream file (#81).

### Added

- A host can give every agent a Claude Code settings file and a permission mode, with no change to a workflow file. The `claude-code` adapter adds `--settings <path>` when `DELEGATE_AGENT_SETTINGS` is set, and `--permission-mode <mode>` when `DELEGATE_PERMISSION_MODE` is set, for each specialist and each verifier. A settings path that is relative or not a file stops the adapter before an agent starts. The settings file must not turn off hooks, because the verifier guard is a hook. With neither variable, the command does not change. For OpenCode, a host sets `OPENCODE_CONFIG`, which OpenCode reads itself; the `opencode` adapter writes a warning when either variable is set.

The harness port has the new result field `refused`; an adapter outside the kit that does not set it still works.
- A host can move the state directory of every repository out of the git directory with `DELEGATE_STATE_ROOT`, an absolute path. Each repository gets `<root>/<name>-<key>/`, where the key comes from its git common directory, so the worktrees, the reports, the journals and the locks are on paths with no `.git` component. Claude Code in `dontAsk` mode refuses `Edit` and `Write` on such a path, also with an allow rule. `run`, `status`, `watch` and `--resume` all find the directory. With no value, the state stays in `<git common dir>/delegate/`.
- The package has a `test` extra: `pip install '.[test]'` installs `pytest` and `pytest-xdist`, so the suite can run in parallel with `python -m pytest -n auto`. The development shell of the flake also holds `pytest-xdist`.

### Changed

- In `economy` mode, the engine runs no gate for one ticket. A valid report with the status `committed`, on a branch with a commit of the ticket, builds the step. At the end of the chain, for each stack, the engine runs the gates once on the chain tip. Red gates start a fix-up round with the output of the red gates, and the gates then run again. Green gates go on to the verifier of the chain. Its brief holds the gate commands, the commit and the output of the green gates, and it tells the verifier not to run the gates again. A REJECT starts a fix-up round, then the gates, then a scoped verifier. The rounds of red gates and of a REJECT count together against the fix-up limit of `economy` mode, which goes from 1 to 2. Before, the engine ran the gates after each ticket, and the verifier of the chain ran them again. `assure` mode does not change.
- The gate events on the tip of an `economy` chain have the phase `chain`. The `fixup-start` event of a chain also has `stack`, `tickets`, and `trigger` (`gates-red` or `reject`).
- In `economy` mode, `delegate status` shows the phase `gates` for the run while the gates of the chain run. The percentage and the ETA count the gates as part of the verification of the chain.

### Fixed

- A verifier that cannot write its verdict file still gives a verdict. When the file is missing, the engine takes the last JSON object with a `verdict` field from the final text of the verifier, writes it to the report path, and checks it as a file; `verify-report` records `source` `final-text`. The verifier brief tells the verifier to end its final message with the verdict object. A host whose permission mode refuses a shell redirect to a file (Claude Code in `dontAsk` mode) needs this. The harness port has the new optional result field `final_text`; an adapter outside the kit that does not set it still works.
- A verifier can write its verdict through the verifier guard. The guard refuses a heredoc and a here-string, and some characters of a command, also inside quotes, so a verifier that tried a heredoc, or a verdict with a backtick in its evidence, failed the step after all its work. The report section of each verifier brief (full, fix-up, and chain) now names the one form that the guard permits: `printf '%s\n' '<json>' > <report path>`, with the JSON on one line, and `$`, the backtick, the apostrophe, `<`, `>` and `&` written as JSON escapes.
