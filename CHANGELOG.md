# Changelog

This file lists the changes of each release of `delegate`. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The version follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- A guard probe shows that the harness runs the guard of each sealed verifier (#219, part of the fix of #213). The harness hooks did not run in the verifier sessions of this repository from 2026-10-16 to 2026-10-31, and nothing showed it: a guard that does not run writes no event. Now a run starts no agent session before the probe of each verifier of the run shows a denial. The engine starts one session for each verifier, from its sealed agent, on the tier `cheap`, in a new temporary directory outside the repository that holds a git repository with one commit. The brief asks for the command `touch delegate-guard-probe` one time, and for the output or the error of the tool in the final text. The result comes from facts: `ran` when the file exists, `denied` when it does not exist and the event stream or the final text shows a denial, and `inconclusive` for any other result. The journal gets `guard-probe` with the agent, the handle, the result and the path of the event stream. At the start of a run, a result other than `denied` ends the run with a reason that names the agent, the result and the limits page; a resume probes again, and a resume that seals nothing probes only a verifier with no denied probe. A resume with `--agents-changed` probes again. `delegate run --dry-run` runs the probe after the setup check, prints `stack <name>: guard probe denied` for each stack with no problem, prints each other result on stderr, and exits 1. No option turns the probe off. The `claude-code` adapter has the probe; the `opencode` adapter has none until it runs from its seal (#214). The version-control port gets `make_scratch_repository`, and the harness port gets the attribute `probes_guard`. See `docs/reference/run.md` and `docs/reference/workflow.md`.

### Changed

- A `prepare` command that leaves the worktree unclean fails the step before the specialist starts (#224). A `prepare` command of a stack copied a directory into each ticket worktree and left an untracked file. The specialist committed its work, the engine found the file in its check for uncommitted changes, and the step went on with the trigger `uncommitted` and a full specialist session. Now, after the `prepare` commands in the worktree of a ticket, the engine checks the worktree for changed paths and untracked paths. A path that `.gitignore` names is not one, so a worktree that is clean after `prepare` goes on as before. When the engine finds a path, the step fails before an agent starts, with the reason `prepare left <paths> in the worktree; add them to .gitignore, or make prepare leave the worktree clean`. The check does not apply to the temporary copy of a verifier. See `docs/reference/workflow.md` and `docs/reference/run.md`.
- A gate has a readable short name, and a workflow can name a gate (#223). In a repository with a frontend, each gate of the form `cd <dir> && <tool>` had the short name `cd`, so the live view of `delegate watch` showed `gates red (pytest 1m, cd 4s, cd 2s, cd 8s, cd 1m red)` and the person could not see which gate was red. Now the short name comes from the last part of a `&&` or `;` chain that is not `cd <dir>`, and the launchers stay skipped: `cd frontend && npx vitest run --project unit` is `vitest`, and `nix develop -c python3 -m pytest -q` is still `pytest`. A gate of a stack can also be a table `{ name = "<name>", command = "<command>" }`. The name goes into the feed, the live view, the pause line and the reason of a red gate, and the journal holds it in `gate-start`, `gate-result` and `gate-skip` of that gate; the command runs as before. A workflow with strings only is valid as before. When two gates of a stack have the same short name, `delegate run --dry-run` prints a warning on stderr that names the gates and says to give each one a `name`, and it does not refuse the workflow. See `docs/reference/workflow.md` and `docs/reference/status-and-watch.md`.
- The docs describe the sealed agent, and give the results of #187 (#220, part of the fix of #213). New: ADR 0007, "The engine runs each agent from a sealed agent, outside the tree under review", with the five measured options, the reason for the choice, and the note that the project settings and the project `CLAUDE.md` are dropped on purpose. The page on the enforcement model adds the sealed agent and the guard probe to what the engine enforces, replaces the limit about a verifier that loads a project agent from the copy, and adds the results of #187 for Claude Code 2.1.287 and OpenCode 1.15.10, with the commands. Limit 24 is corrected: the hooks of a project agent do not run under `--print`, also in a trusted directory. The page also states the limit of decision D-e: on OpenCode, the resolution of the sealed agent was measured, and the enforcement of its permission map in a session was not. The skill `agent-delegation` says that a `delegate run` session uses the sealed agent and that the committed pair stays for the Agent tool, and that its note about the preload of the context skill applies to a subagent of the Agent tool and not to a `--agent` session (#215). The limit of the same text in the skill `agent-definitions` is corrected too. See `docs/adr/0007-the-engine-runs-each-agent-from-a-sealed-agent.md` and `docs/explanation/the-enforcement-model-and-its-limits.md`.
- The sealed agent of the `claude-code` adapter holds the instructions of the repository (#218, part of the fix of #213). Measured on Claude Code 2.1.287: with `--setting-sources user` (#217), a session does not load the `CLAUDE.md` of the project, so the agents lost the instructions of the repository. Now the seal adds the section `## Instructions of the repository` at the end of the body of the sealed agent file. It holds the text of `CLAUDE.md` and of `.claude/CLAUDE.md` of the main checkout, each one that exists, in that order. A line that is one import, `@<path>`, is replaced by the text of that file; the path counts from the directory of the file that imports it, an import in an imported file is replaced to a depth of 5, a missing file keeps its import line, and an import in a code block is not replaced. `CLAUDE.local.md` is not sealed. A repository with no `CLAUDE.md` gets no section. The text is in the seal, so a change of `CLAUDE.md` after the seal fails no step and does not reach the session, and `--agents-changed` seals the new text. See `docs/reference/claude-code-adapter.md` and `docs/reference/run.md`.
- Each Claude Code session of a run starts from the sealed agent of the run (#217, part of the fix of #213). Measured on Claude Code 2.1.287: under `claude --print --agent <name>`, a project agent in the tree replaces the user agent of the same name, the harness does not run the hooks of a project agent, and a committed `.claude/settings.json` with `disableAllHooks: true` turns off a guard that comes from `--agents` or `--settings` too. So a specialist could change the instructions of a verifier, and turn off its guard. Now the engine seals each agent that a role names from the main checkout, at the start of the run, into `<run directory>/agents/<agent>/`, outside each tree. `run-start` records each seal in `agents` (the agent, the source path, the seal directory, the handle, and the path and SHA-256 of each file), and `schema` is 2. Before each agent session the engine hashes each file of the seal, and a difference fails the step with `agents-changed` and the tree `seal`. The engine does not read the agent file in the tree of the agent. `delegate run --resume <run-id> --retry <ticket> --agents-changed` seals again from the main checkout. A resume of a journal with the record of #205 seals at the resume and records the seal. The `claude-code` adapter seals an agent as a plugin (`delegate-seal-<agent>`: the agent file with no `hooks`, `hooks/hooks.json`, a copy of each project skill, and the user settings file in the files of the seal), and the command is `claude --print ... --setting-sources user --plugin-dir <seal directory> --agent <plugin>:<agent> ...`, also for a resumed session. The project settings of a repository no longer apply to an engine session: a host gives its settings with `DELEGATE_AGENT_SETTINGS`. The adapter ends a session as `failed`, with the reason `the harness did not load the sealed agent <handle>`, when the `init` event does not list the handle, and it refuses to seal for a harness before 2.1.287. The method `agent_file` and the module `adapters/agent_files.py` are removed from the harness port. See `docs/reference/run.md` and `docs/reference/claude-code-adapter.md`.
- The harness port seals an agent and judges a command against its guard (#216). Before, the setup check of `delegate run --dry-run` held its own table of agent directories and one branch for each guard format, so knowledge of each harness was outside the adapters. Now the port has `seal(agent, source, into)`, which writes a copy of the agent file into a directory and gives a `SealedAgent` (the name, the handle of the session, the seal directory, and the SHA-256 of each file), and `permits(sealed, command)`, which gives `None` or the reason of the denial. The `claude-code` and `opencode` adapters implement both, and the setup check calls them. Its output does not change. No session changes. See `docs/reference/layout.md`.

### Fixed

- The live view of `delegate watch` follows an active run to its end, and a replay does not stop at a problem that the run went past (#222). A plain `delegate watch` on a terminal exited 3 at a second continuation while the run went on, so the owner read the last frame as a failed run, and a second `delegate watch` replayed the journal and exited 3 at the same line, because only a `continuation` or a `retry` of the ticket, a `step-start`, a `step-end` or a `run-end` counted as a later event. Now a problem never ends the live view (standard output is a terminal, no `--raw`, no `--json`): the feed shows it as a warning line in yellow, with the same text, and the row of its ticket keeps the warning mark `⚠` until the next event of that ticket. The live view ends only at `run-end` (0 for `built`, 1 for `failed` or `abandoned`), `paused` (7) and `halted` (8), and at the limits of the person: `--until`, `--stall-minutes`, `--max-minutes` and Ctrl-C (130). The raw lines and the JSON lines still end with 3 at a new problem, so an agent has the exit as its signal. Their replay takes a problem as history when any later event of the run follows it, so a watch that starts again with no `--from` follows the active run; a problem that is the newest event of the journal still ends the watch with 3. The new option `--follow` makes the raw lines and the JSON lines behave like the live view: no exit at a problem. A replay of an ended run, and a run that was resumed, follow the same rule: a `resume` or a `pause-requested` after a problem now makes it history. See `docs/reference/status-and-watch.md` and the skill `agent-delegation`.
- The engine gives the settings of a worktree through the environment, and writes no `includeIf` section to the configuration of the repository (#221, #84). Claude Code 2.1.287 refuses each worktree-isolated agent spawn in a repository whose `.git/config` holds an `includeIf` section, also one whose condition matches no directory. The engine wrote one section for each ticket worktree (the push guard), so a coordinator in that repository could not spawn such an agent while a run had a worktree. Now the file `delegate.config` in the git directory of the worktree holds `core.fsmonitor=false` and the `core.hooksPath` of the push guard, and the version-control port gives the environment entries (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`) that include that file with a `gitdir:` condition, so only that worktree reads it. The entries go after the entries that the environment holds already. Each agent session and each gate command of a ticket gets them (`AdapterRequest.environment` and the new `environment` argument of `GateRunner.run`), and the git commands of the engine run with `core.fsmonitor=false`. Git 2.31 or later is needed; the engine was tested with git 2.54.0. When the engine makes or removes a worktree, it removes each `includeIf` section that an earlier version wrote; a section of a person stays. `delegate clean` removes such a section of a worktree that a person removed by hand. The push guard and `core.fsmonitor=false` hold for the processes that the engine starts: a shell of a person in a ticket worktree gets neither. The engine still sets no `extensions.worktreeConfig`, because `tea` refuses it (#84). While a run of an earlier engine version has a worktree, spawn an agent with no worktree isolation; see the table of the skill `agent-delegation`. See `docs/reference/run.md`, `docs/reference/layout.md` and `docs/explanation/the-enforcement-model-and-its-limits.md`.
- `opencode run` falls back to the default agent for a rendered pair with `mode: subagent` (#214, part of the fix of #213). Measured on OpenCode 1.15.10 on 2026-10-31: `opencode run --agent <name>` refuses an agent with `mode: subagent`, writes `agent "<name>" is a subagent, not a primary agent. Falling back to default agent` on standard error, runs its default agent, and exits 0. So the engine ran the default agent for the specialist and for the verifier, and the prompt and the `permission` map of the pair did not apply. Now the renderer writes `mode: all` for each OpenCode agent, so the agent works with `opencode run` and as a subagent of a coordinator; render the pair of a repository again to get the change. The `opencode` adapter runs each session from the sealed agent of the run: the seal writes the agent file as an OpenCode configuration (`<agent>.json`, the agent as an entry of `agent`, with `mode: all` and the body as `prompt`) in the seal directory, and the adapter gives it to the session in `OPENCODE_CONFIG_CONTENT`, merged with the MCP servers. Measured with `opencode debug agent`: that prompt replaces the prompt of a project agent of the same name in the tree, and its permission rules come after the rules of the tree. The adapter ends a session as `failed`, with a reason that names the agent, when the standard error of the harness shows that it fell back to its default agent. `agent-definitions validate` gives the new finding `SUBAGENT_MODE` for an OpenCode agent file with `mode: subagent`. The enforcement of the permission map of a sealed agent in a live session was not measured, so the adapter has no guard probe. See `docs/reference/opencode-adapter.md`, `docs/reference/commands.md` and `docs/reference/run.md`.

## [1.13.0] - 2026-10-31

### Added

- `agent-definitions bootstrap --skill-only` writes only `<skills root>/<name>-context/SKILL.md`, and `bootstrap --gate-extra-flag <flag>` writes `gateExtraFlags` (#208). Before, a repository whose declaration held a key that `bootstrap` could not write, for example `gateExtraFlags`, had no command to make its context skill current: `bootstrap` replaced `agents.toml`, so the hand edits were lost, and it copied the rendered pair into the agent directories at once. Now `--skill-only` writes no declaration, renders nothing and copies no agent file, and it needs only `--repo`, `--name`, `--domain`, each `--reference`, `--context-load` and `--skills-root`. `--gate-extra-flag` can be given more than once, writes each entry in the entry format of the declaration (`--flag` or `--flag <value>`), and the command in the header comment of the files that `bootstrap` writes holds it, so a run of that command gives the same declaration again. The text of the `LOAD_BLOCK_NOT_PLAIN` finding now names the fix: run `agent-definitions bootstrap --skill-only` with the options of the command in the header comment of the skill.
- The engine checks the agent files of a run before each agent session (#205). Before, an agent file that git ignores (for example under `.claude/`, when `.gitignore` names it) was in no diff, so no hotspot saw it, and a change of such a file in the main checkout during a run changed the specialist or the verifier of each later step, with no record in the journal. Now `run-start` records the SHA-256 of the agent file of each role of the run, as the adapter finds it for the main checkout, in the new field `agents`: the path and the hash of each file, also for a user-level file outside the repository. Before each agent session, after `prepare`, the engine hashes the same agent file in the tree of the agent. A hash that differs, or a missing file, fails the step before the agent starts. The reason names the file, the recorded hash and the new hash, and the journal gets the new event `agents-changed`. `delegate run --resume <run-id> --retry <ticket> --agents-changed` records the hashes of the main checkout again in the `resume` event, and the step goes on; a resume without the flag fails again with the same message. A step that the check stopped before a specialist session can be retried in `assure` mode too: the retry spawns the specialist, so a changed specialist file does not end the run for good. The reason of the step names the command that goes on, with `--retry <ticket>`. A resume of a journal of an earlier version, which has no `agents`, records the hashes at the resume and says so. The adapter interface has the new method `agent_file`. See `docs/reference/run.md`.

### Changed

- A retry with a new ticket text starts the failed ticket again from its base (#204). Before, `delegate run --resume <run-id> --retry <ticket>` with a new text (rule 10, #202) used the worktree and the commits of the failed step again and went on at the first phase that did not complete. In `assure` mode it spawned no specialist, so a new ruling of the owner, for example "no new dependency", reached only the verifier brief and the fix-up brief, and the old commits stayed. Now a retry that changes the text makes the branch and the worktree of the ticket again from the base of the step, as the first `step-start` took it, and spawns a new specialist with the new text in both modes. Then the gates and the verifier run as for a new step. The rounds of the old step do not count against the fix-up limit, and a step that failed for a phase reason, for example a REJECT after the last fix-up round, can be retried this way. The engine keeps the old branch as `<branch>-failed-<n>`, and `delegate clean` removes it with the other branches of the run. `retry` has the new fields `restart` and `failed_branch`, a new `step-start` follows it, and `delegate status` names the kept branch on a line `kept:` until `delegate clean` removes the branch. The help of `--retry` tells this. In `economy` mode, the tickets after the retried ticket start from the new tip. A retry with no change of the text goes on as before. See `docs/reference/run.md`, `docs/reference/commands.md` and `docs/reference/status-and-watch.md`.

### Fixed

- A retry goes on after the agent check stopped a fix-up session (#209). Before, the check could stop a step before the fix-up session of a round, and the command that the message names, `delegate run --resume <run-id> --retry <ticket> --agents-changed`, exited 1: `assure` mode refused the step because the fix-up specialist gave no report, and `economy` mode refused the ticket because the chain verification failed it. The run could not go on. Now that retry records the hashes again and runs the fix-up of the same round again, on the same rejected commit with the same findings, in `assure` mode (`retry` with `phase` `fixup`) and for the chain fix-up of `economy` mode (`phase` `chain-fixup`, with the tickets that the stop failed in `revived`). The retry is not a new fix-up round, so the fix-up limit stays the same. In `assure` mode, when the run branch moved after the stop, the retry runs the fix-up and its gates, rebases the branch, and starts a full verifier at that round. In `economy` mode, the retry works for a stack that is not the last stack of the chain too. The engine now checks the agent file before it writes `fixup-start`, so a stop leaves no `fixup-start`, and a retry without `--agents-changed` fails again with the agent-check message and writes none. `agents-changed` for the role `fix-up` has the new fields `rejected_commit` and `findings_file`, and in a chain also `stack`, `tickets` and `trigger`. The retry of a stop before a verifier session of `assure` mode is as before. See `docs/reference/run.md`.
- `delegate clean` and `delegate clean --abandon` record a stale lock that they remove (#207). Before, `delegate run --break-lock` appended `lock-broken` to the journal when it removed a stale lock, but the two clean commands removed the lock and appended no event, so the journal did not show that a lock was there, or which process held it. Now each of them appends `lock-broken` with the run id and the process id of the old holder when it removes a stale lock of the run: `--abandon` before the `run-end`, and `clean` before the `cleanup`. A lock that is not there, or whose process exists, gets no event, and `--dry-run` writes none. `lock-broken` after a `run-end` does not continue the run, as `cleanup` does not, so `delegate status` and `delegate watch` show a built run as built. See `docs/reference/run.md` and `docs/reference/commands.md`.
- The example of `delegate status` and its two figures show the journal under the default state root (#206). Before, the example on the reference page of status and watch and the figures `status-table-light.svg` and `status-table-dark.svg` showed `~/project/.git/delegate/runs/...`, which is no longer the default path since #200, so a reader who followed the page looked in the wrong directory. Now they show `~/.local/state/delegate/project-3f9a1c0b7d42/runs/...`, and `delegate docs` makes the figures with the new path. A test checks that no page or figure under `docs/` shows a journal under `.git/delegate`.

## [1.12.0] - 2026-10-30

### Added

- `delegate run --resume <run-id> --retry <ticket>` can change the text of the failed ticket that the retry starts again (#202). Before, a failed ticket had started, so its text was fixed, and a new ruling of the owner for it, for example "no new dependency", needed a new run with the ticket and all the tickets after it. The new rule 10 of the plan change allows only the field `text`, only for the ticket of `--retry`, and only when its newest `step-end` is `failed`. `plan-change` records the old and the new `text_sha256` in `retry_text`, `--resume --dry-run` prints the verdict of the rule, and the briefs of the retried ticket hold the new text.
- `delegate clean --abandon <run-id> --reason "<text>"` ends a run that is not built, for good, and records the decision (#201). Before, `delegate clean` refused a run that was paused, halted, failed or stopped and told the operator to resume it, and no command ended such a run. A coordinator that had to give up on a run removed its worktrees, branches and run directory by hand, and the journal had no record of it. Now the command acts on a run that has no live process. It appends `run-end` with the result `abandoned` and the new field `reason`, and then removes the worktrees, the ticket branches and the hooks directory of the run, also when they hold work that is not committed or not merged. It keeps the run branch and prints its name, and `--delete-run-branch` deletes it too. It refuses a run with a live process and names `delegate stop`, it refuses a run that ended `built` and names `delegate clean`, and the parser refuses it without `--reason`. `delegate status` shows the state `abandoned` and the reason, the live view and the one line of `delegate watch` show the reason, `delegate watch` exits 1 for the run, and `delegate run --resume` refuses it. The version-control port has the new method `discard_branch`. See `docs/reference/commands.md`, `docs/reference/run.md` and `docs/how-to/watch-and-resume-a-run.md`.
- A crash keeps its traceback in a file of the run (#194). Before, the engine wrote only `crashed: <type>: <message>` into `step-end` and dropped the traceback, so a crash in a long run that nobody watched left one line to find the cause from. Now, when `_execute` or the chain verification of `economy` mode records a crash, the engine writes the full traceback to `runs/<run id>/crash-<seq>.txt`, where `<seq>` is the `seq` of the `step-end`, and the event gets the new field `traceback` with the path. `delegate status` shows the path after the reason, `delegate watch` shows it in the problem line, and `delegate clean` removes the file of a run that it cleans and names it in the new `tracebacks_removed` field of `cleanup`. See `docs/reference/run.md`, `docs/reference/commands.md` and `docs/reference/status-and-watch.md`.
- `delegate watch --json` prints each event as one JSON object on one line (#190). Before, a script that followed a run had the raw text lines, or it had to read the journal file itself and do the work of `watch`: find the journal, follow it across a resume, and stop for a reason. Now each line is the event as the journal holds it. When the watch ends for a reason of its own (a problem, a verdict, a stall or the time limit), it prints one last object `{"event": "watch-end", "reason": ..., "exit_code": ...}`. The exit codes are the same as before. The form prints no line `position <seq>`, no run picker, no live view and no title of the terminal, so standard output holds JSON objects only. `--json` and `--raw` cannot be used together: the parser exits 2. The live view stays the default on a terminal. See `docs/reference/status-and-watch.md`.
- The journal has a schema version, and the module `delegate.run.events` names each event and its fields (#189). Before, the names of the events were string literals in the engine, the fields had no definition in code, and a journal did not say which schema it used, so a tool outside the kit had no version to check against. `run-start` now writes `schema`, an integer, and a journal with no `schema` is version 0. A test keeps the module equal to the journal table of the run reference, in both directions. The reference states the version, the rule for changing it, and that the journal is a public interface. The readers of the journal do not use the module yet.
- `delegate stop <run-id>` stops a run now, and leaves it in a state that `delegate run --resume` goes on from (#184). Before, `delegate pause` stopped a run only at its next step boundary, which can be many minutes away, and to stop a run now a user had to find the process id and use `kill`. The command sends SIGTERM to the process that holds the lock of the run. The run ends the process group of its running child, writes `interrupted` in the journal and releases the lock (#178). The command waits up to 30 seconds for the lock to be free, prints the command that resumes the run, and exits 0. When the lock is still held at the end of the wait, it says so and exits 1. A run with no live process holder (ended, paused or stopped) exits 1 with the reason.
- `delegate run --dry-run` refuses a workflow that a run of it would fail for a reason of setup (#182). Before, a missing agent file failed the first agent of its stack, and a workflow gate that the verifier guard did not permit showed only when the verifier tried to run it, which can be an hour into the run. Now, after the plan, the dry run checks each stack. The specialist and the verifier must have an agent file for the adapter of the workflow, in the project directory (`--repo`) or in the user directory; for a missing file the message names the stack, the agent and the paths that the check looked in. The rendered verifier must permit each gate of the stack: for Claude Code the check runs the Bash hook of the verifier with the gate as the command, as the harness does, and for OpenCode it tests the gate against the `permission.bash` map with the matcher of the validator. For each gate that the verifier denies, the message names the gate, the stack and the agent file. The command prints `stack <name>: checked` for each stack with no problem, and exits 1 when it finds a problem. An adapter with no check gets one line that says that the check was skipped, and why. See `docs/reference/workflow.md` and `docs/reference/run.md`.
- A stack can set a time limit for a gate and for an agent session (#179). Before, `ShellGateRunner.run` waited for a gate without a limit, and the idle timeout ended a session only after a valid report, so a gate or an agent that hung before its report stopped a run for ever. `delegate watch --stall-minutes` showed the stall but could not act on it. Now a stack has two optional fields, `gate-timeout` and `agent-timeout`, in minutes. Each one is a number greater than 0, and a fraction is permitted. The workflow check refuses zero, a negative number and a value that is not a number, and its message names the field. With no field, the engine waits as before. The gate port takes the limit in `GateRunner.run(..., timeout=...)`. A gate that runs longer gets its process group ended, and the engine writes `gate-result` with `green: false` and the new field `timed_out: true`. The step goes on as for a red gate: the specialist continues with the trigger `gates-red`, and the output ends with a line that names the limit. The harness port takes the limit in the new field `AdapterRequest.agent_timeout` (seconds). When a session runs longer, the adapter ends its process group and sets the new field `AdapterResult.ended_timeout`, and an empty event stream is no error then. The engine writes the new event `agent-timeout` before the result event and takes the session as one with no valid report, so the existing continuation rules apply. `delegate status` and `delegate watch` name a timed-out gate and a timed-out session: the reason of a failed step, the problem line, and the lines of the feed. `docs/reference/workflow.md`, `docs/reference/run.md` and `docs/reference/status-and-watch.md` describe the fields, the events and the lines.

### Changed

- The `agent-delegation` skill tells the coordinator to tell the owner before it changes the course of a run, and to recover with the commands of the engine (#203). Before, the skill gave no rule for a pause, a stop, an abandon, a retry or a new run that replaces a run, and it gave no recovery path for an invalid verdict, a failed `economy` chain, a new ruling of the owner in the middle of a run, a stop now, giving up on a run, or a dev server that refuses a path with `.git`. A coordinator then used `kill` and removed run directories by hand, and the owner did not know of these steps until the end. Now the new section "Tell the owner before you change the course of a run" gives the rule: the coordinator tells the owner the run id, the reason and the exact command, and only then runs it. An earlier approval does not cover a later step. The section has one row of recovery for each case, with `run --resume`, `--retry`, `--retry` with a new ticket text, `delegate stop`, `delegate clean --abandon` and the default state root. It forbids `kill` on a process id of the engine and the removal of state directories by hand, and it tells the coordinator to check the version of the engine on the host before it starts a run. A test checks that each command of the section parses with the real parser of `delegate`.
- The default state directory is outside the git directory (#200). Before, it was `<git common dir>/delegate`, so each worktree of a ticket was under `.git/delegate/worktrees`, and a tool that refuses a path with a `.git` component failed there: Claude Code in `dontAsk` mode refused `Edit` and `Write` (#97), and the Vite dev server refused to serve the files, so each end-to-end test of a web stack timed out. Now the default state root is `$XDG_STATE_HOME/delegate`, or `~/.local/state/delegate` when `XDG_STATE_HOME` is not set, and the state of a repository is in `<root>/<name>-<key>`. No path that the engine gives to an agent or a gate has a `.git` component. `DELEGATE_STATE_ROOT` still sets the root. The engine writes `<git common dir>/delegate/state-root` for each new run, so each command finds the state from any shell. A run that started under `<git common dir>/delegate` stays there: `status`, `watch`, `stop`, `pause`, `clean` and `run --resume` still find it, and the list of `delegate status` shows the runs of both directories, newest first. `delegate run --dry-run` prints the state directory of the run. See `docs/reference/run.md`.
- `delegate status` shows a run with no live process as `stopped` and not `running` (#193). Before, a run with no `run-end` and no pause was `running`, also after a crash, a kill, a stop of the machine or Ctrl-C, so a model or a person that read `delegate status` reported a dead run as a run that works. Now `status` reads the lock of the run branch, as `watch` does: with no live lock holder, the state is `stopped`, the text output gives the note `no process works on the run; go on with delegate run --resume <run-id>`, and `--json` gives the state `stopped`. A run whose lock holder is alive is `running`, as before. An interrupted run (the journal holds `interrupted`) is `stopped` too. The clock of a stopped run stops at its newest event, and its snapshot has no ETA. See `docs/reference/status-and-watch.md`.
- The agent directories `.claude/agents/` and `.opencode/agents/` are built-in hotspots of each stack (#188). Before, the verifier ran in a copy of the ticket branch and loaded its definition (the prompt, the tools and the guard hooks) from the copy, and a specialist could change that definition on its branch, because the hotspots of a workflow did not name these directories. Now a specialist commit that changes a path in one of them is a `hotspot-finding`, as for any hotspot, and the step fails before a gate runs. The specialist brief lists the built-in hotspots with the others. The page on the limits of the enforcement model names what a specialist can still write: the state directory, the journal and the refs.
- The journal holds the token totals of each agent that ended, and `delegate status` and `delegate watch` read the journal and not the event streams (#183). Before, both commands got the token counts and the time of the last activity of every agent from its event stream, through `Adapter.activity`. The live view parsed each stream of each ticket again on each frame, about once a second. A run with 30 streams of 20 MB cost about 2.4 s of CPU for each frame, which is more than the poll interval, and the views depended on the stream format of each harness. Now, when an agent session ends, the engine reads its stream once and writes `tokens_new`, `tokens_cache` and `last_event` into its result event: `adapter-result`, `fixup-result` or `verify-result`. The views take the totals of an agent that ended from these fields, and read a stream only for an agent that runs now. For a journal of an earlier version with no totals, they read the stream as before. The reader of the live view also keeps the last result for each stream, keyed by the size and the modification time of the file, and parses the stream again only when one of them changes. See `docs/reference/run.md` and `docs/reference/status-and-watch.md`.

### Removed

- The adapter name `cursor` and each mention of Cursor as a harness of the kit (#195). Before, the workflow check accepted `adapter = "cursor"` and `delegate run --dry-run` passed, but no adapter implements it, so the run then exited 1. The kit names only the harnesses that it supports. Now a workflow with `adapter = "cursor"` fails the workflow check as any adapter that is not registered, and the message lists `claude-code, opencode` as the known adapters. The glossary, the abbreviations, the concepts page, the workflow reference, the run reference and the design content no longer name Cursor, and the entry "The Cursor adapter" is gone from the future ideas.

### Fixed

- The two how-to pages that show a dry run say that the agent files of each stack must exist first (#182). Before, `docs/how-to/point-the-tiers-at-a-gateway.md` and `docs/how-to/use-the-kit-after-to-spec-and-to-tickets.md` showed a dry run that succeeds, and a reader with no agent file in `.claude/agents/` or in the home directory got an error from the check of #182. The tests of both pages now write the agent files in the repository of the test and use an empty home directory, so their result does not depend on the host.
- Each command finds the state of a run from any shell, with no `DELEGATE_STATE_ROOT` (#199). Before, a coordinator that started a run with the variable kept its state in `<root>/<name>-<key>`, and `delegate watch` in a shell without the variable looked in `<git common dir>/delegate`. The owner saw an older paused run, and not the live run. Now the engine writes the absolute path of its state directory to `<git common dir>/delegate/state-root` before `run-start`, when the directory is outside `<git common dir>/delegate`. `status`, `watch`, `stop`, `pause`, `clean` and `run --resume` use the variable when it is set, then the path in `state-root`, then `<git common dir>/delegate`. When the variable and `state-root` name different directories, the command uses the variable and prints one warning line on stderr that names both. See `docs/reference/run.md`.
- A detached run that gets SIGINT stops, as it does for SIGTERM (#198). Before, `kill -INT <pid>` of a run that a coordinator started from a background shell did nothing: the run went on, the journal had no `interrupted` event, and the child processes stayed alive. The cause is that a shell that is not interactive sets SIGINT to ignored for a command that it starts with `&`, and `delegate run --detach` and its setsid child inherit that setting. Python installs its handler for SIGINT only when SIGINT is not ignored, so the run had no handler. Now the run handles SIGINT as it handles SIGTERM and SIGHUP when it inherited SIGINT as ignored: it ends the process group of the child, appends `interrupted`, releases the lock and exits 130 within seconds.
- A report with a raw control character in a string is a valid report (#197). Before, the engine read each report and each verdict with the strict JSON parse, which refuses a raw tab or a raw newline inside a string. A verifier that wrote such a character in a finding failed the step with "the verifier returned no valid result", though the verdict was ACCEPT, and the coordinator had to start a new run for one character. Now the engine reads each specialist report, fix-up report and verdict with a parse that accepts raw control characters in strings, and all other checks of the report stay as they are. When a report needed this parse, its `report-validation`, `fixup-report` or `verify-report` event holds `lenient_parse: true`. A file that is not JSON for another cause is still invalid, with the same message as before. See `docs/reference/run.md`.
- The live view and `delegate status` show the verification of an `economy` chain, and the ETA does not show a false end (#196). Before, each ticket row was `built` while the gates of the chain ran, and no row showed the gate, its time or its log. The ETA was `0s` and the percentage stayed at the share of the tickets, for the whole time of the chain: on run `cce3`, a chain gate ran for more than 10 hours and the view showed five `built` rows, `83%` and `ETA 0s`. Now the table has a chain row for each stack that started its verification, under the last ticket of the stack, with its phase (`gates`, `verifier` or `fix-up`), the time used, the gate command and the age of its log, the tokens and the activity of the verifier, and, when the chain ended, its state (`accepted` or `rejected`) and its verdict. A running chain counts in the percentage by its phase. The ETA is `-`, and not `0s`, while a unit of the run runs and the estimate is 0 or less. `delegate status --json` has the new list `chains`. When the rows fold to fit the height of the terminal, the rows in the middle now fold also when no ticket comes after the running one, so the last row stays on the screen. See `docs/reference/status-and-watch.md`.
- A stop during the verifier session does not hide a change that the verifier made to the real worktree (#192). Before, the engine kept the snapshot of the worktree only in memory, and compared it after the session. A Ctrl-C or a kill during the session therefore skipped the comparison. The resume went on with the step, ran the gates on the HEAD that the verifier had changed, and started a new verifier that reviewed the commit of the first verifier as if the specialist made it. No `invariant-violation` was written. Now `verify-start` records the snapshot in the new field `snapshot`. A resume of a step whose newest `verify-start` has no `verify-result` compares the worktree with that snapshot before it does anything else. On a difference it writes `invariant-violation` and halts the run, and it runs no gate. Also, the check for `invariant-violation` in a resume now comes before the check that the plan did not change, so a journal with `invariant-violation` and no `run-end` is refused when the workflow is the same as before. See `docs/reference/run.md`.
- A failed append or a torn last line does not make the journal unreadable (#191). Before, `Journal.append` added to `seq` before it wrote the line, so a write that failed (a full disk, for example) left a gap in `seq`, and `read_events` refused the journal with "line N is not an event with seq N". A power loss that cut the last line made `delegate run --resume` and `delegate clean` refuse the journal, while `delegate watch` read it. One journal that could not be read also made `delegate status` with no run id fail for the whole repository. Now `seq` grows only after the write succeeded, each line is one write call on a file open to append, and a failed write leaves no part of the line. The engine syncs the file after `run-end`, `run-branch-advance` and `verdict`. When a command opens a journal to append, it removes a last line that has no newline at its end, and writes the new event `journal-repaired` with `bytes_removed`. `delegate run --resume` and `delegate clean` read a journal with a torn last line. The listing of runs of `delegate status` and `delegate watch` skips a journal that it cannot read, names it on stderr, and shows the other runs. See `docs/reference/run.md` and `docs/reference/status-and-watch.md`.
- The engine halts the run when a commit that it did not advance to is on the run branch (#186). Before, the engine said that the run branch moves only on ACCEPT, but it did not check this. It rebased onto the tip of the run branch and fast-forwarded from that tip, whatever the tip was. A commit that moved the run branch from outside the engine (a specialist with a shell, a person, another tool) landed with no verification: the verifier diff is the ticket branch against the run branch, so it did not show the commit, and the run ended `built`. Now the engine keeps the tip that the journal says: the `to_commit` of the newest `run-branch-advance`, or the `base_commit` of `run-start` when the run branch did not move yet. It compares the real tip with it before each rebase onto the run branch, before each fast-forward, before the chain verification of `economy` mode, and at each resume. On a difference it writes the new event `run-branch-moved` (`expected`, `found`) and halts the run as for an invariant violation: the step fails, the later tickets are skipped, the run ends `failed`, and a resume, a retry and a plan change of the run are refused. See `docs/reference/run.md` and `docs/explanation/the-enforcement-model-and-its-limits.md`.
- Each command that a skill gives parses with the real parser of that command, and the `--mode` example is correct (#185). Before, the section "When to use the engine" of `skills/agent-delegation/SKILL.md` gave `delegate run <workflow> --mode assure|economy`, and the CLI refused it with `unrecognized arguments: --mode economy`, because the mode is the field `mode` of the workflow file and not an option. The reference pages had tests that keep their option tables equal to the parsers, and the skills had none. Now `tests/test_skill_commands.py` reads each command line in both `SKILL.md` files that starts with `delegate `, `agent-definitions ` or `verifier-brief `, in fenced code and in inline code. It replaces each placeholder `<...>` with a sample value and parses the line with the real parser of the command, with no run. A refused line fails the test, and the message names the file and the line. The comment `<!-- not-a-command -->`, on the line of an inline code or directly above a fence, marks a line that is not a command, such as a synopsis with `[--flag]`. The test found more lines, and the change fixed them: the `bootstrap` example and the `fixup` example of the protocol skill used `[--flag ...]` forms that no parser accepts, two mentions of `delegate pause` had no run id, and one mention of `verifier-brief fixup` was a fragment. The synopsis blocks of the renderer skill carry the marker.
- The workflow check refuses a ticket id and a branch name that the engine cannot use, before the run starts (#181). Before, the check made sure only that an id was a string and unique. The engine uses the id in a path (`worktrees/<run-id>/<id>`) and in the ticket branch name. An absolute path as an id put the worktree outside the state directory, and the push guard then deleted and wrote that path. An id with a space failed only after `run-start`, when the run branch existed, so the step crashed, the later tickets were skipped, and the next run was refused. Now an id must match `^[A-Za-z0-9][A-Za-z0-9._-]*$` and must not hold `..`. `base-branch`, `run-branch` and each ticket branch (`<run-branch>-<id>`) must follow the ref-name rules of git: no space or control character, no `..`, none of `~^:?*[\`, no `@{`, no `//`, no part that starts with `.`, and no end with `/`, `.` or `.lock`. The check is in Python and starts no process. Each problem is one line of the `WorkflowError`, so `delegate run --dry-run` lists each one and exits 1. `docs/reference/workflow.md` describes the rules.
- A resume closes an accepted step when the run branch holds its commit (#180). Before, the engine moved the run branch first and wrote `run-branch-advance` after it. A stop between the two (Ctrl-C or SIGKILL) left a step that the verifier accepted and whose commit had landed. The resume then failed the step with `holds its work already`, `--retry` was refused because the step failed after the verdict, and the engine skipped the tickets that it blocked. Now, on a resume of an open step in `assure` mode, the engine checks two facts: the newest verdict of the step is ACCEPT, and the run branch holds the commit of the `verify-start` of that verdict. When both are true, it writes the missing `run-branch-advance` with the new field `recovered: true`, then `step-end` with the state `built`, and goes on with the next ticket. A resume after an ACCEPT whose commit the run branch does not hold moves the run branch as before. `docs/reference/run.md` describes the field and the rule, and no longer lists this stop as a limit.
- SIGTERM and SIGHUP stop a run as Ctrl-C does, and no child process stays alive after the engine (#178). Before, the engine had no handler for them. `kill <pid>` of a detached run (it has no terminal, so this is the usual way to stop it) ended the engine at once: the journal had no `interrupted`, the lock stayed, and the harness or the gate kept running and committing in the worktree. Then `delegate run --resume` took over the lock and started a second agent in the same worktree. Now `delegate run` turns SIGTERM and SIGHUP into the same interrupt as Ctrl-C: the run writes `interrupted`, releases the lock, prints the command that resumes it, and exits 130. The harness process and each gate process start in a session of their own, and the engine sends its signals to the whole process group: at the idle end of a session, on an interrupt and on an error, it sends SIGTERM to the group, waits up to 10 seconds, and sends SIGKILL to the group. On an interrupt this happens before the lock is released. A gate also gets its standard input from `/dev/null`, so a gate that reads it gets end of file at once and does not wait for the terminal. SIGKILL to the engine cannot be handled, so it still leaves the lock and the children. See `docs/reference/run.md` and `docs/how-to/watch-and-resume-a-run.md`.
- A failure of the harness halts the run, and `--resume` goes on at the open step (#177). Before, an `AdapterError` from the adapter (a harness that is not logged in, a CLI that is missing or changed, a rate-limit exit) failed the step, skipped the later tickets and ended the run with `run-end` `failed`. Then `--resume` was refused, `--retry` was refused because the specialist gave no valid report, and a new run was refused because the ticket branches existed already. Now the engine writes the event `halted` (the ticket, the role, the round and the message), and no `step-end` and no `run-end`, and it releases the lock. `delegate run` prints the message and `delegate run --resume <run-id>`, and exits 4. `delegate status` shows the run as `halted` with the message, and `delegate watch` ends on `halted` with the exit code 8. Each other exception is a crash, as before. See `docs/reference/run.md` and `docs/reference/status-and-watch.md`.
- A gate does not run in a worktree that holds a change that is not committed (#176). Before, the engine recorded a green gate on the HEAD commit, but ran the gate in the worktree as it was. A file that the specialist did not commit, for example a `feature.txt` that it wrote and did not add, could make a gate green that was red on the commit. The rebase that kept the commit then skipped the gate, and the verifier brief said that the gates were green, so the run branch got a commit that was red on its own, and no event showed it. Now, before the gates of the build phase, the engine reads the changes of the worktree that are not committed; a file that git ignores does not count, and neither does a file that red gates of the same run left. When there is one, the engine runs no gate and continues the specialist with the new trigger `uncommitted`: the prompt names each path and tells the specialist to commit or remove it, the continuation counts against the continuation limit, and at the limit the step fails with a reason that names the paths. In `economy` mode the engine reads the worktree at the end of the specialist run too, because the chain gates run on that tree. After a fix-up (also in a chain), a path that the fix-up specialist left uncommitted fails the step with a reason that names the paths, and no gate runs. The rebase needs no check: no agent runs between the build gates and the rebase. The event `gate-result` now has the field `clean`, which is `true`, and only a green result with `clean: true` makes a later gate a `gate-skip`, so a result from a journal of an earlier version does not skip a gate. To upgrade: a gate that makes files that git does not ignore, for example `__pycache__/`, needs an entry in `.gitignore`, or the engine counts those files as a change that is not committed after a restart of the step. `docs/reference/run.md` describes the trigger and the field.

## [1.10.0] - 2026-10-22

### Added

- The command `delegate clean [<run-id>...] [--ended] [--merged] [--dry-run] [--repo <repo>]` removes what ended runs left behind (#168). Before, a run that ended before the clean-up of #167, or with `keep-worktrees = true`, kept its ticket worktrees, its ticket branches and their fsmonitor daemons, and no command removed them or a run branch that the coordinator had merged. Now `clean` takes run ids or the short run ids, and `--ended` selects each run of the repository. It cleans a run only when the newest `run-end` of its journal after its newest `resume` has the result `built`, and no live process holds the lock of its run branch; a run that is active, failed, paused or stopped keeps everything, and its line names the reason. For a run that it cleans, it applies the rules of the clean-up of #167: it stops the fsmonitor daemon of each ticket worktree, removes each worktree with no change that is not committed, with its hooks directory, and deletes each ticket branch that the run branch holds with `git branch -d`. It also removes each verifier copy and proof copy that the journal names and that a killed run process left. `--merged` also deletes the run branch when the base branch holds it, with `git branch -d`; when the run branch is gone already, the base branch is the holder of the ticket branches. The command holds the lock of the run branch while it cleans the run, and runs `git worktree prune` before the runs and at the end, so a ticket branch whose worktree directory a person removed by hand can go too. It prints one line for each run, with the worktrees removed, the branches deleted, each item kept with its reason, and the space freed. `--dry-run` prints what it would remove and keep, and changes nothing. The command exits 0 when it removed or kept each item by the rules, 1 on an error, and 2 with no run id and no `--ended`. The journal of each run where something went gets one `cleanup` event after its `run-end`, with the fields of the engine's event, `copies_removed` and `bytes_freed`; `delegate watch` and `delegate status` still read the run as ended. The version-control port gets `prune_worktrees`. `docs/reference/commands.md`, `docs/reference/run.md`, `docs/how-to/watch-and-resume-a-run.md` and the `agent-delegation` skill describe the command: a coordinator runs `delegate clean --ended --merged` after it merges a run.

### Changed

- A run that ends `built` removes its ticket worktrees and the ticket branches that the run branch holds (#167). Before, the engine removed nothing that a run made, so a repository collected worktree directories, registered worktrees, `run/*` branches and, with `core.fsmonitor` on, one `git fsmonitor--daemon` for each worktree that did not stop by itself. Now, before `run-end` with the result `built`, the engine stops the fsmonitor daemon of each ticket worktree and removes the worktree with `git worktree remove`, with its hooks directory. A worktree with a change that is not committed stays; a file that a gate made and that git does not ignore, for example `__pycache__/`, is such a change. The engine then deletes each ticket branch whose commits the run branch holds with `git branch -d`, never `-D`; a ticket branch that the run branch does not hold stays, and so does the branch of a worktree that stays. The run branch, the journal, the reports and the gate logs stay. The journal records one `cleanup` event with the worktrees removed, the branches deleted, and each one kept with its reason; `delegate status` and `watch` show no line for it. A run that ends `failed`, a paused run and a stopped run keep everything, because `--retry` and a resume need the worktrees. A plan change that goes on with a run that ended `built` makes new worktrees, and in `economy` mode a new ticket after the chain starts from the run branch when its predecessor's branch is gone; the clean-up runs again at the next `run-end` with the result `built`. The new workflow field `keep-worktrees = true` turns the clean-up off for a run. `docs/reference/run.md`, `docs/reference/workflow.md` and `docs/reference/layout.md` describe the clean-up and the field.

### Fixed

- Security fix of the verifier guard: a word after a gate cannot make the gate write (#163). Before, the guard matched a gate by its first words and did not examine the words after it, so `cd app && npm run lint -- --fix` (it rewrites source files), `cd app && npm test -- -u` (it updates snapshots), `cd app && npx tsc --outDir /Users/x/o` (it writes outside a temp directory) and `cd api && ./gradlew test spotlessApply` (it runs a task that formats the source) passed the guard (1.8.0 and 1.9.0). Now, after a plain gate, the guard permits only a path that exists in the git toplevel of the working directory or in a temp directory, for example a test file, the separator `--`, a number (all digits, #169), a redirection, and a flag of the new declaration key `gateExtraFlags`. Each other word denies, and the message names the word and the gate. A relative path counts from the directory of the last `cd` of the command. A flag of `gateExtraFlags` is permitted alone or with `=` and a value in the same word, and an entry `"<flag> <value>"` also permits the next word as the value of the flag, unless that word starts with `-`: a parser such as yargs (Jest) takes no such word as a value, so the guard tests it as a word of its own, and `npm test -- -t -u` denies. The declaration parser checks each entry; `bootstrap` has no flag for the key. `gateExtraFlags` is one list for the declaration: it applies to each gate with no ` *`. A gate with no word after it stays permitted. A gate in `gateCommands` that ends with ` *`, for example `"./gradlew *"` or `"nix eval *"`, takes free arguments (#169): the guard permits each word after it, as before this fix, so `./gradlew test jacocoTestReport -x processTestAot` and `nix eval --raw .#x` pass. The rules for redirections, temp writes and git trees still apply to it. The guard does not check the words after such a gate, so the rendered verifier names each such gate and tells the verifier not to put a word there that can make the gate write. The verdicts are the same in bash, `/bin/sh` and zsh. The OpenCode verifier map now permits each plain gate only as its exact text, with no ` *`, because a pattern cannot tell a path from a word that writes: declare each form of a gate that an OpenCode verifier needs. A gate that ends with ` *` becomes the rule `<gate> *` (#169). To upgrade: if your verifiers run a gate with arguments that are not paths, for example task names, flake refs or subcommands, add ` *` to that gate in `gateCommands`, or list its read-only flags in `gateExtraFlags`, and render the agents again. The example declaration sets `gateExtraFlags = ["--info"]`, and the declaration of this repository names its test gate in full, `nix develop -c python3 -m pytest -rs -n auto`. `docs/reference/opencode-adapter.md`, the enforcement page, ADR 0004 and the `agent-definitions` skill describe the rules, and the skill tells how to choose between a gate with no ` *`, `gateExtraFlags` and ` *`.
- Security fix of the verifier guard: a read command of a declaration does not permit a write subcommand after it (#164). Before, the guard matched a `getOnlyCommands` entry by its words and permitted each word after it, except a method, body or output flag, so with the entry `tea issues` it permitted `tea issues create -t x` and `tea issues close 12`, which write to the issue tracker, and with `gh issue` it permitted `gh issue create` (1.9.0). Now, after the words of an entry, the guard permits only an option (a word that starts with `-`), the word after an option with no `=`, a number, a path (a word with a `/`) and a redirection. Each other word can be a subcommand, so it denies, and the message names the word and the entry. `tea issues`, `tea issues 12` and `tea issues --state open` stay permitted, and `./scripts/api /health` stays permitted. An entry that ends with ` *`, for example `"tea issues list *"`, is a prefix on purpose: the guard permits each word after it, as before, the declaration parser accepts it, and the rendered Claude Code verifier states that the entry is a prefix. The verdicts are the same in bash, `/bin/sh` and zsh. The OpenCode verifier map permits no `getOnlyCommands` entry, as before. The guard cannot tell an option that takes a value from one that takes none, so it reads the word after each option as a value; the `agent-definitions` skill states this limit. The committed verifier pair of this repository is rendered again. ADR 0004 and the `agent-definitions` skill describe the rule.
- The verifier guard reads `--o` and `--ou` as `--output`, and a write target with a `..` component has its own deny message (#165). First, the rendered Claude Code verifier said that the hook denies `--output` and each prefix of it, but the guard read the prefixes only down to `--ou` after a git read command, so `git diff --o /Users/x/o` passed (git 2.54.0 rejects `--o=` as ambiguous), and only down to `--out` after a GET-only command. A command built on argparse accepts a unique prefix of a long option, so `agent-definitions render <file> --ou /Users/x/o` writes to `/Users/x/o`, and with `getOnlyCommands = ["agent-definitions render"]` the guard permitted it (1.9.0). Now the guard reads each prefix of `--output` down to `--o` as the output option, after a git read command and after a GET-only command: the path must be a temp path. The rendered Claude Code verifier, the verifier brief and the reference page of the commands state the new form.
- The verifier has a binding rule for the case where it cannot make the temp copy of a red proof (#152). On one host, Claude Code refused each recursive copy (`cp -r`, `cp -R`, `cp --recursive` and `cp -a`), and the deny list of the host refused `rm -r`, so the break-a-copy recipe could not run. Now, when a step of the recipe is refused or fails, the verifier does not break a check, a test or a file in the worktree under review, and does not make the red proof there. It puts the red proof in `unverified`, with the refused command and its message. The gates can still run in the worktree as read-only checks. The reason: the worktree is the work under review, and the engine checks that the verifier left it as it was (the worktree invariant). The rendered verifier (Claude Code and OpenCode), the verifier brief of a `delegate run`, the committed verifier pair of this repository, the two skills and the enforcement page state the rule.

- On a terminal, `delegate` sets the title of the terminal with the OSC 2 sequence, so the tab shows the command and not the name of the Python process (#80). `delegate watch` shows `delegate watch · <short run id> · <percent>% · ETA <HH:MM>` while it follows the run, and the result when it ends. `delegate run` shows `delegate run · <short run id>`, and each other subcommand shows `delegate <subcommand>`. When standard output is not a terminal, or when `DELEGATE_NO_TITLE` is `1`, `delegate` writes no title.
- A stack of a workflow file can name MCP servers in its new `mcp-servers` table. The engine gives them to the specialist and the verifier of that stack (#87).

### Fixed

- One run has one base: the commit of `base-branch` at the start of the run. The journal records it in the new field `base_commit` of `run-start`, the run branch starts at it, and a resume uses it, not the tip of `base-branch`. No ticket branch starts from `base-branch` itself. Before, a ticket branch that the engine made after a commit landed on `base-branch` started from that newer commit. The rebase onto the run branch then copied the commits of `base-branch` onto the ticket branch, and the verifier diff and the hotspot guard saw them as the work of the ticket (#90). A resume of a journal of 1.2.0 or earlier, which has no `base_commit`, takes the base of the run from the first `run-branch-advance`, or from the tip of the run branch.
- In `assure` mode, a ticket with `blocked-by` starts from the tip of the run branch, also with the default `ticket-start = "base-branch"`. Its blockers are accepted before its step starts, so its branch holds their commits, and its specialist sees their work. Before, the branch started from `base-branch`, and a ticket that changed the files of its blocker stopped with a conflict at the rebase onto the run branch (#91). A ticket with no `blocked-by` keeps the rule of `ticket-start`.
- A resume of a step that the engine rebased onto the run branch counts the commits of the ticket from the commit that the branch was rebased onto. So the hotspot guard and the continuation brief do not see the commits of the run branch under the ticket.
- A specialist that commits its work and writes no report does not fail the step at once. The engine sends a continuation that asks only for the report, as for a report that is not valid. The journal records the trigger `report-missing`, and the continuation counts against the continuation limit of the mode. A missing report on a branch with no commit of the ticket still fails the step (#85).
- `delegate run --resume <run-id> --retry <ticket>` also goes on with a failed step of `economy` mode. It uses the worktree and the commits of the step again. The specialist continues, with the continuation limit of the mode again, or, after a valid report that says `committed`, the engine checks the step again. The journal records the `retry` phase `specialist` or `gates`. The skipped tickets after the step are checked again, and the chain then goes on to the chain verification, which covers only the built tickets whose work the run branch does not hold. A step that the chain verification failed, a step that a later built ticket went past, and a step whose chain start moved cannot be retried (#85).
- `delegate run --resume <run-id>` takes over a lock that names the same run id and a process that no longer exists, with no flag. The journal records `lock-broken`, and stderr names the old process. A lock whose process is alive still stops the resume, and a lock of another run still needs `--break-lock` (#92).
- The verifier guard denies a redirection with `&` to a file: `>&word`, `>& word`, `n>&word` and each `>>&`. It permits `>&` and `n>&` only before a file descriptor number or `-` (#89).
- `delegate watch` and a resume give a text, not `None`, for a report or a step end with a null reason (#89).
- The engine keeps the push guard and the `core.fsmonitor` rule of a worktree in the include file `delegate.config` in the git directory of the worktree, and no longer sets `extensions.worktreeConfig`, which go-git tools such as `tea` refuse. A worktree of an earlier version moves its settings to the include file (#84).
- A `tool_progress` heartbeat and a `thinking_tokens` event of Claude Code count as activity. These events have no `timestamp`, so `delegate status` showed an old last activity for an agent that worked. When the newest event of the stream is one of them, the time is the modification time of the stream file (#81).

## [1.3.0] - 2026-10-18

### Added

- A host can give every agent a Claude Code settings file and a permission mode, with no change to a workflow file. The `claude-code` adapter adds `--settings <path>` when `DELEGATE_AGENT_SETTINGS` is set, and `--permission-mode <mode>` when `DELEGATE_PERMISSION_MODE` is set, for each specialist and each verifier. A settings path that is relative or not a file stops the adapter before an agent starts. The settings file must not turn off hooks, because the verifier guard is a hook. With neither variable, the command does not change. For OpenCode, a host sets `OPENCODE_CONFIG`, which OpenCode reads itself; the `opencode` adapter writes a warning when either variable is set.
- A tool that a permission mode refused (an error tool result with the refusal text) is in the new `refused` field of the result events (`adapter-result`, `fixup-result`, `verify-result`), with the tool and the mode. `delegate watch` shows it as a problem that names them. The harness port has the new result field `refused`; an adapter outside the kit that does not set it still works.
- A host can move the state directory of every repository out of the git directory with `DELEGATE_STATE_ROOT`, an absolute path. Each repository gets `<root>/<name>-<key>/`, where the key comes from its git common directory, so the worktrees, the reports, the journals and the locks are on paths with no `.git` component. Claude Code in `dontAsk` mode refuses `Edit` and `Write` on such a path, also with an allow rule. `run`, `status`, `watch` and `--resume` all find the directory. With no value, the state stays in `<git common dir>/delegate/`.
- The package has a `test` extra: `pip install '.[test]'` installs `pytest` and `pytest-xdist`, so the suite can run in parallel with `python -m pytest -n auto`. The development shell of the flake also holds `pytest-xdist`.

### Changed

- In `economy` mode, the engine runs no gate for one ticket. A valid report with the status `committed`, on a branch with a commit of the ticket, builds the step. At the end of the chain, for each stack, the engine runs the gates once on the chain tip. Red gates start a fix-up round with the output of the red gates, and the gates then run again. Green gates go on to the verifier of the chain. Its brief holds the gate commands, the commit and the output of the green gates, and it tells the verifier not to run the gates again. A REJECT starts a fix-up round, then the gates, then a scoped verifier. The rounds of red gates and of a REJECT count together against the fix-up limit of `economy` mode, which goes from 1 to 2. Before, the engine ran the gates after each ticket, and the verifier of the chain ran them again. `assure` mode does not change.
- The gate events on the tip of an `economy` chain have the phase `chain`. The `fixup-start` event of a chain also has `stack`, `tickets`, and `trigger` (`gates-red` or `reject`).
- In `economy` mode, `delegate status` shows the phase `gates` for the run while the gates of the chain run. The percentage and the ETA count the gates as part of the verification of the chain.

### Fixed

- A verifier that cannot write its verdict file still gives a verdict. When the file is missing, the engine takes the last JSON object with a `verdict` field from the final text of the verifier, writes it to the report path, and checks it as a file; `verify-report` records `source` `final-text`. The verifier brief tells the verifier to end its final message with the verdict object. A host whose permission mode refuses a shell redirect to a file (Claude Code in `dontAsk` mode) needs this. The harness port has the new optional result field `final_text`; an adapter outside the kit that does not set it still works.
- A verifier can write its verdict through the verifier guard. The guard refuses a heredoc and a here-string, and some characters of a command, also inside quotes, so a verifier that tried a heredoc, or a verdict with a backtick in its evidence, failed the step after all its work. The report section of each verifier brief (full, fix-up, and chain) now names the one form that the guard permits: `printf '%s\n' '<json>' > <report path>`, with the JSON on one line, and `$`, the backtick, the apostrophe, `<`, `>` and `&` written as JSON escapes.

## [1.2.0] - 2026-10-17

### Added

- `delegate status` shows the progress of a run: under the run line, the percentage, the tickets that ended, the time used, the ETA, and the tokens. Under the line of each ticket with a step, it shows the phase, the time used, the tokens, and the time since the last activity of its agent. Each form of `status` also works for a run whose adapter the process does not know, or whose adapter has no stream reader: it then shows no tokens and no activity, and the JSON gives `null` for them.
- The token count of a Claude Code stream uses the `usage` of each `result` event. For a session that has no `result` event yet, it adds the usage of each turn, one for each message id. The reference page of `status` documents the rule.
- `delegate status --json` prints one snapshot of a run as JSON. It gives the state, the time used, the tickets that ended, the percentage, the ETA, and the tokens of the run. For each ticket it gives the state, the phase, the time used, the tokens, and the seconds since the last activity of its agent. The reference page of `status` documents each field, and the rules of the percentage and the ETA.
- `delegate watch --raw` prints the raw line of each event also when standard output is a terminal.
- The journal event `agent-start` names the event stream of each agent before the agent starts: the specialist, each continuation, the fix-up specialist, and each verifier.
- The journal event `gate-start` names the gate command and a log file before each gate runs. The gate runner writes the output of the gate to that file while the gate runs. `delegate watch --stall-minutes` counts a change of a gate log as a change, so a long gate that writes output is not a stall. `delegate status` shows the gate that runs and the time since its log changed, in each form. The JSON has the new ticket fields `gate` and `gate_idle_seconds`.
- `delegate run --resume <run-id> --retry <ticket>` goes on with one failed step of `assure` mode, also in a run that ended. It spawns no specialist. It uses the worktree and the commits of the step again, and goes on at the first phase that did not complete: the gates, the verifier, or the scoped verifier. The journal records `retry`. A built step, an unknown ticket, and a step that needs a new specialist make the command exit 1 with a message.

- The workflow field `ticket-start` sets the branch that each ticket branch of `assure` mode starts from. With `run-branch`, a ticket branch starts from the tip of the run branch, so a run can hold a sequential chain of tickets that change the same files, and the engine still verifies each ticket at once. The default, `base-branch`, keeps the earlier behaviour. `run-branch` in `economy` mode is an error.

### Changed

- `delegate watch` on a terminal shows a live view. At the top, the live block shows the snapshot of `delegate status`: one line for the run, and one line for each ticket, drawn again in place at each poll. Below it, a feed shows one short line for each event that matters: the local time, the ticket, and what happened, with no path and no `None`. A problem and a stall are lines that start with `✗`. When standard output is not a terminal, or with `--raw`, `watch` prints the raw lines as before. The exit codes, the options, and the last line `position <seq>` do not change. `delegate status` prints the state once and exits: the live view is in `watch`, and `status` has no `--follow`.
- In `economy` mode, `delegate status` counts the verification of the chain as one more unit of the run, in the percentage and in the ETA. The percentage stays below 100 until `run-end`. While the verification runs, each form of `status` shows its phase, `verifier` or `fix-up`, and the JSON has the new run field `phase`. Before, `status` showed 100% and an ETA of 0 seconds while the verifier of the chain ran.
- The gate port changed, so a gate runner outside the kit must change too. `GateRunner.run` has the new argument `log`: the path of a log file that the engine makes for each gate run. The runner appends the output of the command to that file while the command runs.
- A verifier run that ended with no verdict, for example one that the time limit of a harness killed, does not count against the fix-up limit. A resume runs that round again with the same round number. Before, the resume started the next round, and the step lost one of its fix-up rounds.
- The harness port changed, so an adapter outside the kit must change too. `AdapterRequest` has the new field `event_stream`: the engine chooses the file of the stream, and the adapter writes the stream there. The helper `stream_path` of `delegate.adapters.streams` is gone. An adapter has the new method `activity(stream)`, which returns an `Activity` with the tokens so far and the time of the newest event. `read_events` raises `AdapterError` for a stream file that is missing.
- The stream of a verifier is in `runs/<run id>/verifier/<ticket id>/` from the start, not in the temporary copy. `delegate watch --stall-minutes` now sees the stream of an agent that runs, because the journal names it at the start.
- A valid report and a success result continue the step, whatever the exit status. Before, a session that a coordinator stopped with SIGTERM (exit status 143) after its valid report failed the step. The end state of an adapter result now comes from the stream only, and the engine weighs the exit status. `delegate watch` does not show a `finished` result with a bad exit status as a problem: the report event or the `step-end` decides.
- A specialist report that is not valid, on a branch with a commit, does not fail the step at once. The engine sends a continuation in the same session that asks only for a corrected report, and names each problem of the check. The journal records the trigger `report-invalid`, and the continuation counts against the continuation limit of the mode. A missing report, and a report that is not valid on a branch with no commit, still fail the step.
- After a valid report, the engine ends an agent session that writes no event for 900 seconds, and the step continues. The journal records `idle-timeout`. The harness port has the new request fields `idle_timeout` and `report_valid`, and the new result field `ended_idle`. The helper `run_harness` of `delegate.adapters.process` runs a harness process and ends an idle session. An adapter outside the kit that ignores the new fields still works, but the engine cannot end its idle sessions.

## [0.1.0] - 2026-10-09

The first release.

### Added

- Two agent skills as plain Markdown directories: `agent-delegation` (the protocol of a coordinator, a specialist and a verifier) and `agent-definitions` (the renderer and the validator).
- `delegate render` writes a specialist and its verifier twin for Claude Code and OpenCode from one declaration. A tier table gives the model for each harness.
- `delegate validate` checks the rendered agent files against the schema of each harness. Each finding has a code.

- `delegate brief full` and `delegate brief fixup` build the brief of a blind verifier.
- `delegate run` is the workflow engine. It makes the worktrees, drives a harness through a headless adapter, runs the gates, spawns the verifiers, and records each step in a journal. It has two modes: `assure` verifies each branch at once, and `economy` verifies at the end of a chain.

- `delegate status` and `delegate watch` show the state of a run and follow its journal. A stopped run resumes.
- `delegate docs` writes the generated sections of the reference pages from the code. A test fails when a committed page differs from the code.

- A neutrality check that fails when a term of a private denylist appears in the tree.
- Documentation: a tutorial, seven how-to pages, six explanation pages with the decision records, and the reference pages.
- `CONTRIBUTING.md`, with the setup with `pip` and `pytest`, the test-first rule, the regeneration command, and the checklist for a new adapter.
